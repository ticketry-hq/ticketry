# Source-control pull-request DRF override record

## Commit, push, and open a GitHub pull request for a task worktree

- DRF-native capability attempted: a serializer-backed create action on `WorktreePullRequestViewSet`.
- Exact missing behavior: the request drives a git working tree and the user's `gh` CLI rather than creating an ORM row, so there is no model, queryset, or instance for `CreateModelMixin` to build. The response is an ordered list of five typed step outcomes, and both a rejected push and a refused pull request are explicit `failed` steps on `200` rather than errors — a commit that already landed and a branch that was already published are the only record the caller has of them, and an error envelope would carry neither.
- Why a frontend adapter over the generated SDK is insufficient: only the sidecar can stage a working tree, run `git commit` with the repository's hooks, push an explicit refspec, spawn a headless generator CLI, and invoke `gh pr create` in that checkout. A client sequencing three calls could also commit and then fail to push, or push a commit the user never confirmed.
- Why a serializer field / `validate` / `read_only_fields` is insufficient: the request serializer does validate the whole input — three context identifiers and nothing else — but resolving the base branch, checking the login, generating the title and body, and running the three steps in order is application behavior with no serializer expression.
- Why `permission_classes` and `get_queryset` scoping are insufficient: default API-key authentication applies, and the scope that matters is not a queryset but the recorded worktree path for the task; `apps.source_control.checkouts.checkout` resolves it and refuses anything that is no longer a git checkout. The GitHub scope is the user's own `gh` login, which this app never reads.
- Why a database constraint/default is insufficient: what may be committed, whether the remote would accept the push, which branch is the repository's default, and whether a pull request already exists are all current git and GitHub facts held outside the database.
- Why an existing service function is insufficient: the application operations `apps.source_control.actions.pull_request_action.commit_push_and_open_pull_request_for_task` and `open_pull_request_for_task` own all of the behavior; the custom seam only invokes and serializes them.
- Smallest custom seam: `WorktreePullRequestViewSet.commit_push_pr` and `WorktreePullRequestViewSet.pull_request`.
- Service module / `transaction.atomic` used: `apps.source_control.actions.pull_request_action` coordinates the stack, `apps.source_control.actions.pull_request` and `apps.source_control.clients.gh_cli` own the provider boundary, and writes are serialized per checkout through `apps.source_control.actions.checkout_lock` for the whole three-step sequence. No transaction is used or wanted: the durable state changed here is a git repository and a GitHub pull request, and holding a database transaction across a hook or a network call would be worse than useless.
- Protected fields excluded from the request schema: no title, no body, no base branch, no head branch, no reviewer list, no path list, no remote, no `force`, no `--no-verify` equivalent, no GitHub token, and no filesystem path are accepted. The text is generated inside the action, the base is resolved from the repository, hooks always run, the push never forces, and the login is the user's own `gh` — none of which a client may override. Branch, base branch, sha, pull request URL, title, text source, subject, message source, and counts are read-only response fields.
- Identity/scope binding (URL kwarg + queryset filter): `task_id` is required in the body, with optional `parent_id` and `module_id`; the worktrees service derives the top-level worktree identity from that context, exactly as the review reads and the other actions do.
- Contract-drift and regression test: `apps/source_control/tests/test_pull_request_api.py` and `test_pull_request_message.py` cover the ordered five-step success, the body-file and no-token provider contract, generator preference and template fallback, default-branch rejection, dirty-tree rejection of the pull-request-only action, a missing and a logged-out `gh`, a refused pull request that keeps the commit and shows no provider output, a failed push that skips the pull request, and an already-open pull request reported as a skip — all against real temporary repositories, a real bare remote, and a `gh` substituted at the process-spawn boundary. `npm run contract:check` seals the schema.
- Registry entry, if this is genuinely non-CRUD: `POST /api/worktrees/changes/commit-push-pr` and `POST /api/worktrees/changes/pull-request` in `worktracker.registry.HOST_ROUTES`.
