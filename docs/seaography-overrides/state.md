## State writes

- Generated capability attempted: Seaography create-one, create-batch, update, and delete for `worktracker_state`.
- Exact missing behavior: create locks one Project before choosing a unique palette color and the next order. Update writes one concrete State and its durable status fact together. Delete locks the Project and rejects protected, last-in-group, occupied, or workflow-referenced rows. Reorder validates and replaces the complete project-owned order.
- Why `.graphql` selection/alias/adapter is insufficient: a caller document cannot bind generated update and delete filters to one required identity, lock a Project, inspect sibling colors and order, validate delete references, or make row changes and status facts one transaction.
- Why `ColumnOptions`, skips, guards, or `entity_filter` are insufficient: those controls restrict fields and rows. They do not provide cross-row locking, complete-set validation, ordered cleanup checks, or transactional outbox writes.
- Why a database constraint/default and SeaORM lifecycle hooks are insufficient: constraints protect simple row facts but cannot allocate a palette color from the current project catalogue, enforce the last-state-in-group rule, check all workflow references, or append the caller's durable fact. Generated update and delete also bypass the required pre-save and delete lifecycle seams at the pinned versions.
- Create-one safety: unrestricted generated create is private because color and order depend on a locked project catalogue and the status fact must share the insert transaction.
- Create-batch safety: private because the public contract has no batch caller and batch-wide color and order allocation is not defined.
- Update safety: unrestricted generated update is private because its optional filter can update many rows and cannot append each authoritative status fact in the same transaction.
- Delete safety: unrestricted generated delete is private because it can delete many rows and skips the protection, group, occupancy, workflow-reference, and fact rules.
- Smallest custom seam: restricted `create_state`, `update_state`, and `delete_state` model views plus the registered `reorder_states` domain operation. Their GraphQL names, arguments, and return types are unchanged.
- SeaORM transaction/domain module used: `catalog::prepare_state_create`, `catalog::prepare_state_update`, `catalog::prepare_state_reorder`, and `state_configuration::prepare_state_delete` prepare SeaORM models and append status facts through the caller's transaction. Seaolim owns persistence, commit, rollback, and ordered results.
- Protected fields excluded: callers cannot set `id`, `project_id` after create, `is_protected`, `created_at`, or `updated_at`. Create allocates identity, protection, order, and timestamps. Update exposes only `name`, `group`, `color`, and the existing compatibility `sort_order` field.
- Identity/scope binding: create requires one `project_id`; update requires one `id`; delete requires one `state_id`; reorder requires one `project_id` and the exact owned State identity set.
- Drift/regression test: State view tests pin all four SDL fields, exercise color and order allocation, protected deletion, cleanup, returned reorder order, durable facts, and rollback of every row and fact after a late persistence failure.
- Registry entry, if this is genuinely non-CRUD: `reorder_states` remains in the Work Management operation registry because complete ordering is not model CRUD. Create, update, and delete are model-shaped and need no registry entry.
