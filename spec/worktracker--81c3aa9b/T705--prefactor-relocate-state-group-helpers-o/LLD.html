Problem & solution

#704 adds signals.py receivers that resolve a state's group (and whether it is "resolved"). They are wired from WorktrackerConfig.ready() at app-init. The only place that logic lives today is api.py.
PROBLEM

The group vocabulary is trapped behind the Ninja router

_state_group() and _RESOLVED_GROUPS sit in api.py, the module that also constructs router = Router(...) and imports every schema and route.

For #704 to reuse them, signals.py — imported from AppConfig.ready() — would have to import from api.py, dragging the entire API surface into app-initialization. That is both wasteful and a circular-import hazard (api already imports models; init-time edges between api and signal wiring invite cycles).

SOLUTION

Lift the ~12 lines into a dedicated state_groups.py

Create a small single-purpose module beside models.py — matching the repo's existing ranking.py / sequences.py / seed.py convention — that holds RESOLVED_GROUPS and state_group() and imports only State from models. No Ninja router anywhere in its import graph.

api.py stops defining them and imports them from state_groups instead — its two call sites are otherwise untouched. signals.py (#704) then imports the same names from state_groups with no router pull. One definition, one home, no duplication.

Decisions

The ticket offers two candidate homes ("alongside State in models.py, or a small dedicated groups module"). These resolve that and the surrounding fine print.
D1 · HOME

A dedicated state_groups.py, not models.py

The package already keeps single-purpose helpers in their own small modules — ranking.py, sequences.py, seed.py. A state_groups.py beside them is the idiomatic home: it names exactly what it holds, keeps models.py to model definitions, and gives both api.py and the future signals.py a self-documenting import target.

Rejected: folding into models.py. It would grow the model module with a query helper and the RESOLVED_GROUPS derivation, blurring "what the tables are" with "how groups are interpreted".

D2 · NAMES

Promote to public state_group / RESOLVED_GROUPS

The symbols are now a deliberate cross-module export consumed by api.py and signals.py. Dropping the leading underscore signals that intent; importing an underscore-private name across modules reads as a smell. The rename is mechanical and applied at the two existing call sites in the same change.

Not done: keeping _state_group / _RESOLVED_GROUPS. Lower diff, but it leaves a "private" name being imported by two siblings — exactly the confusion the relocation is meant to remove.

D3 · NO SHIM

api.py imports — it does not re-export

Delete both definitions from api.py and add from worktracker.state_groups import RESOLVED_GROUPS, state_group. No backward-compat alias is left behind, satisfying "no duplicated definitions remain". The two call sites switch to the public names only.

D4 · BEHAVIOR FROZEN

The fresh-read query stays in state_group

state_group deliberately re-reads State from the table (not via issue.state) so patch_work_item's post-reassignment lookup can't return a stale cached FK. That behavior is load-bearing for the #633 transition and is preserved unchanged — this is a move + rename, not a rewrite.

Behavior invariants — what must stay byte-identical

A prefactor earns its keep only if nothing observable moves. These are the exact things the change must not perturb.
  • Scope-context (GET /work-items/{id}/scope-context) returns the same state_group and resolved for every neighbor — _scope_ref still tests group in RESOLVED_GROUPS.
  • The #633 transition in patch_work_item behaves identically: active→cancelled archives + cascades, cancelled→active restores self only, same-group is a no-op — new_group = state_group(issue.state_id) still resolves from a fresh row read.
  • The group vocabulary is unchanged: backlog / unstarted / started / completed / cancelled, with {completed, cancelled} the resolved subset, still mirroring the FE RESOLVED_GROUPS.
  • No migration, no schema change, no API signature change, no new dependency.
  • import worktracker.state_groups pulls no Ninja router (the property #704 depends on).

Build steps

Decision-complete and ordered. No code blocks by design — each step names the exact edit.
  1. state_groups.py — Create the module. Add the module docstring, from worktracker.models import State, then RESOLVED_GROUPS (with its scope-context / FE-mirror comment) and state_group(state_id) (with its fresh-read docstring), bodies lifted verbatim and renamed to public.
  2. api.py — Delete the _RESOLVED_GROUPS constant (and its comment) and the _state_group function (and its docstring).
  3. api.py — Add from worktracker.state_groups import RESOLVED_GROUPS, state_group near the existing intra-package imports. If State is now used nowhere else in api.py, leave its models import as-is only if still referenced (it is — state CRUD routes use it).
  4. api.py — Update the two call sites to the public names: group in RESOLVED_GROUPS in _scope_ref, and new_group = state_group(issue.state_id) in patch_work_item. Leave the old_group = issue.state.group line untouched.
  5. Confirm neutrality & no leftovers — grep api.py shows no def state_group / RESOLVED_GROUPS =; the names appear only as the import and two call sites.
  6. Run the backend suite — full pytest green, with attention to test_scope_context.py (resolved) and the #633 cancel-archive tests; no test edits expected.
