# Agent launch

Start a task agent, a taskless planning agent or an instant conversation through the configured launch policy, a provider picker, or a supplied first message.
Surfaces: browser, desktop
Editions: pocock, core

## Sub-features

- agent-launch-run-item: Current-stage Run item and the normal-run command use backend launch defaults.
- agent-launch-run-now: Eligible Ideas Stories convert to Implementation in Implement before launching.
- agent-launch-open-agent: Open a task agent through the shared activated-provider picker.
- agent-launch-open-with-prompt: Collect task-bound free text before provider choice.
- agent-launch-plan: Use the global Plan shortcut for a module-scoped, taskless planning prompt and provider choice, independently of the sprint Plan workspace.
- agent-launch-instant-default: Start an instant conversation immediately with the configured default agent.
- agent-launch-instant-prompt: Open the inline composer to supply the first message and optionally choose a provider.
- agent-launch-picker: Browse activated providers, select by mouse or keyboard, or cancel.
- agent-launch-prompt-input: Submit a multiline prompt or dismiss the prompt dialog.
- agent-launch-workflow-defaults: Resolve task provider, model, reasoning, profile, prompt and skills from persisted launch policy.
- agent-launch-stage-skill-warning: Warn on missing or unchecked stage skills using the resolved provider's actual launch checkout, while allowing launch.

## How to get to it

- Select a work item and open Details. The button named `Run item` invokes its current-stage launch; `normal-run-command` defaults to Cmd+Enter. A branch can route that same command to Run subtree; see [dependency-graph runs](dependency-graph-runs.md).
- An eligible leaf Story in Ideas offers `Run now`; `run-now` defaults to R.
- `open-agent` defaults to O and opens `Select Agent` for the selected task. The task workspace's `＋ Agent` button opens the same picker with captured task context.
- `open-with-prompt` defaults to Shift+Enter; `open-with-prompt-command` defaults to Cmd+Shift+Enter. Both open `Prompt`, then `Select Agent`. A missing module-folder link first opens the folder gate.
- `plan` defaults to N. With a selected project and module, it calls `startPlanFlow`: missing folder → `Module Folder` → `Prompt` → `Select Agent`, or directly `Prompt` → `Select Agent` when a folder is linked. This is the global agent-planning action, separate from the core-edition [sprint Plan workspace](plan-workspace-navigation.md).
- Under Conversations, click the `New conversation` treeitem, or use `instant-change` (Cmd+I, with bare I as a default alias). Click `Start a conversation with a prompt`, or use `instant-change-with-prompt` (Cmd+Shift+I), to open the inline composer. See [conversations](conversations.md) for its continued interaction.
- In `Select Agent`, `modal.previous` / `modal.next` default to ArrowUp / ArrowDown; `modal.confirm` defaults to Enter. In `Prompt`, `modal.submit` defaults to Ctrl+Enter with Cmd+Enter as a default alias; ordinary Enter inserts a newline. `modal.close` defaults to Escape; the dialog's `Close dialog` button also dismisses it.

## Prerequisites

- Select a project and module; task-bound picker paths require a real persisted task, not the synthetic conversation workspace. Run item is shown only with module context, a state, and a configured launch-binding state for its issue type.
- N-key Plan requires a selected project and module, but no selected work item or sprint and no core-edition build. With either identity missing, no flow opens. It uses the linked module folder and an explicitly chosen activated provider; it does not skip the picker for a remembered default. Modal/typing shortcut gates still apply.
- Run now requires a Story in Ideas, no children, and an Ideas-to-Implement workflow transition. Rust additionally preflights the module folder and destination Implementation type/binding; visible eligibility does not guarantee launch readiness.
- Link a writable module folder and satisfy provider/worktree trust where required; see [module folders and trust](module-folders-and-trust.md). Provider execution needs an activated, discoverable real or disposable provider and tmux. The picker reads activation from host capabilities.
- Default instant launches need a configured global launch default. Provider overrides in the inline composer must also be activated. Use the isolated profiles and disposable-provider baseline from the [index](README.md).

## Expected behavior

- Run item launches with backend-resolved policy and does not itself choose a new workflow stage. It guards duplicate clicks while pending, marks `aria-busy`, observes the new task run tab, and acknowledges it only after launch returns. A refusal cancels the tab watch, refreshes capabilities and reports `Agent run could not be started`.
- Run now guards repeated requests, converts the same Story identity to Implementation in Implement, and selects the acknowledged run. Refusal reports `Run now could not be started`; an error can carry an already committed conversion, which the UI preserves and explains rather than pretending the Story stayed in Ideas. A Story with any child has no Run now action.
- The picker displays only activated `claude`, `agy`, `codex` and `gemini` choices. Loading, failed and empty provider-list messages replace absent provider rows. Some workspace callers also offer `Terminal`, which opens a plain module shell rather than an agent. Escape cancels without creating a run and returns focus to the launcher.
- An explicit picker (open-agent, open-with-prompt, plan, instant) launch opens a placeholder terminal tab before the run is created. If creation is refused, the placeholder is closed rather than left as a blank selected terminal, and the translated refusal appears as a dismissible error toast; selecting a provider again retries (CODING-2763).
- Open-agent and open-with-prompt capture the task context before the modal chain, so a later selection change does not silently retarget that launch. Free text is carried to the picker and then submitted as user input. Cancel before provider commitment does not launch. The generic Prompt dialog permits empty text unless its caller sets `requireText`; this task flow does not set it.
- N-key Plan captures project/module identity for the modal chain. Saving the folder gate resumes at Prompt; invalid folder input or save failure keeps the gate open with feedback. Dismissing the folder, Prompt or picker before choosing a provider creates no planning session (a saved folder link remains). Prompt carries the entered text unchanged, including blank text, because this caller does not set `requireText`. Provider choice calls `launchScratchPlanning` with `taskId: null` and `isPlanning: true`, without a parent or workflow-state change. The picker requests the module scratch bucket's terminal surface, selects the local synthetic workspace and closes; those local selection effects do not prove a visible terminal or provider execution. If durable creation is reached, the transport submits kind `planning` with the module target and working-directory identity. A refused create removes the placeholder and shows `Conversation did not start: <reason>` through the shared creation seam. Empty/failed activation uses the shared picker messages; the N flow offers no plain `Terminal` choice.
- Promptless instant change sends neither provider nor first-message overrides. After success it selects one conversation's exact terminal in the module workspace. The prompt path disables `Start` for blank text, trims the message, submits with Ctrl/Cmd+Enter or `Start`, and allows a provider override. Escape closes the composer while retaining its draft. A missing folder gates launch; launch failure surfaces `Conversation did not start`.
- Task launch policy selects the current type/state binding, requires its prompt, and resolves provider/model/reasoning/profile and skills on the backend. Missing compatible configuration or provider activation is a refusal. Global defaults fill unresolved selections; a profile owns its model/reasoning. Picker provider overrides are validated and drop incompatible binding model/reasoning/profile. Instant launch uses conversation starter settings plus optional first-message text, rather than a task's workflow binding.
- Durable run and terminal records support restoration after reload; the desktop harness proves that round-trip for Run item. Conversation restoration and run status are detailed in [conversations](conversations.md) and [agent lifecycle and status](agent-lifecycle-and-status.md).
- Fresh task launches and handoffs check stage skills with the same read-only checker used by workflow configuration, against the resolved provider and actual working directory (including a selected worktree). Missing names and provider read failures produce a persistent run warning, not a launch refusal. The terminal surface shows every missing/unchecked name and provider after acknowledgement and when revisiting the run. A new run checks again after installation; the historical run keeps its warning. Warning text does not enter PTY output or provider arguments. Existing stage-skill prompt text and pinned required-skill refusal remain unchanged.
- A run read started before a newer handoff observation preserves the newer report when it completes, including a successful check that clears the warning. The banner and live run holding share that observation through Apollo's normalized run entity; delayed null or non-null reads cannot undo it.
- If background recovery already owns a launch effect, the requesting launch waits for that same effect to settle and acknowledges its durable session. It does not create a second terminal or report lease contention as launch refusal.

## Gotchas

- Browser worktree creation succeeds, but Codex task launch from its untrusted checkout refuses `worktree_trust_approval_required: Approve codex trust for <checkout> in Worktree details, then retry.` The browser runtime has no `prepareDirectoryTrust`; its Worktree details expose no approval action. The suite proves the refusal and no persisted terminal, and proves missing/install/new-run warning behavior against the actual module checkout. Approval and warning success from a selected worktree require the desktop trust surface; no provider trust state is manufactured for browser tests.

- Browser controls and fixture tests can establish GraphQL requests, guards and feedback. The cited browser cases cannot prove native libghostty rendering, native terminal retention or real/disposable-provider launch. Native execution proof requires the desktop build and a provider executable; the disposable harness supplies one. The current Rust browser adapter configures the same terminal launch runtime authority (`studio/src-tauri/crates/app/ticketry-dev-tools/src/bin/ticketry_graphql_adapter.rs`), so historical blanket browser-launch refusal wording is stale; the feature suite now proves disposable-provider success through this adapter for task, Run now and instant launches. No paid-provider success is claimed.
- Source-only surface distinction: desktop Run item uses launch delivery with the binding's workflow prompt. The browser default path uses `terminal_session_create` with kind `task`; interactive task material in `LaunchAuthorityService::task` omits the workflow prompt, while kind `automation` includes it. Picker task launches also use factual ticket context plus supplied user input. Do not infer prompt parity from a successful UI test.
- Global launch shortcuts are suppressed while a modal is open or an editable target is typing; modal navigation and composer submission own their input. Chords are defaults and can be reconfigured. The generic modal textarea has no label/test ID; do not invent one.
- N-key Plan is independent of sprint planning and its edition build gate. Its frontend carries the entered prompt to the planning transport, but `studio/src-tauri/crates/execution/ticketry-launch/src/authority/service.rs` rebuilds planning material without using `request.prompt`; prompt carry-through to the picker is not proof of provider prompt delivery. The synthetic scratch selection and connecting session are local intent, not proof of terminal visibility or a durable run.
- A Run item binding projection or visible activated provider does not prove an executable is installed, a directory is trusted, or prompt delivery will succeed. Keep launch refusal distinct from an acknowledged run and wait for its durable identity before attaching.
- The context map's older concrete module links predate the crate layout; its Agent Execution ownership description has no standalone Agent Execution CONTEXT link. The existing graph-run context is the linked execution glossary; current source/test paths above establish behavior. The desktop harness README's browser-unavailable statement is a proof limit, not a promise that every browser adapter rejects every request before reaching Rust.
