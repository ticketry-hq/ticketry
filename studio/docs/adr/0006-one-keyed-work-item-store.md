# One keyed work-item store replaces per-feature record copies

Work-item records lived in four stores across two feature lineages: `tasksStore` held a lossy `TaskSummary` from the module load plus a second copy in `details`, while `issueStore`, `backlogStore`, and `drawerWorkspaceStore` held the faithful `WorkItem`. A selected task therefore existed three or four times in two incompatible shapes, was fetched from `GET /work-items/{id}` twice on every selection, and was mutable through two independent code paths for state and parent — so each mutation site updated a different arbitrary subset of the copies and the status feed reconciled only two of the four (T82). The visible symptom was the detail panel blanking to "Loading issue…" on every selection: the module list already returns every descendant as a complete `WorkItemOut`, but `normalizeTask` discarded `blocked_by_ids`, `blocks_ids`, `lifecycle_state`, `lifecycle_transitions`, `is_archived`, and `created_at`, leaving the client unable to render from data it already held. We make `issueStore` the single owner, keyed by id, with the other three stores holding only IDs, and delete `TaskSummary` along with its fabricated `{name: "No state"}` so `state: null` is carried honestly. The revision guards move to where the records now live, because a guard in a different store from the data it protects is only half installed. We chose a hand-rolled keyed store over adopting TanStack Query, which we considered and deferred: a query cache keyed by id would have given dedupe, staleness, and prefetch for free but would not have normalized — a list query and a detail query still hold separate copies — so the disagreement bug class this ADR exists to kill would have survived. Retention, staleness policy, prefetch, and eviction are deliberately absent here and remain available to a later library adoption on top of this shape.
