Key finding — the one real blocker. WorkItemPatch already accepts sprint_id (schemas.py:193), so you can assign a sprint today — but WorkItemOut (schemas.py:53–92) does not return it. You can set a sprint and never read it back. Exposing sprint_id on WorkItemOut is the hard precondition for any per-task display and for #603.

Decision

Lead with the cheapest things that unblock everything, then the highest-value human surface.

DO NOW · STOP-GAP

Register Sprint in admin + expose sprint_id

Two tiny, zero-risk changes worth doing immediately regardless of the larger plan. SprintAdmin (~8 lines, mirrors existing classes) gives eyes-on today. Adding sprint_id to WorkItemOut removes the one blocker for all per-task display and for #603.

FIRST PRODUCT BUILD

Sprint field in DetailsTab

The natural home: a task's sprint is a property, so it slots after the Parent section, before WorktreeBlock. Reuses the proven Status/Parent pattern — label + button → cursor picker → PATCH /work-items/{id}.

This single field is both the first display surface and the assign / move / clear affordance. (See subtask "Display current sprint in the Details tab".)

NEXT

Lightweight sprint list / detail

Once the data flow is proven on the field, a simple per-project sprint list + single-sprint detail (progress already derived in GET /sprints/{id}, its tasks via /sprints/{id}/work-items) is the better second step than jumping to the full grid.

LATER

Planning map (#603) feeds from this

The modules × sprints story map is the aggregate planning view. It is more build and is complementary — not the right first view. This spike precedes and unblocks it.
