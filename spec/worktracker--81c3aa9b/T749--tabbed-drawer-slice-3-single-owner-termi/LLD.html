Why registry alone is insufficient

The registry only decides which surface is visible. If /coding and the drawer each kept their own entry map (as TerminalHost.entriesRef does today), an ownership transfer would spawn a second Terminal and a second WebSocket for the same run — breaking the no-duplicate criterion. Single-owner therefore needs both pieces.

Shared entry pool (mechanism)

  • The Terminal/WS pair for a session exists exactly once, independent of how many surfaces reference it.
  • ensureConnected is idempotent — a second call while a handle exists is a no-op, so a second WS viewer is impossible.
  • Scrollback lives in the Terminal's in-memory buffer, not the DOM node it is open()-ed into — so reparenting the one instance preserves it.

Registry (policy)

  • Exactly one surface attaches the shared entry's DOM at a time, chosen by per-session claim.
  • Drawer claim wins; unclaimed keys resolve to /coding with no write.
  • Releasing a claim returns eligibility to /coding without touching the pool entry or the backend run.

Identity and key model

Both consumers must agree on one key per live run so a claim survives the temp→server rekey.

Foreground key

  • foregroundKey(meta) = meta.agentRunId ?? meta.sessionId.
  • Durable run id when known; live session id before ready.
  • Drawer derives the same key from the CODIN-748 seam's persisted agent_run_id.

Single migration point

  • Key migrates once at tmp_* → serverId + agentRunId in terminalStore.setReady.
  • Registry rekey(old,new) is fired there — a claim placed pre-ready survives without a coding-flicker window.

Doc-chat sessions

  • Participate in the pool like any session.
  • Drawer never claims their keys this slice, so they always resolve to coding (Decision 3).

Registry API — stores/terminalForegroundStore.ts (NEW)

A small, session-agnostic Zustand store: it holds claims and host targets, never session metadata. The third "backgrounded" state is a null resolution (no live session for a key), not a stored value.

State

  • claims: key → owner. Only non-default (drawer) claims are recorded; coding is the implicit fallback.
  • hostTargets: owner → mount-target HTMLElement | null. /coding registers here now; drawer in CODIN-751.
  • Vocabulary: ForegroundOwner = 'coding' | 'drawer'.

Actions (the adapter API)

  • acquire(key, owner) — record a claim; drawer overrides the coding default.
  • release(key) — drop one claim; key reverts to coding-eligible.
  • releaseOwner(owner) — drop every claim an owner holds (drawer close / issue switch).
  • rekey(oldKey, newKey) — move a claim across the identity migration.
  • registerHost / unregisterHost(owner, el) — publish/retract a mount target.

Selectors (pure, exported)

  • resolveOwner(state, key) → claims[key] ?? 'coding' — the one source of truth for "who owns this key".
  • isCodingEligible(state, meta) → resolveOwner(state, foregroundKey(meta)) === 'coding' — the boolean TerminalHost gates on.

Per-session, not global

  • A drawer claim on session X leaves session Y coding-eligible.
  • Distinct sessions can have distinct active owners at once (Decision 2).

Owner resolution states

Per session key, the resolved owner drives whether each surface attaches DOM.

coding (default)

No claim recorded. /coding attaches the pooled Terminal; drawer (when it exists) shows inactive for this key.

drawer

Drawer claim present. Drawer attaches; /coding renders its inactive/empty box and holds the entry, tab, and history.

null / backgrounded

No live session for the key. Nobody attaches; not a stored value — absence in sessions.

Acceptance signal

Ready for implementation when: a live session has exactly one foreground xterm DOM owner across /coding and drawer consumers; drawer wins while it foregrounds a session; the matching /coding presentation goes inactive rather than duplicating; ownership transfer preserves session identity and scrollback with no second Terminal/WS/backend session; release on close/tab-switch/issue-switch/exit returns /coding eligibility without killing the run; and focused tests prove no duplicate xterm/WebSocket viewer for the same live session.
