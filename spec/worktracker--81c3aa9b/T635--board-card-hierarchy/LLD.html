Board Card Hierarchy — Low-Level Design

Decision-complete implementation harness for #635. Give sub-task cards a token-coloured left accent bar + one indent and a ↳ immediate-parent chip; give any card with children a count badge — on both the flat board and the #632 epic swimlanes. The whole change is one shared classifier in the board selectors plus a presentational branch in one card component. Item arrays stay untouched, so drag/drop, #626 reorder, selection, keyboard and click-to-open are byte-for-byte unchanged. Zero backend/SDK.

Build order

Five steps, selectors-first so the card branch consumes a typed annotation that is already tested. Each step is independently green.
STEP 1
Shared classifier In backlogSelectors.ts, add the exported CardHierarchy type, the pure cardHierarchy() helper, and buildCardMeta(). Replace the two inline isSubtask locals with the helper.
STEP 2
Selector output Extend boardColumns (per-column cardMeta) and boardSwimlanes (one top-level cardMeta) to carry the annotation map. Item arrays + rank sort unchanged.
STEP 3
Card branch + seam In BoardCard.tsx, add isSubtask/parentKey props, the accent seam, the indent + bar, the ↳ parent chip, and the count badge.
STEP 4
Thread the props BoardColumn reads cardMeta[item.id]; BoardSwimlane forwards the shared map; BoardView passes it from both selectors.
STEP 5
Tests + green Selector-annotation tests + render/regression tests. Then typecheck, test, build.

Locked decisions

Everything below is settled — no open question gates implementation.
D1 · CLASSIFICATION

One shared sub-task predicate

A card is a sub-task when parent_id !== null and the parent id is present in the work-item map. The map is built only from work items, so a Module parent is absent (→ top-level story) and a dangling parent is absent (→ top-level, mirroring the No-Epic promotion). The single membership check covers both exclusions. Promoted from the existing inline locals to one exported helper so the hide-toggle filter and the annotation can never diverge.

D2 · TRANSPORT

Side map, never a card wrapper

Per-card metadata travels as a Record<id, CardHierarchy> keyed by item id. The ordered WorkItem[] arrays the columns/cells render — and that reorderNeighbors() consumes — are left exactly as today. No typed per-card wrapper; nothing in the DnD path changes.

D3 · ACCENT SEAM

One isolated colour function

The left-bar colour comes from a single presentation function that takes the card's CardHierarchy and returns a Tailwind border-colour class. Today it returns one fixed token for every sub-task. A later connected/per-parent accent is a body-only change to this function — classification, selector data, selector contracts and card layout are untouched.

D4 · BINARY

One bar, one indent — any depth

Sub-task treatment is binary. A nested sub-task gets the same single bar + single indent as a first-level one. No depth-scaled indentation, no card reordering, no bucketing change.

D5 · BADGE

Count badge is toggle-independent

The child-count badge renders whenever sub_issues_count > 0 — regardless of the Show-sub-tasks toggle and regardless of whether the card is itself a sub-task. So a nested sub-task shows both its parent chip and its own badge.

DEFAULT · TOKEN

Which token today

The bar defaults to lifecycle-active (cyan) — an existing theme token visually distinct from the blue focus-accent selection ring. The exact token is immaterial to the contract since it lives behind the D3 seam; any single existing token is acceptable.

Acceptance signal

Done when, on both board layouts, a sub-task card is immediately distinguishable — one token-coloured left accent bar + one indent, plus a ↳ immediate-parent-key chip — while every card with children shows a count badge, visible even with sub-tasks hidden, and a nested sub-task shows both. The distinction stays binary; the accent lives behind an isolated seam for a later connected treatment; drag, #626 reorder, selection, keyboard activation and click-to-open are unchanged; flat board and swimlanes behave identically; and it ships with zero backend / API / SDK change. Typecheck, the relevant Vitest suites, and the production build are green.
