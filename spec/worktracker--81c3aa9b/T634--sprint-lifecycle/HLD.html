Sprint Lifecycle — Jira-style naming, goal, start & complete-with-carryover

Sprints already have a model, CRUD, a single-active guard, and a Now/Later/History lens. What's missing is the lifecycle Jira gives you: sprints that auto-name themselves, a goal and a duration, an explicit Start step, and a Complete step that decides where unfinished work goes. This design adds exactly those four, on top of the surfaces that already ship — no new view, no story points.

The four gaps, as build pillars

Click a pillar to expand its boundary. ✓ exists   + new   ◌ out of scope
PILLAR 1 · NAME-001 / GOAL-001

Auto-naming & goal

Sprints name themselves Sprint 1, Sprint 2… and carry an optional one-line goal.

  • New Project.sprint_seq counter — monotonic, never reused after delete (Jira parity)
  • create_sprint mints Sprint {seq} when name is blank; user can still type / rename freely
  • New Sprint.goal TextField (blank default) on model, SprintOut/In/Patch, and SDK
  • Rename / recolor / re-date already work via existing PATCH /sprints/{id}
PILLAR 2 · START-001 / INV-001

Explicit Start operation

Starting becomes a deliberate step with a duration and goal — not a silent status edit.

  • New POST /sprints/{id}/start — sets status=active, start_date, derives end_date from a duration (default 2 weeks)
  • Start dialog: prefilled name, goal, duration picker (1/2/3/4 wk or explicit dates)
  • Single-active guard reused — Start returns 409 if another sprint is active
  • Sprint capacity / velocity / story points — stays deferred (#602)
PILLAR 3 · COMPLETE-001 · the heart

Complete with carryover

Completing a sprint decides the fate of unfinished work, atomically — the piece #604 deferred.

  • New POST /sprints/{id}/complete body {carryover, target_sprint_id?}
  • Freezes done items, moves the rest to Backlog (sprint_id=NULL) or a chosen sprint, in one transaction
  • Complete dialog shows the done/incomplete split + the carryover choice before confirming
  • Cross-project carryover, partial carryover (per-item) — out of scope

Complete-with-carryover — the sequence

The one genuinely new behavior. Click a step for its mechanics and edge cases. Everything happens in a single server transaction so a half-moved sprint can never be observed.
STEP 1 · CLIENT

Open the Complete dialog

From the Now tab, "Complete sprint" opens a dialog that reads the current split: X done (state group completed/cancelled) vs Y unfinished, computed by the existing sprintProgress().

Edge: Y = 0 → dialog still opens but skips the carryover picker (nothing to move); confirm just closes the sprint.
STEP 2 · CLIENT

Choose where unfinished work goes

One choice: move the Y unfinished issues to Backlog (sprint_id = NULL) or to an existing planned sprint (dropdown of this project's planned sprints). A "+ new sprint" shortcut creates one inline to receive them.

Edge: no planned sprint exists yet → only Backlog + "new sprint" are offered; the active sprint being completed is never a target.
STEP 3 · SERVER

POST /sprints/{id}/complete

Body {carryover: "backlog" | "sprint", target_sprint_id?}. In one transaction.atomic(): set status=completed; re-point every unfinished member's sprint_id to the target (or NULL); leave done/cancelled members on the now-completed sprint as the historical record.

Edge: target_sprint_id is missing/completed/another project → 422, whole transaction rolls back. Completing an already-completed sprint → 409.
STEP 4 · CLIENT

Optimistic apply + reconcile

The store moves the cards optimistically (same pattern as moveItemToSprint), flips the sprint to History, and surfaces the moved-count. On a non-2xx it rolls every card back to its prior sprint and shows the error — no partial board.

Edge: a concurrent edit changed an item's state mid-flight → server is source of truth; reconcile on the response, never trust the optimistic copy.

Decisions & open questions

Green = decided in this HLD. Red = genuinely open; neither gates the build.
DECIDED · scope consolidation

Where does close-as-advance live?

Here. #604 designed but deferred "close-as-advance"; this story absorbs it as COMPLETE-001. #604 is marked superseded so carryover isn't split across two tickets.

DECIDED · counter

How is "never reused" guaranteed?

A persistent Project.sprint_seq, incremented on create — not max(existing)+1. Deleting the highest sprint does not free its number, matching Jira's board counter.

DECIDED · operations vs PATCH

New routes, or overload PATCH?

Dedicated /start and /complete routes. PATCH stays for plain edits (rename, re-date). Carryover and duration-math are operations with side effects, not field writes.

DECIDED · done definition

What counts as "finished" at complete?

State group completed or cancelled — the same definition sprintProgress() already uses. Everything else is "unfinished" and subject to carryover.

OPEN · low-pressure

Auto-name format configurable?

Defer. Ship the literal Sprint N. A per-project name template (e.g. Iteration N) can come later without schema change.

OPEN · low-pressure

Server-side progress envelope?

Defer. SDK already declares SprintProgress/SprintDetail but the API doesn't return them; progress stays client-computed. Wire it only if a non-Studio consumer needs it.

Acceptance signal

The story is done when, in Studio: clicking Create sprint offers a sprint pre-named Sprint N (N from a per-project counter that never reuses a deleted number) with an optional goal; Start opens a dialog with a goal and a duration that defaults to two weeks, sets the sprint active and stamps start_date/end_date, and is refused with a clear message if another sprint is already active; and Complete opens a dialog showing the done/unfinished split and a single choice — move unfinished work to Backlog or to a chosen sprint — that on confirm closes the sprint and re-points exactly the unfinished items in one transaction, rolling back cleanly on any error. Backend, SDK, and Studio test suites are green; no story points, velocity, or burndown are introduced.
