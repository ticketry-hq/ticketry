Call flow — one "Execute graph" invocation

Identical whether triggered by the MCP tool or the UI button. The graph drains off issue_state_changed completions after the initial launch — no polling loop in the driver.

  1. Trigger. MCP execute_dependency_graph(root) or the Dependency-view button POSTs /work-items/{root}/execute-graph {agent:"codex"}.
  2. Build + seed. driver.execute_graph BFS-walks the root's task subtree, builds GraphState from blocked_by edges, and seeds each node from durable facts (completed group → done; live AgentRun → adopted running; else idle).
  3. Launch ready-set. decide_graph(execute_requested) returns the launch actions for idle nodes whose blockers are all done; the driver calls spawn_run for each (codex, scope="task").
  4. Respond. 201 GraphOut{root_id, nodes:[{task_id, status, agent_run_id, error}]}. Idempotent — a re-invoke re-seeds and launches only genuinely-new work (no 409).
  5. Drain. As each run finishes, the issue_state_changed receiver feeds the seam event through decide_graph, releasing newly-unblocked nodes. A failure flips the node failed and transitively halteds its dependents; independent branches keep draining.
  6. Reflect. The Dependency view merges GET /runs/lifecycle-states (live badge) with GET execute-graph (engine idle/running/done/failed/halted); 404 → badge-only.
