Backlog Inline-Create Row & Keyboard Navigation — High-Level Design

Today the only way to create an issue is the modal or a per-epic "Add story" link, and the backlog list cannot be driven from the keyboard at all. This slice closes G12 with an always-present name-only inline-create row at the top of the backlog (Enter creates, clears, and keeps focus — Jira's rapid-entry behavior) and G13 with a read-only j/k/arrow cursor that walks the visible rows and opens the highlighted issue on Enter. Pure frontend, zero backend, zero migration — it reuses createIssue and the existing /issues/:key drawer.

TODAY'S BACKLOG
Creating an issue means opening the CreateIssue modal or clicking a per-epic "Add story" link (BacklogList.tsx:314) — both route through the modal. There is no quick path to type a name and keep going. And the list is mouse-only: there is no keyboard cursor, so you cannot move down the tree or open an issue without clicking. The Epic rail (#627) already multi-selects into filters.epicIds[], but nothing uses it to seed a quick create.
⟶
THIS DESIGN
A single inline-create row pinned to the top of the list: type a name, press Enter → createIssue appends it optimistically, the input clears and keeps focus for the next one. When exactly one real epic is selected in the rail, the new issue is parented to it so it lands in the visible group; otherwise it's top-level ("No Epic"). Separately, j/k/↑/↓ move a read-only cursor over the visible rows; Enter opens the cursor's issue in the drawer. The modal stays for richer creates; multi-select stays with C2 (#637).

PILLAR 1 · G12

Always-on inline create

A name-only text input pinned above the first epic group; Enter creates, clears, and keeps focus.

  • Single controlled input rendered before the first group in BacklogList
  • backlogStore.createIssue(projectId, {name, parent_id}) — existing, optimistic append, returns WorkItem | null
  • Enter → create with priority defaulting to none, then clear value, refocus; Esc blurs
  • Whitespace-only name is disabled / no-op; errors ride createIssue's existing error path
  • The CreateIssue modal stays for priority/parent pickers — the row never duplicates them
PILLAR 2 · G13

Read-only keyboard cursor

A single highlighted row that j/k/arrows move over the visible tree; Enter opens it.

  • Cursor walks a flattened list of visible rows — respects collapsed epics & collapsed parents
  • Visible set derived from the same groupBacklog() output + the collapsedEpics/collapsedRows sets BacklogList already keeps
  • Enter reuses the row's onOpen → navigate(`/issues/${key}`) → drawer
  • Active row gets a visible highlight and scrollIntoView as it moves; index clamps at both ends
  • Guarded by the same isTypingTarget rule as useCodingAppShortcut; skips when a modifier is held
PILLAR 3 · blast radius

Additive & composable

Frontend-only, no store shape change required, and the cursor is built to compose with C2 selection later.

  • No backend, no SDK, no migration — reuses existing read/create paths only
  • Rail-aware parent reads filters.epicIds (#627) — single real epic = length === 1 && [0] !== NO_EPIC
  • Cursor is read-only: no Space/Shift-range, no checkbox, no bulk bar — that stays with C2 #637
  • Lands in the shared multi-agent Studio tree alongside C1/C2/C4; keep edits to BacklogList + one hook

Decision board

Green = resolved in the refined requirements. Red = genuinely open, settled in LLD — none gates the shape.
RESOLVED · row scope

What's in the inline row?

Name only. A single text input — no inline priority/parent pickers. The CreateIssue modal stays as the path for richer creates, so the row never duplicates pickers.

RESOLVED · parenting

Where does a quick-created issue land?

Rail-aware. Exactly one real epic selected → seed it as parent_id so the issue shows in that group. Zero or many selected → top-level (null) into "No Epic". The NO_EPIC sentinel ("none") does not count as a real epic.

RESOLVED · cursor nature

Is the cursor selection?

No — read-only navigation. One highlighted row, no checkbox/Space/Shift-range/bulk bar. Multi-select & bulk are C2 #637; the two are designed to compose later.

RESOLVED · modal kept

Does this replace the modal or "Add story"?

No. The per-epic "Add story" link and the CreateIssue modal are unchanged. The inline row is an additive fast path at the top of the list.

OPEN · LLD Q1

Where does the visible-row flattening live?

C4 #639 (drawer prev/next) needs the same flattened-visible-order walk. Extract a shared helper (e.g. flattenVisible(groups, collapsed)) or keep it local to BacklogList for now? Recommendation: shared helper to avoid divergence. Decide in LLD / coordinate with #639.

OPEN · LLD Q2

Cursor lifecycle on reorder / reload / filter change

When the visible list changes under the cursor (a create appends, #626 reorder, an epic collapses, a filter applies), does the index clamp, reset to top, or track the same item by id? Recommendation: clamp to valid range, reset on project/filter change. LLD detail.

OPEN · LLD Q3

Cursor state location vs C2 composition

Keep the index as local useState in BacklogList, or lift to uiStore so C2 multi-select can build on it? Recommendation: local for now, with a clean shape that C2 can promote. LLD detail.
