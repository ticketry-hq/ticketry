Task-state-change event hook — the seam for graph execution

When an Issue's workflow state changes, emit a structured event on commit and dispatch it to a pluggable in-process signal. v1 registers exactly one receiver that logs the transition. The orchestration that later launches agent runs hangs off this seam — and is out of scope here.

Problem & solution

From the parent epic #700 ("execute a dependency graph"): something has to notice when a task is done so its dependents can be released. There is no signal for "a task changed state" today — every consumer would have to poll or wire into each write path by hand.
PROBLEM

State changes are invisible to the rest of the system

A task's workflow state is changed through several paths — the MCP update_task_status tool, the Studio PATCH, board drag-drop, bulk actions — and nothing downstream is told it happened.

The graph executor needs to react to one specific transition (a task entering the completed group) but there is no done lifecycle signal: the 9 run-lifecycle values (starting/working/needs_input/turn_complete/quiet/reconnecting/exited/error/unknown) never mean "task finished" — turn_complete fires every turn. The tracker Issue.state is the only unambiguous completion gate, and it has no event.

SOLUTION

One pluggable event the whole system can subscribe to

Add a broad-net post_save chokepoint on Issue that, when (and only when) state_id actually changes, sends a custom Django signal issue_state_changed carrying the resolved before/after state groups.

Dispatch fires on transaction.on_commit, so rolled-back writes never emit. Any number of receivers can connect(); v1 ships one that just logs. The orchestrator, verifications, and audit hang off the same seam later without touching the emit site.

When does it emit?

The signal fires on every state assignment, including creation — receivers self-filter. It stays silent only for true no-ops and non-state saves. The one state change that slips past the chokepoint is called out in red.

Implementation decisions

Click a pillar to expand its boundary. Three moving parts, all inside worktracker/worktracker/.
PILLAR 1 · CHOKEPOINT

post_save on Issue + pre_save snapshot

A broad-net post_save catches every issue.save() — current routes, raw ORM, future routes. pre_save snapshots the old state_id so from_group is recoverable.

  • Chosen over a per-route emit: all 4 UI/MCP paths funnel through one patch_work_item save, but post_save also covers raw/future saves at ~5 lines of plumbing
  • Groups resolved from State rows; reuses the existing _state_group helper and _RESOLVED_GROUPS = {completed, cancelled} vocabulary (mirrors scope-context & FE RESOLVED_GROUPS)
  • Emits for both type='task' and type='module' (epics) — seam observes all; orchestrator policy decides what to act on
  • Does NOT catch queryset .update(state=…) — one such path exists (state-delete), documented as a gap
PILLAR 2 · THE SEAM

Custom Signal, dispatched on commit

A new Django Signal issue_state_changed. post_save registers a transaction.on_commit callback that sends it. Synchronous, in-process — matches the frozen dispatch decision.

  • Payload: {issue_id, project_id, from_state_id, to_state_id, from_group, to_group}
  • on_commit guarantees rolled-back transitions never reach receivers — the future orchestrator inherits commit-accurate semantics for free
  • Pluggable: any subtask registers a receiver with signal.connect(); the emit site never changes again
  • Contract (docstring): receivers must NOT synchronously mutate Issue.state, or they re-enter the signal
PILLAR 3 · v1 RECEIVER + WIRING

One logging receiver, registered in ready()

A new signals.py holds the signal, the save receivers, and one stub receiver that logs the transition via stdlib logging.getLogger(__name__). WorktrackerConfig.ready() imports it.

  • apps.py gains a ready() that imports signals (the standard Django registration point — none exists today)
  • v1 handler is a no-op-equivalent: logs issue_id + from_group → to_group at INFO
  • No migration, no new HTTP surface, no settings change beyond the logger
  • Launch capability, ready-set computation, run-state tracking — all later #700 subtasks

User stories

"User" here is mostly a downstream developer/system consuming the seam — this subtask ships no end-user-facing behavior by design.
The seam consumer (future orchestrator / verifications author)
  1. As a graph-executor author, I want a single event that fires whenever a task's state changes, so that I don't have to wire into each write path (MCP, Studio, drag, bulk) by hand.
  2. As a graph-executor author, I want the event to carry the resolved from_group and to_group, so that I can cheaply detect "entered the completed group" without re-querying the database.
  3. As a graph-executor author, I want the event to fire only after the transaction commits, so that I never react to a state change that was rolled back.
  4. As a graph-executor author, I want to subscribe by connecting a receiver, so that I can add orchestration later without modifying the emit site.
  5. As a verifications author, I want every state transition (not just completion) surfaced on the same seam, so that I can run side-effects on any transition I care about and ignore the rest.
  6. As a seam consumer, I want transitions on epics (type='module') as well as tasks delivered on the same channel, so that epic-lifecycle logic can reuse the seam.
  7. As a seam consumer, I want the event to identify the issue and project, so that I can scope my reaction correctly in a multi-project workspace.
  8. As a seam consumer, I want a brand-new issue created directly into a state to emit (from=null), so that I never miss work that is born in a terminal state.
The platform / operator
  1. As an operator, I want a no-op save (rename, reprioritize) to emit nothing, so that the seam isn't noisy and downstream receivers aren't woken for non-transitions.
  2. As an operator, I want the v1 handler to log each transition, so that I can watch real state changes flow through the seam on a running system before any orchestration is built.
  3. As an operator, I want this change to introduce no user-visible behavior, so that shipping the seam is risk-free and reversible.
  4. As a maintainer, I want the one path that bypasses the seam (state-delete .update) documented, so that nobody later assumes the seam is total.
  5. As a maintainer, I want the receiver contract ("do not synchronously mutate state") written down, so that a future orchestrator doesn't create an emit loop.
End users (indirect, via existing paths — unchanged)
  1. As a developer using the MCP tool, I want update_task_status to keep working exactly as before, so that the seam is invisible to my workflow.
  2. As a Studio user, I want board drag-drop and PATCH state edits to behave identically, so that nothing about my UI changes.

Testing decisions

One seam, tested by external behavior: connect a spy receiver to issue_state_changed, drive a real state change through the existing ninja API, assert the signal fired (or not) with the right payload. No coupling to post_save/pre_save internals.
WHAT A GOOD TEST IS

Observe the event, not the wiring

Assert "a PATCH that changes state produced one event with these groups" — never "pre_save stored attribute X". The signal is the contract; everything behind it is free to change.

Drive the API · spy the signal

Out of scope — later #700 subtasks

This subtask is the smallest reversible step: wire the seam, watch transitions flow, then design orchestration on top. Everything below is explicitly deferred.
DEFERRED · launch

Launch capability

WorkTracker has no way to start an agent run. Runs launch via a WebSocket init frame → tmux session in the coding-app server/, where the run/lifecycle DB lives — not in worktracker-stack. No server-to-server REST launch exists. This is the central #700 HLD question.

DEFERRED · loop

Orchestration loop

Compute the ready-set from blocker states, launch unblocked tasks in parallel, react to completion to release newly-unblocked tasks. Built on this seam later.

DEFERRED · state

Run-state tracking & idempotency

Distinguish launched / running / done / failed; no-double-launch on re-invocation.

DEFERRED · failure

Stall & failure handling

Run ends but the task never reaches completed → its subtree stalls; independent branches continue. Who flips a task to Done (agent self-marks vs. human gate) is still open.

DEFERRED · trigger

execute_dependency_graph trigger

The MCP tool execute_dependency_graph(root_task_id) and/or a Dependency-view UI action.

DEFERRED · gap

Closing the .update(state=…) gap

If a future need requires state-delete reassignment to emit, add an explicit send in that route — out of scope now, documented as a known boundary.

Acceptance signal

The subtask is done when changing a task's state through any path that hits patch_work_item (MCP update_task_status, Studio PATCH, board drag, bulk action) fires exactly one issue_state_changed event with the correct from_group/to_group; creating an issue directly into a state fires one event with from=null; a save that does not change state_id fires none; the event fires on commit (a rolled-back transition emits nothing); the single v1 receiver is invoked with the structured payload and logs it; and there is no user-visible behavior change. The state-delete .update(state=…) gap is documented and pinned by a test. Orchestration and launch remain open in the #700 HLD.
