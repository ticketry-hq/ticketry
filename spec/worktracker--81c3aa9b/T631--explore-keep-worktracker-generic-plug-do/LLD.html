WorkTracker Studio · Ticket #631 · Low-Level Design draft

Slot Registry Extraction for Generic WorkTracker

Convert the current direct coding seam into a first-party extension registry so @worktracker/core owns the tracker composition, while integrations/coding registers agent-driven UI, shortcuts, and services. This LLD is a design artifact only: no implementation code is changed in this phase.

Implementation goal

The LLD turns the HLD decision into a concrete migration harness. The first implementation ticket should add the registry without changing behavior; later tickets move each current coding call-site behind registrations.
Core owns

Tracker composition

Backlog, board, story map, drawer shell, filtering, ranking, labels, blockers, sprints, search, selection, and routing stay inside the generic core package.

Coding owns

Agent provenance

The badge, lifecycle polling, coding deep-link, w shortcut, terminal launch, loops, and workflow-builder entries live outside core and register into named extension points.

Meml gets

Clean tracker

The future meml app imports the same core package and registers nothing, so no coding API env vars, agent badge, or coding shortcut ship in that consumer.

Registry contracts

Core keeps the layout and calls typed slot renderers with a narrow context. Integrations cannot reach into generic stores except through context passed by core or public store APIs.
Core API
export interface SlotContext {
  issue?: WorkItem;
  projectId: string | null;
  selection: SelectionSnapshot;
}

export type RegionSlotId =
  | "issue.drawer.header.afterTitle"
  | "backlog.row.afterTitle";

export type ActionSlotId =
  | "global.shortcuts"
  | "issue.drawer.actions";

export type RouteSlotId =
  | "project.nav.extra"
  | "project.routes.extra";

export type ServiceSlotId =
  | "app.services";

Boundary enforcement

The migration is only complete when the dependency direction is mechanically enforced. Code review alone is not enough for this seam.
Allowed
  • apps/coding-studio imports @worktracker/core and integrations/coding.
  • integrations/coding imports public core extension types.
  • apps/meml-studio imports only @worktracker/core plus generic app config.
Blocked
  • @worktracker/core importing integrations/coding.
  • Core reading VITE_CODING_APP_URL or VITE_CODING_API_BASE.
  • Core rendering AgentStateBadge by name.
Lint shape
rules: {
  "no-restricted-imports": ["error", {
    "patterns": [
      {
        "group": ["integrations/coding/*", "apps/coding-studio/*"],
        "message": "@worktracker/core must not import coding-layer modules."
      }
    ]
  }]
}

Test plan

Tests focus on behavior parity and boundary safety. Existing user-facing behavior should remain unchanged until the meml app is introduced.

Build order

These are follow-up implementation tickets. This LLD intentionally stops before code changes.

Add registry in place

Create typed registry/context/outlet helpers inside current studio/src first. Do not register anything and do not change behavior.

Move current coding seam behind registrations

Register badge region slots, the app-root lifecycle service, and the w shortcut action from integrations/coding. Remove direct core imports.

Package core

Extract the generic tracker into @worktracker/core. Coding Studio becomes a consumer that imports core and calls the coding integration registrar.

Add meml consumer

Stand up apps/meml-studio against the same core package with an empty registry. This is the proof that core is generic.

Land new coding features as add-ons

Terminal launch, loops, and workflow-builder features enter through new slot registrations, with no core edits unless a genuinely generic slot is missing.

Acceptance signal

Ready when approved: the LLD defines the registry files, slot IDs, contribution contracts, current seam migration, lint rule, tests, and build order. The task should remain in Backlog until this design is reviewed; after approval it can move forward for implementation-ticket splitting.
