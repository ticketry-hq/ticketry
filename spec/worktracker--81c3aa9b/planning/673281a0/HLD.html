Deletable States + Per-State Agent Prompts — High-Level Design

Workflow states become deletable, and deletion never strands work — issues in a removed state roll back to Backlog. Each state also gains a reusable agent prompt, so when you run an agent on an issue, the launcher auto-loads the prompt for the state the issue is in. One additive WorkTracker slice plus one read-and-prefill touch in the coding-app launcher.

ASK 1 · DELETE

A state can be deleted

Today the State API is read-only (GET …/states only). Add a delete path so a project's workflow states can be removed.

ASK 2 · NO ORPHANS

Its issues roll to Backlog

Deleting a state must reassign its issues to the Backlog state — not silently null them out (today's SET_NULL behavior).

ASK 3 · PROMPT

A state carries an agent prompt

Each state gets an editable prompt. When you run an agent on an issue, the launcher pre-loads the prompt of the state that issue is currently in.

The slice, in three pillars

Click a pillar to expand its boundary. Pillars 1–2 are pure WorkTracker; pillar 3 reaches one read into the coding-app launcher.
PILLAR 1 · DELETE-STATE · worktracker API

Deletable workflow states

New DELETE /projects/{pid}/states/{sid} route, transactional, guarded.

  • Removes the State row for a project
  • Runs the reassign (pillar 2) before the delete, in one transaction
  • Refuses (409) to delete the last remaining Backlog state — there'd be nowhere to roll issues to
  • Layers onto #619's state CRUD if that lands first; otherwise ships the route itself
PILLAR 2 · ROLL-TO-BACKLOG

No issue is ever stranded

On delete, every issue in the doomed state moves to the default Backlog state first.

  • Target = the default Backlog state (_default_state_id(), the oldest backlog-group state)
  • If the state being deleted is that default but other backlog states exist → target the next-oldest backlog state
  • Bulk UPDATE … SET state=target then DELETE, atomic — no partial state
  • Never leaves state = NULL; the legacy SET_NULL stays only as a safety net
PILLAR 3 · STATE PROMPT → LAUNCHER

States as reusable agent playbooks

New State.prompt text field, edited where states are managed, read by the launcher.

  • State.prompt (TextField, blank) — additive field + migration; exposed on StateOut, settable via create/patch
  • Issue read already nests its state → the prompt rides along to the coding app, no new route
  • Launcher auto-fills the agent prompt box from the issue's current state's prompt; user can edit before launch
  • Empty prompt → no pre-fill (today's behavior). Template variables deferred

Edge cases & open questions

Green = resolved this session. Red = genuinely open, deferred to LLD — none gate the slice.
RESOLVED · last backlog

Delete the only Backlog state?

Blocked with 409. With no backlog target, issues would strand — so the operation refuses. At least one backlog state always survives.

RESOLVED · default backlog

Delete the default Backlog (others exist)?

Allowed. Reassign target falls through to the next-oldest backlog-group state; the deleted one's issues land there.

RESOLVED · in-flight agents

State has issues with live agent runs?

Fine. Runs are keyed to the issue, not the state; reassigning the issue's state doesn't disturb any running agent.

RESOLVED · empty prompt

State with no prompt set?

No pre-fill. Launcher behaves exactly as today — the prompt box opens empty/with its usual default.

OPEN · LLD

Template variables in the prompt?

Deferred. v1 is plain reusable text. Interpolating issue title/description/key ({{title}}) is a clean follow-up, not in scope.

OPEN · LLD

Where prompts are edited if #619 Settings hasn't landed?

Deferred. Studio Settings (#619) is the home; if it isn't present yet, a minimal editor surface (e.g. coding-app DetailsTab) is decided in LLD.

Acceptance signal

The slice is done when a developer can delete a workflow state and watch its issues reappear in Backlog (never state-less); when deleting the last Backlog state is refused with a clear 409; when a state can hold an editable agent prompt; and when running an agent on an issue pre-fills the launcher with the prompt of the state that issue is in — editable before launch, empty when unset — with template variables and the exact edit surface still answerable later.
