Premise — completeness, not capability

The S2 drawer (#615) already loads the full issue detail. issueStore.open is a WorkItemDetail { task, attachments[] }, fetched by getWorkItem() from GET /work-items/{id}. The drawer renders the task and its children but ignores attachments, offers no share/placement affordance, and has no keyboard path. C4 closes those three presentation gaps. Nothing is fetched that isn't already in memory.

G04 · IssueDrawerHost.tsx · keydown

Keyboard navigation — TUI-style

A document-level keydown listener: Esc closes; ↑/↓ move within a column, ←/→ jump across columns — the geometry follows the surface, all focus-guarded.

  • Esc closes the drawer (navigate to backlog)
  • Over the board — a 2-D cursor like the TUI: ↑/↓ step within the focused state-column, ←/→ move to the adjacent column, landing on its nearest card
  • Over the backlog — ↑/↓ step the flattened Epic→Story→Sub-task line; ←/→ are no-ops (no columns)
  • Geometry = the same boardColumns() / groupBacklog() the surface already renders; move by item.key via /issues/
  • Clamp at every edge (no wrap); ←/→ skip empty columns; no-op when the current key isn't in the loaded set
  • Guard: bail when activeElement is input / textarea / contenteditable

A single existing read serves all three gaps. The drawer mount already triggers it; C4 just consumes more of the payload and reads one selector.

The keyboard walk — line vs grid

Navigation moves through issues in the exact order behind the drawer. The host resolves the surface and picks geometry: a 1-D line over the backlog, a 2-D grid over the board — the same cursor model as the TUI kanban. Click a step for mechanics and edge cases.
  1. 1Resolve the originating surface — the board or backlog the drawer was opened over — and read the same store inputs it renders from.
  2. 2Board: boardColumns(items, states, modules, filters) → BoardColumn[], one column per state, each items[] rank-sorted. This is the grid.
  3. 3Backlog: groupBacklog(...) flattened depth-first → a single line of keys (sub-tasks included).
  4. 4Locate the open issue: on the grid → (col, row); on the line → one index.
  5. 5↑/↓ = row∓1 within the column (index∓1 on the line). ←/→ = nearest non-empty column, row clamped to its length. All clamped, no wrap.
  6. 6navigate(`/issues/${nextKey}`) — the route swap re-opens the drawer on the next issue.

  • No backend, SDK, migration, route, or new dependency.
  • The host resolves the originating surface — board grid (boardColumns) vs backlog line (groupBacklog) — to pick geometry; how that origin is threaded (router location state / a uiStore origin field) is LLD, and a cold deep-link with no origin defaults to the backlog line.
  • The flatten helper is a few lines beside groupBacklog (or inline in the host) — deterministic depth-first over EpicGroup.rows; exact placement is LLD scope.
  • The keydown guard extends the Popover pattern: Popover closes on Esc unconditionally; the drawer listener additionally bails when activeElement is input/textarea/contenteditable, so an open inline name/description editor keeps its own Escape.
  • Human-readable size formatting (B/KB/MB) is a tiny local utility; null → —.

Acceptance signal

The slice is done when, in the issue drawer: an issue that has attachments shows a rows list (icon · name · size · new-tab link) that disappears when there are none; the header offers a copy-link that puts ${origin}/issues/${KEY} on the clipboard with a brief "Copied"; a Project › Epic crumb sits above the name and both segments navigate (Project-only when there's no epic); and the keyboard works like the TUI — Esc closes; over the board ↑/↓ step within the focused state-column and ←/→ move to the adjacent column's nearest card; over the backlog ↑/↓ step the visible, filtered line; every axis is clamped (no wrap) and an open inline editor keeps its own typing and Escape. tsc + vitest + build stay green, with new coverage in IssueDetail.test.tsx and a drawer keyboard test.
