# Descriptions and documents

Edit a ticket's Markdown description and its registered design documents while preserving drafts and resolving external changes.

Surfaces: browser, desktop
Editions: pocock, core

## Sub-features

- `documents-rich-description`: live rich Markdown description, formatting/source modes and parse fallback.
- `documents-description-autosave`: ticket-keyed drafts, pause/blur/Story-switch saves and write serialization.
- `documents-description-external-change`: clean refresh and dirty-draft keep/load choice.
- `documents-registered-tabs`: discovered Markdown and HTML documents, filename labels and retained editors.
- `documents-markdown-save`: explicit save/cancel, periodic autosave and digest-guarded conflict recovery.
- `documents-html-viewer`: sandboxed HTML with authorized sibling assets.

## How to get to it

- Select a module, select a Story in the Stories tree and open the `Details` tab in the `Workspace tabs` tablist. Click the description (`issue-description`); it is a live editor, with no separate description Save button. Empty descriptions show `Add a description…` while the editor loads.
- In the same tablist, select a registered document by filename without extension, such as `DESIGN` or `REPORT`. Editable Markdown opens the rich editor automatically; after cancelling, use `Edit document` to resume. A full HTML document stored in a `.md` file stays in the read view until `Edit document source` is chosen. HTML files open the iframe viewer.
- Default `workspace-tab-next` / `workspace-tab-previous` actions are `Cmd+Right` / `Cmd+Left`. In the compact description editor, `Tab` and `Shift+Tab` leave prose; lists retain indentation handling. These bindings and editor-specific handling are defined in `studio/src/app/navigation/keymapBindings.ts` and `studio/src/features/documents/RichMarkdownEditor.tsx`; see [workspace tabs](ticket-workspace-tabs.md) for navigation and dormant-tab behavior.
- The tree's `New conversation` action starts a taskless run using defaults. It does not open a visible scratch-document workspace. Selecting an existing conversation shows its terminal surface; current scratch-document reachability limitations are below.

## Prerequisites

- A selected project/module and persisted Story are needed for description writes. Description drafts are keyed by the concrete ticket ID; create two Stories for isolation checks.
- Document discovery needs a module linked to an authorized local folder and files in that ticket's canonical design directory. Use the design directory supplied by Ticketry rather than constructing a live-data path. The browser document fixture creates disposable directories and refreshes the Rust registry before opening tabs.
- External-change checks need a second writer: change the Story through the server, or change a registered file on disk. Observe an authoritative refresh/subscription result before asserting a notice.
- Native WebKit description proof requires macOS and the desktop harness prerequisites in `studio/e2e-desktop/README.md`.

## Expected behavior

- **Rich description:** Markdown formatting supports headings, lists, links, images, tables, code blocks, undo/redo and source view. Initial editor normalization is ignored as an edit. Legacy HTML is readable and converted to Markdown when edited; parsing failure retains text in `Ticket description source` with a visible fallback notice. The compact toolbar appears on focus (`RichMarkdownEditor.tsx`, `DescriptionEditor.tsx`).
- **Description saves:** after an 800 ms typing pause, focus leaving the description or Story unmount, dirty text is submitted through the selected ticket's update path. Opening a clean draft writes nothing. `Saving…` indicates an in-flight write; rejection retains the draft, shows `Description not saved:` and permits retry at a later save boundary. Same-Story requests serialize and preserve edits made during a pending write (`descriptionDrafts.ts`, autosave acceptance).
- **Server changes:** a clean editor follows refreshed server text. A dirty editor keeps its text behind `description-external-change`, says `This description changed on the server. Your draft is still here.`, and pauses its normal autosave while the choice is pending. `Keep my draft` accepts the new baseline while preserving local text; `Load the server version` replaces it. This is a choice between versions, not a merge (`DescriptionEditor.tsx`, external-change acceptance). There is no description Cancel-editing action.
- **Document discovery and retention:** registry refresh rescans authorized roots, discovers additions and prunes deleted files; labels derive from filenames. Each open document stays mounted across tab switches, preserving an unsaved buffer. An empty registry contributes no document tabs. A failed registry refresh does not prove a remembered document was deleted: the workspace keeps the rows Apollo already holds for that ticket (a cache-only read) but does not report the registry as fetched, so restoration never prunes remembered intent until a later refresh succeeds (`documentRegistry.ts`, `queries.ts`, `WorkspaceTabBody.tsx`).
- **Markdown document saves:** `Save document` persists the draft and leaves edit mode active; the button is disabled for an unchanged draft or while saving/loading. `Cancel editing` discards unsaved text and returns to `markdown-document`. A 10-second periodic autosave attempts dirty, unblocked drafts after checking the current disk digest; this is separate from description autosave (`DocViewer.tsx`, `MarkdownDocumentEditor.tsx`).
- **Disk conflicts/errors:** dirty buffers survive external changes. `Compare versions` shows `Document comparison` with `Mine` and `On disk`; `Reload external version` opens `Reload external version?`, whose Cancel preserves the draft and `Reload theirs` discards it. A stale explicit save exposes `Overwrite with mine` for a deliberate retry against the returned digest. Automatic conflict detection first exposes the external version. Load failures show `Unable to load this document.`; save failures show `Save failed` (`DocViewer.tsx`, document-save acceptance).
- **HTML:** `workspace-doc-frame` loads registered HTML using the runtime document URL, with the document label as its title and `sandbox="allow-scripts"`. Scripts can run inside the opaque frame; they cannot access the host document. Authorized sibling assets load; an escaping symlink asset is rejected by the browser fixture. HTML files have no Markdown save/cancel editor (`HtmlDocumentViewer.tsx`, documents-and-scratch browser spec).
- **Persistence:** a description is durable only after the server returns the ticket update and an authoritative ticket read returns the new description. Reload, reopen Story A and verify its server text, then open Story B and verify its distinct text; a retained draft alone proves neither persistence nor isolation. For a saved document, read the runtime-served bytes/digest (and fixture disk bytes where available), refresh its server registry, reload and reopen the tab. Unsaved editor retention across tab switches is a different claim from saved persistence.
- **Scratch ownership:** task and scratch registries are separate; scratch refresh binds a module ID and resolves authorized planning/instant-run roots. That retained registry is not evidence of a currently reachable scratch-document tab (`queries.ts`, Rust document registry and selected-ticket source).

## Gotchas

- Wait for the lazy rich editor and the write's server readback. `Saving…` disappearing or text surviving a tab switch alone cannot prove persistence. Rich-editor mocks named `Story description` or `Preloaded description editor` are test scaffolding, not production accessible names.
- Description and file documents have different save/conflict rules. Description unmount explicitly requests a save; pending external-change choice blocks normal timer/blur saves, so do not infer that switching away with an unresolved notice is a verified safe cancellation path.
- The module scratch registry is backend infrastructure without a visible document entry on either surface. `SelectedTicket.tsx` hides the New conversation workspace unconditionally, and `useTaskWorkspace.ts` supplies no documents when `conversationRunId` is set. It is therefore not a document UI sub-feature or a desktop-only coverage exemption. New conversation launch belongs to conversations; public scratch-registry contract proof belongs to agent-facing services. Historical “Local scratch workspace” wording in the browser spec title does not establish a visible document feature.
- Browser HTML proof does not establish native document-protocol asset behavior. Report native cases skipped separately when macOS/WKWebView is unavailable.
- Browser setup is partly stale: `studio/e2e/web-app.spec.ts` still expects `Open Modules pane` and historical sidebar recovery text. Its shared `studio/e2e/support.ts` `openModule` helper waits only for the selected module tab and module workspace region (CODING-2847); current module chrome uses the Module Manager. Report a setup failure as such instead of claiming that the description/document scenario ran or failed. The shared helper also serves the document and rich-description specs cited above.
- The [e2e skill](../../.claude/skills/e2e/SKILL.md) still mentions Django. Use the [index](README.md) and Rust GraphQL adapter launcher for isolated browser setup; do not direct document writes at live data.
