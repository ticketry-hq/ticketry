Sprints in WorkTracker — High-Level Design

A sprint is a time-box. WorkTracker already groups work by topic (the epic/module tree); sprints add a second, independent axis — when a task ships. This slice lays the foundation: a new Sprint model, a one-FK link on every task, and the CRUD + assignment surface. Reporting comes later.

One task, two questions

The core idea. A task's epic and its sprint are independent — assigning one never touches the other. This is why a sprint is a new model, not a renamed module.
EXISTING AXIS · WHAT

The epic / module tree

A task's parent link answers what this work is part of — its feature, its epic. Already shipped: Issue.parent walks the module → task → subtask tree.

NEW AXIS · WHEN

The sprint

A task's sprint link answers when this work ships — which time-boxed iteration it's committed to. New: Issue.sprint, a nullable FK to a project-scoped Sprint.

A task can sit in an epic AND a sprint at the same time. The two axes never collapse into one.

PILLAR 1 · SCHEMA

Sprint model + one FK

A new Sprint table, project-scoped like State/Label, plus a nullable sprint FK on Issue.

  • Sprint: name, start_date, end_date, status (planned/active/completed)
  • Issue.sprint FK — null=True, on_delete=SET_NULL
  • Migration 0002 adds table + column; backfills NULL, no data migration
  • No story points / estimate field on Issue
PILLAR 2 · API

CRUD, listing & assignment

Five additive sprint routes behind the existing ApiKeyAuth; assignment rides the existing work-item patch route.

  • list / create / get / patch sprints; list a sprint's tasks
  • PATCH /work-items/{id} extended to set/move/clear sprint_id
  • GET /sprints/{id} returns progress counts (total / done / open)
  • SDK gains a sprints resource (additive)
  • No new MCP tools in this slice
PILLAR 3 · BOUNDARY

What waits for later

Foundation now; the analytics and surfaces that ride on top are separate tickets.

  • Burndown / velocity / completion-rate reporting
  • Estimates / story points
  • MCP tools for sprint create/list/assign
  • Frontend / TUI sprint surface
  • Schema chosen so estimates & reporting bolt on without rework

Decisions & edge cases

Green = a decision locked with the requester. Amber = a behavior the implementation must get right.
DECISION · model

New table, not a renamed module

Sprints time-box; modules group by topic. Reusing the module issue type would force a task to choose epic OR sprint. A separate Sprint model keeps both axes independent.

DECISION · membership

One current sprint per task

A single nullable FK. Re-assigning replaces the prior sprint; there is no membership history. Spillover is handled by moving the task to the next sprint.

DECISION · metric

Count tasks, no points

Progress = done vs total, derived from each member task's state group (completed/cancelled = done). No estimate field this slice; velocity is a later add.

DECISION · surface

Additive only

The 13 frozen routes and the provision/import paths are untouched. SDK gains a sprints resource. No MCP tools, no sprints minted at provision.

EDGE · delete

Deleting a sprint never deletes work

SET_NULL means a removed sprint just unsprints its tasks — they survive with sprint_id=NULL. Must be covered by a test.

EDGE · close & tree

No auto carry-over, no cascade

Closing a sprint leaves incomplete tasks attached until re-assigned. A subtask's sprint_id is independent of its parent's — membership does not cascade through the tree.

Acceptance signal

The slice is done when a caller can create a sprint in a project, assign and move tasks in and out of it via the work-item patch, list a sprint's tasks, and read back progress counts driven by task state — while the epic tree is unaffected, deleting a sprint leaves its tasks intact with sprint_id=NULL, the 13 frozen routes are byte-for-byte unchanged, the SDK exposes the new routes, and the full worktracker + sdk + server suites stay green.
