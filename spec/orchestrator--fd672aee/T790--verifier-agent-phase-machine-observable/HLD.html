Verifier-agent phase — machine-observable quality verdict

v1 completes a node on structural facts — commits exist, the check command is green. This adds a quality axis without reopening a human gate: a cheap judge agent runs against a node's artifact, and its own postcondition is writing a machine-readable accept/reject verdict. Accept lands the node; reject drops into the node's existing corrective retry with the findings as diagnostics. This is what makes the auto/gated flag a real choice — auto = verifier verdict, gated = human approval.

V1 · STRUCTURAL ONLY
A node is done when the driver's implement postcondition holds: ≥1 new commit AND the check command green in the node worktree. Correctness of intent is never judged — a green build with a wrong-headed diff still lands.
→
GATED FALLBACK
For doc-producing work there is no structural postcondition at all, so quality can only be caught by a human at the landing gate. That makes auto a non-choice for those strategies.
→
THIS DESIGN · VERIFY PHASE
A separate cheap judge agent runs after the structural postcondition, before merge-back. Its postcondition is a machine-readable verdict.json. Accept lands; reject feeds the corrective retry. The human gate stays collapsed to the two bookends.

Where verify slots in — one seam, before merge-back

The verify phase inserts itself into a single transition: the moment an implement node's structural postcondition would have flipped it to done. In auto mode with a verify-capable strategy, that flip is deferred until a judge verdict exists. Everything downstream (merge-back #788, halt propagation, budgets) is untouched.
BEFORE (v1)

implement → done

Driver verifies check_implement_postcondition (commit + check green) → node done → topo merge-back into the integration branch.

AFTER (this HLD)

implement → verify → done

Postcondition green → node enters the new verify phase (pending, re-launchable) → judge writes verdict.json → accept → done → merge-back. Reject → corrective retry.

THE INVARIANT

rejected code never merges

Verify runs in the node's own worktree, entirely before the merge queue. A reject relaunches implement on the same branch with findings; nothing enters the integration branch until a verdict is accept.

PILLAR 1 · PURE REDUCER · state.py + reducer.py

A verify phase & verdict transition

The reducer learns one new phase and how a verdict routes it. Still total, pure, framework-free.

  • Phase gains "verify"; Event gains verdict: "accept"|"reject"|None; RunState gains verify_enabled: bool
  • Implement node succeeds & verify_enabled → not done yet: phase→verify, status→pending
  • verify exit: accept→done; reject→implement pending + burn the single per-node retry; retry-spent or no-verdict→failed+surface
  • Scheduler picks the pending verify node with no change — its blockers are already done
  • Halt propagation, max_depth, capped ready-set — all as-is
PILLAR 2 · EFFECTFUL DRIVER · driver.py + loader.py + policy.py

Launch the judge, read the verdict

The judge is just another headless run; its verdict artifact is a checked fact, exactly like every other postcondition.

  • check_verify_postcondition: a parseable verdict.json with a valid verdict exists (postcondition = "a verdict was written")
  • resolve_exit reads the verdict file → sets event.verdict + postcondition_ok
  • Launch renders verify.md (judge prompt) with the node's diff injected; spawns the cheap-model run in the node worktree
  • loader: verify is an optional phase; new whitelist token diff; driver-supplied context
  • policy: (phase=verify) → cheap model rule; verify added to the phase literal
  • headless launch primitive, worktree, MCP injection, supervisor timeout — all reused
PILLAR 3 · REJECT PATH & RECORDS · models.py + strategy pack

Reject reuses the corrective retry

A reject is not a new failure mode — it is the existing "one informed corrective relaunch per node," with the verifier's findings as the diagnostic.

  • Reject → the node's retried flag + corrective implement relaunch (§3.6) — no new retry counter
  • Corrective implement prompt threads the verifier's findings alongside the existing diagnostics
  • HeadlessRun gains verdict + verdict_findings (migration 0004) — durable, feeds A/B reject-rate metrics (§5)
  • strategies/default/verify.md + pack.toml declares the verify phase & its cheap-model policy rule
  • by-interface pack (#5) may ship its own verify.md; packs without one simply don't verify

Owner forks

Green = locked this session. Red = deliberately deferred; neither blocks the build.
LOCKED · Fork A

Which artifacts does verify gate?

Doc + code. Verify gates all implement nodes — a quality axis layered on commit+check-green for code, and the sole machine gate for doc-producing nodes. Matches the ticket text literally.

LOCKED · Fork B

How does a verify run count against budget?

Counts against max_total_runs. One hard ceiling; a verify is a normal launch. Worst case per node = implement + verify + implement-retry + verify = 4 runs; budget_exceeded surfaces loudly as designed.

OPEN · deferred

Model escalation on the corrective retry?

Off in v1 (owner decision #7). The (phase, depth, attempt) policy axis already exists, so a stronger model on the reject-driven retry is later config, not code.

OPEN · deferred

Verify the decompose node too?

No. Decompose already has a structural gate (§3.2) that machine-checks its output. Verify targets artifact quality (code diff / doc), which is an implement-phase output. Revisit only if decompose quality proves a real gap.

Acceptance signal

With a verify-capable strategy in auto mode, an implement node whose structural postcondition passes launches a cheap judge run that writes verdict.json; an accept lands the node and it proceeds to merge-back unchanged, while a reject relaunches implement once with the verifier's findings threaded in and, if the retry is spent or no verdict is written, the node fails loudly and surfaces. A strategy pack with no verify.md behaves exactly as v1. Verify runs are counted in max_total_runs and their verdicts are recorded on the HeadlessRun for A/B reject-rate metrics. The reducer changes are covered by pure unit tests (accept / reject-with-retry / reject-retry-spent / no-verdict / verify-disabled bypass); the driver's verdict read and the loader's optional-phase handling are covered by their existing suites — all green.
