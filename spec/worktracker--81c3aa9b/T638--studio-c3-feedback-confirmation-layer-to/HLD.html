The two policies that govern everything below

Confirmed this session. They decide when a toast fires and where an error is allowed to surface — so the new layer never double-reports and never spams.
POLICY 1 · WHEN TOASTS FIRE

Errors always, successes only for discrete acts

An error toast fires in every mutation catch — the rollback case is no longer silent. A success toast fires only for discrete / destructive actions: delete issue, delete type/state, create issue/sprint, start/complete sprint. High-frequency edits — drag, reorder, inline rename, state change — stay quiet.

Error = always · Success = discrete/destructive only
POLICY 2 · ONE CHANNEL

Mutation errors route to toasts; load errors stay inline

Mutation-error inline banners are removed and routed through toasts — a single channel, no double-surfacing. Page-LOAD error banners stay inline (a failed list fetch is a page state, not a transient event). The store error field may remain set; it is simply no longer rendered for mutations.

See Open Item Q1 — the shared error field needs a per-site split

The slice, in four parts

Click a card to expand its surface. Two new stores, three new shell components, edits across the three mutation stores plus two views.
PART A · G16 · TOAST SYSTEM

toastStore + ToastHost

A zustand store of transient messages and a single host that stacks them bottom-right, above the drawer.

  • stores/toastStore.ts — toasts: Toast[], push(kind, message, opts?), dismiss(id); kind ∈ {success, error}
  • Thin toast.success(msg) / toast.error(msg) helpers via getState() — callable from non-hook store code
  • Auto-dismiss success (~4s); errors persist longer / until dismissed
  • shell/ToastHost.tsx — stacked toasts, kind icon (from lib/icons), message, dismiss button
  • role="status" / aria-live="polite" for success; role="alert" for error
  • Mounted once at app root (Shell), above IssueDrawerHost
PART B · SHARED PRIMITIVE

Modal shell

One accessible overlay used by the new dialogs only. The existing IssueDrawerHost / CreateIssue overlays are left untouched.

  • shell/Modal.tsx — backdrop + centered panel on the Studio dark token theme
  • role="dialog" / aria-modal, Esc-to-close, backdrop-click close
  • Focus trap + focus restore on close
  • Rendered within app root — same overlay convention as IssueDrawerHost (z-backdrop + z-panel), no new portal lib
PART C · G01 · DELETE-CONFIRM

dialogStore.confirm()

An imperative promise API so a click handler can await a yes/no before mutating.

  • confirm(opts): Promise<boolean> · opts = { title, body, confirmLabel, danger? }
  • DialogHost renders the active dialog through Modal
  • IssueDetail.onDelete awaits confirm(…) before deleteIssue; cancel → no-op
  • Existing sub_issues_count > 0 disable-gate stays — no confirm offered when blocked
PART D · G17 · REASSIGN MODAL

dialogStore.reassign()

Replaces the two window.prompt calls; the two window.alert blockers become disabled, tooltipped affordances.

  • reassign(opts): Promise<result> · null = cancelled, {} = delete-only-if-unused, else target id
  • opts = { title, itemName, candidates: {id,name}[] }; rendered by the same DialogHost via Modal — radio list of targets + "Delete only if unused"
  • SettingsView type & state onDelete → await reassign(…) then deleteType/deleteState(id, targetId)
  • Un-deletable cases get a disabled + tooltipped affordance, so the modal only opens when deletion is actually possible:
  •   · is_default type → "Set another default first"
  •   · last-state-in-group → "Last state in its group"

VERIFY · Q1 banner classification

The store error field is shared by load and mutation

The ticket lists 5 banners to remove (Board, Backlog, SprintsLens, StoryMap, Settings) and 2 to keep (routes.tsx, IssueDetail). Exploration found the four view banners are full-screen gates that render on load failure, while the same error field is also set by mutation catches. LLD must inspect each of the 7 sites and decide the mechanism — e.g. split a dedicated load-error path from the transient mutation path — so load failures still surface inline while mutation errors go only to toasts. Removal target stays "mutation-error banners"; the per-file count is confirmed in LLD.

CONFIRMED · helper reach

Toast helpers callable from non-hook code

toast.success/error use getState() so store actions (which aren't React hooks) can fire toasts directly inside a catch. No prop-drilling, no context.

CONFIRMED · no browser dialogs left

Zero window.prompt/alert/confirm in Studio

Both Settings prompt calls → reassign(); both alert blockers → disabled + tooltipped affordances. The IssueDetail delete → confirm(). Grep for the three globals must come back empty.

CONFIRMED · icon gap

Icon set needs success + error glyphs

lib/icons has IconX and IconAlertTriangle but no check/success icon. Add a check (success) and an error glyph; reuse IconX for the dismiss button.

Acceptance signal

The slice is done when:
  • A failed mutation shows an error toast — and the optimistic UI still rolls back.
  • Discrete / destructive successes show a success toast; drags and inline edits do not.
  • Deleting an issue requires confirming a modal; cancel aborts with no mutation.
  • Deleting a type/state with assignable issues opens an in-app reassign modal; un-deletable types/states present a disabled, tooltipped affordance.
  • No window.prompt/alert/confirm remain in Studio.
  • The mutation-error inline banners are gone; the load-error banners remain.
  • Regression green: existing board / backlog / storymap / settings / issue suites + new toastStore / dialogStore / Modal / IssueDetail / SettingsView tests + tsc + build.
