Register approved HLD split — the register phase

Add a fourth phase register to the process-local execution tracer (apps/execution). When an approved root task moves into the LLD state, the same signal that completes the split phase now chains directly into a register run — no second human gate — that launches an agent to read the approved HLD and create the split tree in WorkTracker. The engine owns only the launch and its relaunch guard; the create/edge side effects live inside the agent (Fork B). This is a pure-reducer + thin-driver change: one new phase, one new recipe, one new reducer branch, and the observe path learns to apply a launch action. No models, no migration, no endpoints, no frontend.

The flow: one signal, one new branch — split completes by chaining into register

Everything hangs off a single issue_state_changed event reaching the task's EngineState in the process-local registry. Today, a running split observing to_state=="LLD" is marked done. #745 replaces that leaf with a chain: mark the split complete by advancing the same EngineState's phase to register and emit a register LaunchAction; the driver applies it via spawn_run. Reducer contract — the new issue_state_changed branch

The reducer stays pure: same decide(state, event) → Decision(next, actions) shape. #745 adds one branch before the existing completion check and removes split from _is_complete (it now chains instead of completing to done). No new event kind, no new LaunchAction field — recipe already carries the phase.
PHASE VOCAB
Phase = Literal["implement", "refine", "split", "register"] in state.py. Adding the string is the whole type change; LaunchAction.recipe: Phase and EngineState.phase: Phase both widen for free.
CHAIN BRANCH
Inside if event.kind == "issue_state_changed":, first: if state.status == "running" and state.phase == "split" and event.to_state == "LLD": return Decision(next=replace(state, phase="register", status="idle", agent_run_id=None, error=None), actions=[LaunchAction(task_id=state.task_id, project_id=state.project_id, module_id=state.module_id, agent=state.agent, recipe="register")]).
WHY status→idle
Mirrors the execute_requested pattern: the launch action is emitted while next is not-yet-running; the driver applies it and feeds run_started to flip running (or run_failed). Keeps a single code path for "emit action → apply → observe result".
REMOVE FROM _is_complete
Delete the if state.phase == "split": return event.to_state == "LLD" case. split no longer terminates in done; the chain branch above handles it. _is_complete now covers only implement (to_group=="completed") and refine (backlog→unstarted).
RELAUNCH GUARD
After the first chain, state.phase == "register". A replayed to_state=="LLD" fails the chain condition (phase != "split") and falls to _is_complete, which has no register case → Decision(next=state), no action. The engine's contribution to idempotency is exactly this phase check.
NEVER-COMPLETE
register is absent from _is_complete, so no issue_state_changed ever flips it to done. Registration completeness (and any partial-failure halt) is owned by the agent run and its terminal output. A durable HLD Approved → Split Registered state is future work (#744).
UNCHANGED
execute_requested / run_started / run_failed branches are untouched. Task-id mismatch still short-circuits. The Decision and SeamEvent shapes are unchanged.

register recipe — the agent-prompt contract (decisions 1–4)

Because registration is agent-driven (Fork B), decisions 2–4 live in the register prompt, not in engine ports. initial_prompt_for("register", issue) in recipes.py returns a _register_prompt(issue) string; the driver threads it into spawn_run(initial_prompt=…) exactly as it does the refine/split prompts. The prompt instructs:
InstructionEncodesDetail
Read the approved HLD from the task's spec directory and extract the proposed leaves + intended blocked_by edges.Decision 1Source of truth is the visual HTML HLD the #720 splitter wrote (prose split tree). The agent parses it; the engine never parses the HLD.
Create each missing leaf as a type=task child of the root, tagged with its stable slug; skip if a child with that slug already exists.Decision 2Slug embedded deterministically (e.g. in the child key/title/description marker). Idempotent-on-slug replay convergence — no duplicate leaves across relaunches.
Create leaves in the Todo state (not the project-default Backlog).Decision 4Leaves skip #719 refinement and are directly eligible for #743 leaf-LLD generation.
Wire each missing directed blocked_by edge (A blocks B / B blocked_by A); skip if B.blocked_by already contains A; respect the existing blocker_would_cycle guard.Decision 2Uses the #624/#699 blocked_by M2M + cycle guard via the WorkTracker blocker tools. Idempotent-on-edge.
Stop on the first create-or-wire failure; report the partial state clearly (what was created, what failed, why); do not claim registration complete.Decision 3Surface-and-halt. No automatic multi-item resume within a run. Visible via the agent run's terminal output.
Do not generate leaf LLDs and do not implement code.Scope fenceLeaf LLDs are #743; implementation is later. Registration is create + wire only.

The prompt embeds task identity (issue.id, issue.key, issue.name, issue.project_id, issue.project.slug) the same way _split_prompt does, so the agent has the root context it needs to look up existing children and create under the correct project.

How does split "complete AND launch register" in a pure reducer?One chain branch; advance phase, emit actionOn split+running+→LLD, return next with phase="register" and a register LaunchAction in one Decision. Split "completion" = phase advanced past split; no separate done leaf, no second event round-trip. Keeps the reducer pure and the driver's apply path single.
Keep a durable "split done" record?No — single EngineState, phase advancesThe tracer holds one EngineState per task in _registry. Advancing its phase to register is the completion signal. A durable per-phase lifecycle model is explicitly #744.
Where does the observe path get spawn and the Issue for the prompt?observe gains spawn=spawn_run param + loads Issueobserve_issue_state_changed already does an ORM lookup to resolve to_state_id → name; it also fetches the Issue to build the register prompt. The injectable spawn default keeps the signal receiver call unchanged while letting tests mock the launch.
Share the launch-apply code between execute() and observe()?Extract _apply_launch(state, action, issue)execute() already applies a launch action (spawn → feed run_started/run_failed). Lift that into one helper both paths call, so register launch behaves identically to an execute_requested launch, including run_failed on spawn error.
Does the observe path re-validate phase preconditions (backlog/Todo gates)?No — the →LLD transition is the gateThe refine/split state-group gates live in execute()'s setup, not in _apply_launch. Register is triggered by an already-approved transition, so no extra gate; the relaunch guard prevents duplicates.
Which agent runs registration?The task's EngineState.agent (the split run's)replace() preserves agent; the register LaunchAction.agent = state.agent. One consistent agent across the task's phases.
Does LaunchAction need a new field for the HLD path or slugs?NoThe agent reads the spec dir and derives slugs itself (decision 1/2). The engine passes only recipe="register"; the recipe prompt carries the rest.

Acceptance signal. The slice is done when:
  • The execution engine has a fourth phase register with a split-registration recipe (_register_prompt).
  • An approved root moving into LLD completes split (phase advances) and, in the same observe, launches the register run for that task — no second human gate.
  • A replayed →LLD transition launches no second registration run (phase-check relaunch guard); the recipe's slug/edge dedup prevents duplicate leaves/edges even across launches.
  • The recipe instructs slug-idempotent leaf creation into Todo under the root, idempotent directed blocked_by wiring respecting the cycle guard, and stop-on-first-failure with a clear partial-state report; it does not write leaf LLDs or implement code.
  • The engine never marks register done (absent from _is_complete); partial/failed registration stays visible via the agent run, and a launch failure yields status="failed".
  • test_reducer.py + test_driver.py cover the register launch action, the relaunch guard, and run_failed on launch failure (mocking spawn_run); test_signals.py stays green unchanged.
