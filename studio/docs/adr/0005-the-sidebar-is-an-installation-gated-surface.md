# The sidebar is an installation-gated surface, and pane flags are subordinate to it

[ADR 0004](0004-projects-behind-an-installation-feature-flag.md) gated the Projects surface behind an installation feature flag read from `features.json`, defaulting to hidden. This decision extends that model to the collapsible sidebar itself. Everything 0004 established — a config file rather than a database row, gating the rendered surface rather than the REST or MCP contract, one flag read once at process start — carries forward unchanged and is not restated here.

The new flag is named for the **surface**, `sidebar`, not for the Modules pane it contains. The alternative we rejected was a pane-scoped `modules` flag, making `features.json` a flat registry of panes with the sidebar as an emergent surface that exists whenever any pane flag is on. That composes more prettily, but it puts the flag at the wrong altitude: what an installation wants to switch off is the *surface* — the `\` binding, the pane-focus navigation model, the footer hint, the shortcut entry — not one pane's worth of content. Naming the flag for the surface makes the thing being gated the thing being named, and leaves the sidebar's internal composition a private matter.

That makes `projects` **subordinate** to `sidebar`: it selects a pane *within* a rendered sidebar rather than standing beside it as a peer. We resolve the resulting contradictory state — a Projects pane enabled with no surface to live in — in `load_features()`, by coercing `projects` to false whenever `sidebar` is off. The configuration response therefore only ever carries satisfiable states, and no frontend code needs to know that one flag conditions the other. We chose backend coercion over an implication in the other direction (`projects: true` forcing the sidebar on) because that would stop `sidebar: false` meaning what it says, and over leaving the combination legal-but-inert because that spreads the subordination rule across every consumer of the flag.

`sidebar` defaults to `false`, matching `projects`. This is safe only because module selection and module creation both already exist on the Module tab strip, independent of the sidebar: turning the flag off removes a redundant surface, not a capability. Had the Modules pane been the sole route to either, the default would have had to be `true`.

A consequence we accepted deliberately: the guided tour no longer manipulates layout. It previously forced the sidebar visible and installed the default panel layout so its module-creation coach mark had an anchor, then restored the user's own layout when it ended. With the sidebar gated off by default, revealing it for one step would teach a surface the installation has switched off and cannot return to. The module-creation anchor therefore moves to the Module tab strip unconditionally — one anchor, one code path, the same tour in every flag combination — and the tour's layout capture-and-restore clause is deleted rather than made conditional.

## Consequences

- With `sidebar` off, the Edit view is the only Studio layout. There is no key that reveals a sidebar, no footer chip, and no keyboard-shortcut entry advertising one: the affordances are absent rather than inert, so a switched-off sidebar reads as a configuration rather than a broken binding.
- A webview that already persisted a visible sidebar — any installation upgrading across this change — has that preference overridden by the flag, not honoured. The stored value survives untouched, so turning the flag back on restores the sidebar the user last had.
- The persisted panel layout keeps its four-slot shape. The two sidebar slots lie dormant while the surface is off, so flipping the flag back restores prior pane sizes rather than resetting them.
- Every installation upgrading to this change loses its sidebar until it opts back in. This is a visible change to a working setup, justified only by the Module tab strip already carrying everything the Modules pane offers.
- Adding a third sidebar pane later means a second subordinate flag and a second coercion clause, not a new top-level surface flag. If the sidebar ever gains a pane whose capability has no equivalent elsewhere, this ADR's default should be revisited.
