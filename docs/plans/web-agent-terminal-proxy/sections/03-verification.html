Verification, rollout, and scope

This change has two realtime channels with different jobs. The existing GraphQL status subscription stays on the Rust adapter's streaming HTTP endpoint, consumed as SSE over fetch. A new WebSocket route carries only terminal input, terminal output, resize, and scroll control. Launch remains a GraphQL mutation. A passing terminal socket cannot make an agent visible if the status stream is broken, and a healthy status stream cannot make a terminal interactive if the PTY route is broken, so the checks below keep those paths separate.

Implementation order

  1. Freeze the boundary. Record the browser socket path, the WebSocket frame shapes, close-code meanings, input and output size limits, and the rule that the browser viewer uses ViewerTransport::Browser. Derive the socket URL from the configured GraphQL origin. Reject an invalid origin during runtime startup, before a socket is opened.
  2. Build the adapter route. Add one focused WebSocket module beside the development GraphQL adapter. Register it in studio/src-tauri/src/bin/ticketry_graphql_adapter.rs. The route accepts an attach frame containing a validated run id and geometry, calls the existing terminal attachment boundary, stages and acquires a viewer lease, sends one ready frame, and then runs the input, output, control, renewal, and cleanup loop. It must close the attachment and release the exact lease on every exit path. It must not create a second terminal store or kill tmux when a browser viewer detaches.
  3. Port the browser transport. Port the narrow Rusty client and wire builders into the existing terminal client contract. Change terminalClientRuntime.ts to select the browser WebSocket client outside Tauri. Keep the desktop selection on tauriTerminalClient. Reconnect only after a ready connection has failed, stop after the bounded retry budget, and stop sending input after session loss or viewer replacement.
  4. Route browser launch through GraphQL. First prove parity between the desktop direct-launch command and the existing terminal_session_create mutation. If parity holds, remove the browser-only rejection in launchDefaultAgent.ts and enter through that model-shaped create with concrete project, module, issue, target, working-directory, geometry, and request identities. Add a named launch mutation only if the parity test identifies behavior the create contract cannot represent. Do not add REST or substitute run_now unless the product action is explicitly the workflow transition.
  5. Compose browser launch and wire development forwarding. Configure the adopted interactive terminal runtime with the isolated web profile's launch paths, hook runner, spool directory, in-process MCP URL, and run authority. Retain the MCP runtime for the process lifetime. Add only the PTY WebSocket entry to studio/vite.proxy.ts with WebSocket forwarding enabled. Leave /graphql/subscribe as an ordinary HTTP proxy. Add the browser terminal endpoint to browserRuntime.ts and its tests. The adapter remains bound to loopback in web development.
  6. Prove the combined flow, then preserve desktop behavior. Run focused unit tests first, Rust attachment and ownership tests second, browser acceptance tests third, and the full overhaul gate last. Only after the browser flow passes should the old structural test be changed from "no WebSocket transport" to "only the registered PTY route exists."

Acceptance criteria

  • Browser launch. In a browser development session, the Details action sends the approved GraphQL launch operation. No Tauri invoke is required. The isolated launch runtime has a live MCP endpoint and hook runner. A launch error reaches the UI with the same actionable error shape used by desktop launch.
  • Existing agent visibility. On project selection, the browser opens the current GraphQL status subscription through /graphql/subscribe. The initial snapshot contains already persisted runs, a new launch produces the expected status event, and unsubscribe cancels the SSE reader. The implementation does not add a status WebSocket or change the subscription protocol.
  • Terminal attachment. The browser opens the configured PTY WebSocket, sends a valid attach frame, receives one ready frame, and renders binary output. A missing, ended, malformed, or unauthorized run closes with a stable error and does not leave a lease or attachment behind.
  • Terminal interaction. Keyboard bytes arrive at tmux, resize changes the PTY geometry, and scroll changes copy-mode history. Binary output is not decoded as JSON. Text control frames are bounded and invalid controls do not panic the adapter.
  • Durability and ownership. Closing the browser viewer releases the lease and detaches the viewer while the hosted tmux process remains alive. A second viewer replaces the first, the first receives the replacement outcome, and a stale renewal or release cannot affect the new lease.
  • Recovery. A transient socket close reconnects with the last geometry and emits a resumed event after ready. Reconnect attempts use a cap and jitter. A session-not-found, lease replacement, or exhausted retry budget moves the client to reattachment_required and disables input.
  • Desktop non-regression. Tauri still selects the native client, native viewer ownership and output activity tests pass, and desktop launch, terminal restoration, detach, and close behavior remain unchanged. The browser route must not be reachable through the Tauri command surface.

Observability and diagnostics

Web development already captures the Rust adapter and frontend child-process output in .ticketry-dev/logs/ticketry.log. Use npm run logs:clear before a reproduction, npm run logs:follow while opening and closing a terminal, and npm run logs for the retained tail. The route should log structured, non-secret boundary facts: connection outcome, run id, viewer id, transport, close code, normalized failure code, bytes or frames rejected by a limit, lease acquire or renew failure, and cleanup result. Never log keyboard bytes, terminal output, prompts, authorization headers, or full GraphQL variables. Browser-side state should expose the existing terminal failure layer and reattachment reason so support can distinguish transport, PTY, tmux, session, renderer, and control-plane failures.

For a failed browser run, capture the frontend URL and adapter port, the exact launch and attach timestamps, the run id, the WebSocket close code and reason, and the relevant log slice. Confirm the SSE status stream separately with the browser network panel or the existing status-stream test. Confirm tmux durability with the isolated tmux harness rather than by attaching to a product session manually.

Security and failure cases

  • Bind the development adapter to 127.0.0.1. Do not expose a wildcard listener or add an externally documented terminal API.
  • Validate run identifiers, geometry, control names, scroll counts, frame types, and frame sizes before invoking tmux. Clamp geometry through the existing terminal boundary and use its input limit.
  • Require a durable run and its existing authorization checks before attachment. Do not accept a client-supplied project, task, or tmux session name as authority for attach mode.
  • Use a fresh viewer id per socket and the exact lease generation for renewal and release. A stale socket must not detach a replacement viewer or terminate a hosted run.
  • On malformed init, unknown run, ended session, too many sessions, tmux failure, PTY read failure, output backpressure, or input pressure, send a stable error frame and close. Do not return database paths, SQL, stack traces, prompts, or raw tmux errors to the browser.
  • Bound concurrent browser sockets and output send time. A slow browser must not accumulate unbounded input or output in memory, and an adapter task must not outlive its socket.
  • Ensure the WebSocket route cannot be mistaken for GraphQL subscription traffic. /graphql/subscribe remains POST plus text/event-stream; the PTY route has its own path, handler, and tests.

Rollout and rollback

Roll out behind the existing browser development path first. Run the isolated temporary SQLite and tmux profile, then a product snapshot, then desktop smoke tests. Keep the browser client behind a single runtime-selection seam so a failed browser transport can be disabled by selecting the unavailable client or by removing the development WebSocket route without touching Tauri commands, terminal persistence, or SSE status delivery.

Rollback means reverting the adapter route, browser runtime URL, browser client selection, launch caller change, and Vite WebSocket entry as one change set. The existing desktop Tauri client and GraphQL SSE status path remain the fallback. Before rollback, close active browser sockets if possible and verify that leases are released; do not delete durable agent runs or tmux sessions merely because the viewer transport was rolled back.

Open decisions before implementation

  • Confirm the canonical browser path name, for example /ws/terminal, and whether the GraphQL endpoint may be an absolute URL with a separate WebSocket origin.
  • Confirm whether browser attach is the only supported WebSocket mode for this slice. The Rusty spawn frame contains more launch fields, but the narrow Ticketry plan should prefer GraphQL launch followed by attach unless product behavior explicitly requires spawn-over-socket.
  • Choose the adapter-side concurrency limit and output-pressure timeout, then make both values constants covered by tests.
  • Choose whether browser reconnection reuses the same viewer id or creates a new viewer id. The safer default is a new id with exact lease replacement and an explicit resumed event.
  • Confirm the desired UI treatment for reattachment_required: preserve scrollback and show a retry affordance, while preventing input until a fresh attach succeeds.
  • Run the launch parity test and decide whether terminal_session_create is sufficient. A new launch_default_coding_agent mutation is allowed only if that test records a concrete behavior gap.
  • Choose how web development locates the hook runner and reserves its isolated MCP port. Both values must come from validated startup configuration, not browser input.
  • Decide whether the browser acceptance test runs against an in-process route fixture or a spawned ticketry_graphql_adapter. The latter is closer to the web workflow; the former is faster for frame and cleanup cases.

Out of scope

  • Changing GraphQL status subscriptions from SSE to WebSocket, adding a status WebSocket, or changing cursor and snapshot semantics.
  • Adding a product REST API, terminal REST endpoints, an external compatibility contract, or a second backend.
  • Replacing Seaography GraphQL CRUD, launch authority, run persistence, terminal lifecycle reconciliation, viewer ownership, tmux naming, or the native Tauri viewer.
  • Rewriting the PTY or tmux implementation, introducing a new terminal store, changing xterm presentation, or moving durable sessions into the browser.
  • Porting Rusty's broader runtime, event system, provider system, durable event bus, or document-chat launch model.
  • Changing desktop launch semantics, desktop status delivery, native lease behavior, or the existing SSE development adapter beyond route registration needed to host the PTY socket.
  • Deploying the adapter as a public service, adding authentication beyond the existing local development boundary, or supporting cross-origin production browser clients.
