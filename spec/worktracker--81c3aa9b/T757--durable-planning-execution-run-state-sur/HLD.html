Durable Planning / Execution Run-State

Move engine run-state out of a process-local dict into a durable table so the planning_run_already_running guard tells the truth across an ASGI restart — no duplicate agent launches, no silent loss of a live run. Terminal transitions are agent-reported or manually released; the server never infers that a run died.
Follow-on to A/B · CODIN-700 family Durable EngineRun table Guard reads DB · survives restart No liveness inference failed = manual release only

Scope

Persist the engine's run-state (today a process-local dict) so the guard is truthful across restarts. Storage + guard-derivation only — no death detection, no phase re-invention.

Build

  • NEW durable EngineRun table — one row per task_id mirroring today's EngineState: task_id (PK), project_id, module_id, agent, phase, status, agent_run_id, error, updated_at. The task_id PK IS the guard — a unique row per task enforces one-run-per-task at the DB layer.
  • NEW GraphRun header table — one row per root_id (root_id (PK), project_id, module_id, agent). Graph nodes are the EngineRun rows across the subtree; graph edges stay derived from blocked_by (never stored).
  • Retarget driver.py _store/_store_graph/get_state/get_graph to read/write the tables; the in-memory _registry/_graph_registry become an OPTIONAL cache, never source of truth.
  • Rewire the planning_run_already_running 409 in create_planning_run to read the durable row.
  • Persist exactly the transitions written today: idle→running (spawn success), →failed (spawn FAILURE at launch), →done (agent-reported via the observe_issue_state_changed seam), graph halted-propagation recomputed on read.

Do NOT build

  • NO passive liveness / death detection, NO timeout, NO boot sweep that INFERS a run died — explicitly rejected: the agent lifecycle markers are unreliable, so inference would falsely declare live runs dead or miss dead ones.
  • NO agent-facing "report failure" MCP tool — a failed/abandoned run is cleared ONLY by the manual release hatch (subtask A / CODIN-755).
  • NO dependency on CODIN-756 (auto-release on death) — passive death-detection is deemed unreliable; #757 does not lean on it.
  • NO new phase semantics — phase mirrors #744's lifecycle_state; do not invent states.
  • NO cross-process message bus / IPC — the durable table already makes state shareable; sharing is a consequence, not a feature to build.

Problem

One root cause — the "which run is driving this task" binding lives only in a process-local dict — makes the guard lie in BOTH directions. Key fact: agents run in detached tmux and SURVIVE the ASGI restart; only the server's memory of them dies.

False negative → duplicate launch (scenario B)

  • 1. Refine agent launched; _registry[task]=running.
  • 2. ASGI process restarts. tmux agent keeps running.
  • 3. _registry is empty → guard says "free".
  • 4. Second POST /planning-run → NO 409 → a SECOND agent launches beside the orphaned first. Two agents race.

False positive → wedged (scenario A)

  • 1. Refine agent dies in tmux without moving the ticket.
  • 2. _registry[task] stays running forever.
  • 3. Every POST /planning-run → 409.
  • 4. Can never launch again — wedged. (Near-term band-aids: A/#755 manual release, B/#756.)

The durable table fixes the false-negative outright (guard survives restart). The false-positive is deliberately NOT auto-healed — see State flow / Restart.

Read / write surface

The seams that change. All narrow; no new public HTTP/MCP surface.
  • driver._store/_store_graph — write-through to EngineRun/GraphRun (was: dict assignment).
  • driver.get_state/get_graph — read the row (fall back to / refresh the cache).
  • api.create_planning_run — the 409 guard reads the durable row instead of _registry.
  • api.get_execute_graph (GET) — rebuilds from durable rows; a 404 now means "never launched", not "process restarted".
  • Manual release (subtask A / #755) — retargeted to clear the durable row (the lock is now a DB row, not a dict entry).

Test plan

The regression that matters: the guard must survive a simulated restart.
  • Guard survives restart: seed a running row, CLEAR the in-memory cache (simulating restart), POST /planning-run → still 409. No duplicate launch.
  • Fresh process, no row → POST /planning-run → launches (no false 409).
  • Agent completion via seam persists: observe_issue_state_changed → row flips to done durably.
  • Spawn failure at launch persists: row = failed with error.
  • Manual release clears the durable row → next POST launches.
  • task_id uniqueness: a second concurrent execute() for the same task cannot create a second running row.
  • Graph re-seed is lossless: GraphRun + rows reconstruct nodes incl. agent + error after cache clear.
  • NEGATIVE guard: no code path flips running→failed on a timeout or a dead marker (assert absence / no such branch).

Open questions — resolved

Does #757 need anything beyond #744?

Yes. #744 makes the PHASE durable (lifecycle_state) but not the run↔AgentRun binding, the error reason, or the guard rewire. Worse, durable phase turns a transient wedge into a permanent one — so #757's reconciliation-by-manual-release + guard-from-DB is what makes #744 safe.

New table, or derive everything from #744 + AgentRun?

New table. AgentRun rows carry no kind/purpose, so "the planning run for this task" isn't cleanly queryable, and AgentRun liveness is untrusted. Store the binding.

Auto-reconcile stuck running rows by liveness?

No. Markers unreliable; never infer death.

Reliable death signal source?

Only the agent reporting terminal state via MCP (today: completion via state move). Genuine crashes → manual release (A).

Failure path — agent MCP report or manual?

Manual release hatch (A / #755) only.

Depend on #756?

No.

Graph durability in scope?

Yes; assume re-seed lossy; persist it.

Acceptance signal

Green signal: Across an ASGI restart, a live planning run's planning_run_already_running guard still fires (no duplicate agent launched) and a legitimately-running row is not lost. A run becomes failed only from a launch-time spawn error or the manual release hatch — never by server inference. execute-graph rebuilds losslessly from durable rows. #744's lifecycle_state axis is untouched. No boot sweep, no death-detection code exists.
