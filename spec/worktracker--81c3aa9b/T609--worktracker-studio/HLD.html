Why split it out

Today one shell carries two jobs. New tracker features have nowhere natural to live.

The problem

The coding app (web/frontend) overloads work-tracking (modules, tasks, sprints, planning) onto an execution-first shell (per-task terminals, agent runs, worktrees). Both pivot on the same selectedTaskId and converge in one right pane (TicketWorkspace). A backlog or story-map view has nowhere to go without fighting the terminal layout.

The move

Build a purpose-made issue tracker as its own frontend folder inside worktracker-stack, talking to the worktracker django-ninja API over HTTP. The coding app stays where you execute; Studio is where you plan and track. They link, they don't merge.

📋 Backlog — flat, filterable list of issues
Grouped/sortable list across a project or epic. Inline create, quick state & priority edit, parent reassignment. API: GET /work-items (filter by parent/state), POST /work-items, PATCH /work-items/{id}. ready
🗂️ Board — columns by state group
Kanban across the five state groups; drag a card to change state. API: GET /projects/{id}/states + GET /work-items, drag → PATCH /work-items {state_id}. ready
🗺️ Story Map — epics as columns, stories beneath
User-story-map: epics across the top (backbone), stories in vertical lanes, optional sprint swimlanes. Overlaps with the deferred #603 (sprint planning map) — Studio is the natural home for it. API: GET /modules, GET /modules/{id}/work-items (subtree walk). ready
🏃 Sprints — plan & track iterations
Create sprints, see progress (done/open/total), assign issues. Now/Later/History framing (#604) lives here. API: full sprint CRUD + PATCH /work-items {sprint_id}. ready
📝 Issue detail — edit one work item
Name, description (HTML), state, priority, parent, sprint, assignees, labels, attachments. API: GET/PATCH /work-items/{id}, attachments endpoints. Assignee/label assignment exists in read shapes but has no management endpoint. partial
⚙️ Settings — projects, issue types, states
Manage projects, define issue types, configure workflow states. This is the view that exposes the real backend gaps. API: projects are read/seed-only; types don't exist; states aren't editable. needs backend

Open product decisions

Three forks that change scope. Recommendations marked — react to these and the breakdown firms up.

1 · Issue types & states — configurable or fixed for v1?

The hierarchy (Epic→Story→Sub-task) is free today via type+parent. But categorical issue types (Bug/Feature/Chore) don't exist, and states aren't editable. Making both configurable is real backend work (new field/migration for types; new routes for state CRUD).

Recommend: v1 fixed — ship a working tracker on the existing model (Epic/Story/Sub-task + the 5 state groups). File "configurable types & states" as a fast-follow phase.

2 · Relationship to the coding app

Studio is standalone, but issues still get executed somewhere. Do we (a) just deep-link from an issue out to the coding app, (b) ignore execution entirely in v1, or (c) embed a thin "open in coding app" affordance?

Recommend: (a) per-issue link-out seam only — no terminal/agent concepts in Studio.

3 · Tech stack & how it's served

New folder in worktracker-stack needs a stack + serve story. Options: reuse the coding app's React/Vite/Zustand conventions (familiar, copy-paste-able patterns) vs. a fresh choice; served standalone (its own dev server/port) vs. mounted by Django static like the coding app.

Recommend: match the existing React + Vite + Zustand conventions; standalone dev server hitting the API over HTTP; decide static-serving at build time.

S4Story Map + Sprint planning
Epics-as-columns map and sprint plan/track. Absorbs the deferred #603 and the #604 Now/Later/History framing into their natural home.
S5Backend: project + module mutation routes
Create/rename/archive projects; rename/delete modules. Small additive routes to make Settings real.
S6Backend: configurable issue types & states (deferred)
Only if decision #1 goes "configurable." New type/category field + migration; state CRUD routes. Explicitly fast-follow, not v1.
