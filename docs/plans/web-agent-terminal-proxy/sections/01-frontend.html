Frontend and browser PTY map

This section covers the Studio-side changes for a browser terminal. It does not move the native renderer, replace the terminal pool, or turn GraphQL subscriptions into a socket transport. Agent status remains a GraphQL subscription over the existing streaming HTTP endpoint. The terminal's input and output use one dedicated WebSocket.

The Rust create service discards caller-supplied launch material and resolves policy through its interactive authority. Prefer this existing model-shaped create seam. Add a named launch operation only if a focused parity test proves that the desktop decision-recording behavior cannot enter through terminal_session_create.

Browser data flow

Run agent button
  -> LaunchAgentAction
  -> launchDefaultAgent(issueId)
  -> existing terminal_session_create mutation over /graphql
  -> Rust launch policy + durable terminal session
  -> status subscription over /graphql/subscribe updates session state
  -> entryPool.ensureConnected(agentRunId)
  -> browserTerminalClient opens /ws/terminal
  -> ready frame binds the server session to pooled xterm
  -> binary output flows to xterm; xterm input flows back as binary

  Agent picker / shell paths already create their session through GraphQL.
  They enter the same entryPool and WebSocket attach path after creation.

The GraphQL create is the control-plane step. The WebSocket only attaches to the resulting durable run. It must not create a second run on an attach. The existing run_now operation should remain reserved for its Ideas-to-Implement workflow transition unless the product explicitly changes the Details button's meaning.

WebSocket URL contract

Use one URL accessor, rather than constructing a socket URL inside the terminal client. The browser runtime owns endpoint validation and origin conversion.

Configured GraphQL endpointTerminal URLWhy
/graphql/ws/terminalSame-origin browser URL, handled by the Vite development proxy.
http://127.0.0.1:8790/graphqlws://127.0.0.1:8790/ws/terminalAbsolute development adapter origin.
https://host.example/graphqlwss://host.example/ws/terminalPreserves TLS for a deployed browser adapter.

The adapter must register /ws/terminal on the same origin that serves /graphql. The browser client should fail configuration early for unsupported URL schemes, just as the current GraphQL endpoint does.

Wire protocol to port and verify

DirectionFrameMeaning
Browser -> serverText JSON {"type":"init","mode":"attach","agent_run_id","cols","rows"}Attach the viewer to an existing durable run. Reuse this frame after every reconnect.
Server -> browserText JSON {"type":"ready","session_id","agent_run_id"}Confirms attachment and gives the server session identity used to rekey the pooled entry.
Browser -> serverBinary bytesKeyboard input. Apply a size limit on the server and surface pressure as a terminal client error.
Server -> browserBinary bytesPTY/tmux output, written directly to the pooled xterm.
Browser -> serverText JSON {"type":"resize","cols","rows"}Resize the attached PTY. Clamp geometry on the server.
Browser -> serverText JSON {"type":"scroll","dir":"up|down","lines"}Request tmux scrollback movement.
Server -> browserText JSON {"type":"error","message"}, followed by a close codeReports a stable attach, session, lease, or pressure failure.

Rusty's checked-in builder names the scroll field dir, while its checked-in Rust consumer deserializes direction. Ticketry should keep the established TypeScript and Python wire name, dir, and make the new Rust handler and contract tests agree. Do not accept both spellings.

Client lifecycle and failure behavior

  • On attach, emit connecting, open the URL, send the attach init on open, and emit ready only after a valid ready frame.
  • Set binaryType = "arraybuffer". Write only binary messages to xterm. Parse text as JSON and classify malformed or unknown frames as protocol errors.
  • Guard input, resize, and scroll sends with readyState === WebSocket.OPEN. A stale xterm callback must not throw after the socket closes.
  • On an unclean close after a successful ready, retry the same run with bounded exponential backoff. Rusty's policy is eight attempts, a 500 ms base, a factor of two, a 10 second cap, and small jitter. Reset the attempt counter after a new ready frame.
  • Do not reconnect after an intentional detach. A clean viewer close emits eof and closed with viewer_exit.
  • Map session_not_found to reattachment_required with the session reason. Map lease replacement to the existing replacement reason. After retries are exhausted, emit the existing generic reattachment-required path so entryPool can mark the session lost.
  • Keep suspend and resume separate from run termination. Suspend closes the transient viewer, and resume opens a fresh attach while preserving xterm scrollback.

entryPool.ts already translates these events into xterm notices and session-store transitions, including reconnect banners, session-lost state, and ownership replacement. The browser client should fit that contract rather than adding a second state machine in React.

Files deliberately left alone

  • studio/src/features/agents/terminal/internal/terminalClient.ts. Its platform-neutral contract already covers the browser adapter.
  • studio/src/features/agents/terminal/internal/entryPool.ts, xterm presentation, session store, terminal ownership, and retained viewer code. They already consume the client contract and own the single pooled viewer.
  • tauriTerminalClient.ts, native Ghostty components, and the Tauri viewer commands. Native desktop remains the native path.
  • statusStreamClient.ts, statusStreamFeed.ts, GraphQL status operations, and the browser SSE reader. Status and PTY traffic have different lifecycles.
  • REST terminal routes, REST compatibility clients, a status WebSocket, or a second browser API. None is needed for this feature.

Implementation boundary

The frontend work is complete when a browser can launch or discover a durable run through GraphQL, attach one pooled xterm through /ws/terminal, exchange PTY bytes, and recover from a transient socket close. It is not complete if it merely makes the socket connect while the launch button still rejects browsers. It is also not complete if it changes status subscriptions, native rendering, terminal persistence, or the broader application runtime.
