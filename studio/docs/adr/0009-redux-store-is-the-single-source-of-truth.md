# The Redux store is the single source of truth, and the invariant is enforced by tests

Studio's state layer is rebuilt on Redux Toolkit: records live in entity slices, membership and ordering live in list slices (`moduleTree`, `sections`), RTK Query is used for request lifecycle only and never as a data source, and the status feed and mutations are writers into the same store. zustand (18 stores, 6,530 lines) and TanStack Query both leave. We got here from a one-line bug — a renamed Story kept its old name in the Stories pane — which traced to a work item's `name` being stored in six places, three of which a rename refreshed; the Stories pane read a lossy `TaskSummary` copy in `["tasks",pid,mid]` that the edit path never touched, and `issueStore` held no reference to `tasksStore` at all. State edits only *appeared* correct because the status feed reconciles committed workflow-state moves into the tree and nothing else. ADR-0006 declared this same problem solved and `TaskSummary` deleted; both claims were false when this was written, and `CONTEXT.md`'s assertion that a record "can never exist in two places and disagree with itself" was false with it — which is the real reason for this ADR. Two overhauls had each introduced a correct mechanism and left the previous lineage alive behind a compatibility shim, so **the decision that matters here is not the library but the enforcement**: a store-wide uniqueness test (rename, then walk the serialised store and assert the old value appears zero times), an endpoint-shape test asserting no RTK Query cache entry holds record objects, and a type-level prohibition on record types outside the entities slice. Prose invariants had already failed twice; they have no mechanism of action. We considered and rejected: a normalizing GraphQL client, which diagnoses the problem correctly but needs a second API surface kept consistent with the REST one the MCP path uses; `normy`, which auto-syncs the copies but keeps them, cannot move rows between lists, and ignores `state_revision`; and the orthodox split (React Query owns server state, Redux owns client state, derive rather than copy), which was agreed mid-decision and costed at roughly 2,500 lines deleted versus 8,500 rewritten, then declined in favour of one inspectable store and independence from invalidation fan-out — recorded because it is the most reasonable thing a future reader will propose. Optimistic writes and `state_revision` ordering survive as one implementation at the entity-upsert choke point, replacing today's duplicated pair across `issueStore` and `tasksStore`; multi-writer convergence is real regardless of latency, because agents write through MCP while a user edits. Full reasoning, measurements and rejected alternatives: [`docs/decisions/2026-08-04-frontend-state-and-api-contract.md`](../../../docs/decisions/2026-08-04-frontend-state-and-api-contract.md).
