After — one deep module

Session  ·  spawn(intent) · terminate(run_id) · live_run_for(task_id) · sessions_for(task_id) · reconcile()

profile + prompt + worktree (#587)
AgentRun row + status flip on exit
tmux create / kill / reconcile
doc watcher start / stop — symmetric

internals invisible to callers · in-memory adapter satisfies the same interface

Problem: launch, liveness, and teardown each enter a different door, so the lifecycle invariants (watcher stops when tmux dies; AgentRun.status reflects reality) live nowhere and are silently violated.

Solution: a deep Session module whose implementation owns profile resolution, worktree rooting, the AgentRun row, tmux, and the watcher — spawn and terminate become symmetric by construction.

Two live defects this fixes (found in review, stronger than the ticket states):

· AgentRun.status is never flipped off "running" by any production path — update_agent_run_exit has zero non-test callers. Terminated runs look live forever.

· reconcile_sessions reaps tmux but never stops doc watchers; its docstring defers to a "run-reconciler" that does not exist.

  • Locality: lifecycle invariants in one module
  • Leverage: 3 callers, one interface
  • Interface is the test surface
  • Two adapters justify the seam: tmux + in-memory fake

Solution: WS calls Session.spawn and keeps only what is genuinely WS-shaped — viewer-PTY attach, resize, the byte pump — outside the seam.

Problem: the execution driver decides "already running → don't relaunch" from a raw filter over a status field nothing maintains; correctness depends on an invariant no module owns.

Solution: live_run_for / sessions_for on the Session interface; the implementation keeps status truthful (terminate and reconcile flip it), so the answer is trustworthy and fakeable in tests.

Scope correction to the ticket: validate_worktracker_refs.py:94 is a referential-integrity scan over all runs, not a liveness query — it does not belong behind live_run_for. Propose dropping it from this deepening.
  • Leverage: one liveness answer, N callers
  • In-memory adapter → driver tests need no DB
  • GET list stops hiding a reap write

Top recommendation

Candidate 1 — the Session facade, with candidate 4's seam-placement decision made first

The facade is where the depth is: it fixes two live defects (eternal "running" status, leaked watchers) as a by-product of making spawn/terminate symmetric, and candidates 2 and 3 fall out of it almost mechanically. But its interface shape depends on who the callers are — so settle candidate 4 (does the orchestrator import Session directly, or reach it through the execution seam?) before freezing the interface.
