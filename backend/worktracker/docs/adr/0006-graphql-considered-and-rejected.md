# GraphQL was considered for the work-management surface and rejected

We evaluated putting GraphQL over the worktracker domain — Strawberry or Graphene on Django, Apollo Client or urql `graphcache` in Studio — and decided against it, for reasons that are worth recording because the diagnosis behind the idea was *correct* and it will be proposed again. The problem it was meant to solve is real: a normalizing client cache keys every object by `__typename:id`, so a mutation's returned entity updates every query result that references it, and a second copy of a record becomes impossible to hold rather than merely forbidden by convention. That is exactly the property whose absence produced the Studio rename bug, where a work item's `name` lived in six places. It was rejected on cost and timing, not merit. There is no GraphQL anywhere in this repository, and adding it means a second API surface over one domain that must stay permanently consistent with the REST surface — which cannot be deleted, because `surfaces/worktracker-agent` (the MCP server) and both generated SDKs consume it. The backend it would be built on is also slated for replacement by `WORKTRACKER_RUST_LLD.md`, so the schema and resolver layer would be throwaway work; and it would arrive immediately after a migration of Studio's server state into TanStack Query, discarding that. Worth knowing for whoever revisits this: the backend is well layered for it — `worktracker/api/*` is ~900 lines of thin HTTP delegating to ~1,900 lines of services, so resolvers would call the same service functions and models, migrations, services and the 18,578-line test suite would be untouched. The real work would be a type layer (~the scale of `schemas.py`), thin resolvers, translating the workflow gate's structured rejection (`detail`/`code`/`from`/`to`, which the Studio client depends on) into GraphQL errors, and its own auth, since `ApiKeyAuth` is applied at the ninja router level and a GraphQL view would not inherit it. On the Rust side `async-graphql` is mature and `seaography` generates a schema directly from SeaORM entities, which is model-derived in exactly the way we want — so **if GraphQL returns, it belongs on the new backend, not bolted onto this one.** Instead we adopted DRF for model-shaped CRUD with a declared route registry (ADR-0005) and rebuilt Studio's state layer with an enforced single-copy invariant (studio ADR-0009). Full reasoning: [`docs/decisions/2026-08-04-frontend-state-and-api-contract.md`](../../../../docs/decisions/2026-08-04-frontend-state-and-api-contract.md).
