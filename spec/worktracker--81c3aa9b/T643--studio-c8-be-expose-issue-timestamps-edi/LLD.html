The label write block

Drops in beside the blocked_by_ids replace-set, after issue.save() (M2M edits need a persisted row). The one non-obvious detail: Label.id is a UUIDField(primary_key=True) with no default, so the create branch must mint the pk via defaults.

# api.py — patch_work_item, after issue.save() and the blocked_by_ids block (:640)
    if "labels" in data:
        # Normalize: trim, drop empties, dedupe (preserve order), cap at 255.
        names, seen = [], set()
        for raw in (data["labels"] or []):
            name = (raw or "").strip()[:255]
            if name and name not in seen:
                seen.add(name)
                names.append(name)
        # Name-based get-or-create, project-scoped. Mint the pk on create
        # (Label.id has no default). color defaults "" → neutral chip.
        labels = [
            Label.objects.get_or_create(
                project=issue.project, name=name,
                defaults={"id": uuid.uuid4()},
            )[0]
            for name in names
        ]
        issue.labels.set(labels)            # replace-set; [] clears all

Match is (project, name), case-sensitive (Jira semantics — "Backend" ≠ "backend"). Reuse is automatic: the same name on another issue in the same project resolves to the same row, never a duplicate. Orphaned labels (zero issues after .set()) stay in the table — cheap, and they feed the FE autocomplete.

No DB-level uniqueness: Label has no unique_together("project","name") (unlike State, models.py:163–164), and adding one would need a migration this ticket forbids. get_or_create is get-then-create, so two truly-concurrent first-writes of the same name could mint two rows. For this single-tenant tracker that race is an accepted residual; a future ticket can add the constraint + dedupe migration if it ever bites.

Front-end deltas

One thin store action, one new picker, one drawer section rewrite. Chips key by name throughout — the only key consistent across optimistic and server state (decision 3: no id in the contract).

// issueStore.ts — patchLabels: optimistic + rollback for free via patchField
async patchLabels(names) {
  await get().patchField({ labels: names });   // reconciles open.task, rolls back on throw
}                                              // no reverse write-through (labels have no inverse edge)
// IssueDetail.tsx — editable Labels block replaces the read-only one (:363–376)
const names = task.labels.map((l) => l.name);
<Field label="Labels">
  <div className="flex flex-wrap justify-end gap-1">
    {task.labels.map((l) => (
      <LabelChip key={l.name} label={l}
        onRemove={() => void patchLabels(names.filter((n) => n !== l.name))} />
    ))}
    <LabelPicker currentNames={names} saving={Boolean(saving.labels)}
      onAdd={(name) => void patchLabels([...names, name])} />
  </div>
</Field>

// metadata row — read-only, absolute dates
<Field label="Created">{fmtDate(task.created_at)}</Field>
<Field label="Updated">{fmtDate(task.updated_at)}</Field>

LabelChip renders name on a tint from color (e.g. inline style when color is a hex, else the neutral bg-pane-title class the read-only chip used). The picker's suggestion list is computed from useBacklogStore().items.flatMap(i => i.labels.map(l => l.name)), de-duped, minus currentNames.

Optimistic gap: a freshly-typed name has no color until the patch returns, so its chip shows neutral for one round-trip, then re-tints from the server's (blank → still neutral) value. This is why chips key by name, not a server id that doesn't exist yet.

  • Typing a label name + Enter adds a chip and persists it; the same name on another issue in the project resolves to the same Label row — no duplicate.
  • PATCH { labels: [] } clears all labels; omitting labels leaves them untouched.
  • Names are trimmed, de-duplicated, empty-dropped, capped at 255, and matched case-sensitively ("Backend" ≠ "backend"); labels are project-scoped.
  • Chips render their color; blank-color (name-created) labels show a neutral chip.
