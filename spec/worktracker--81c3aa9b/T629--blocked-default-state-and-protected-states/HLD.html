Why

Two gaps, one ticket — both about the workflow-state set being too easy to lose and missing a common status.

1 · No “Blocked” status. Issues that are stuck have nowhere to sit. Today the only signal is the blocked_by relationship (#624) — an amber chip, not a board lane. Work that's parked reads as still “In Progress”.

2 · Critical states are deletable. The only delete guard is “can't remove the last state in a group” (api.py:872). The moment a group gains a second state, Done or In Progress can be deleted out from under the board and roll-ups that key off them.

Blocked = real state, not derived

Chosen over deriving it from blocked_by: a real state is a first-class board column users can set directly. It is independent of the relationship — an issue can be “In Progress” yet have a blocker, or “Blocked” with none. The two signals coexist.

Blocked is its own group

A new sixth blocked group — not folded into unstarted. A parked issue counts as neither not-started nor in-progress: it gets its own board lane and is excluded from both roll-ups, which is the honest signal for stuck work.

Acceptance signal

  • A freshly provisioned project shows six states across six groups; Blocked sits in its own blocked group after In Progress and renders as a board column.
  • DELETE /states/{id} on Done, In Progress, or Blocked returns 409 regardless of how many siblings the group has.
  • Deleting Backlog / Todo / Cancelled still works once its group has ≥2 states (existing behavior preserved).
  • Running the migration on an existing project adds Blocked and sets the three protected flags — re-running changes nothing.
  • Studio Settings shows no delete control on Done / In Progress / Blocked; StateOut.is_protected flows through the SDK.
  • GROUP_CHOICES gains blocked only; roll-ups exclude it; backend + SDK + Studio test suites green.
