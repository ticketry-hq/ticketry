The transition rule

Keyed on the transition (old group vs new group), not on a stored "why archived" flag — which is why it needs no field and no migration.

# api.py — patch_work_item (:549). Capture OLD group BEFORE any mutation.
def patch_work_item(request, issue_id, payload):
    issue = get_object_or_404(Issue, pk=issue_id)
    data  = payload.dict(exclude_unset=True)

    # Read the pre-patch group from the DB value still on `issue`.
    old_group = _state_group(issue.state_id)

    # ... existing field application (state_id, parent_id, sprint_id, ...) ...
    issue.save()
    # ... existing blocked_by replace-set ...

    # #633 — cancel↔archive coupling, on the state-change transition only.
    if "state_id" in data:
        new_group = _state_group(issue.state_id)
        if old_group != "cancelled" and new_group == "cancelled":
            _archive_subtree(issue.id)                 # self + descendants
        elif old_group == "cancelled" and new_group != "cancelled":
            Issue.objects.filter(pk=issue.id).update(is_archived=False)  # self only

    return _resolve_issue(str(issue.id))


def _state_group(state_id):
    # Resolve the group from the State table — do NOT trust issue.state, whose
    # cached relation is stale after we assign a new state_id.
    if not state_id:
        return None
    return State.objects.filter(pk=state_id).values_list("group", flat=True).first()

Two reads of _state_group bracket the save: the first uses the row's original state_id (old), the second uses the just-assigned one (new). Same-group edits (active→active, cancelled→cancelled) match neither branch, so is_archived is left untouched — the property that stops a manually-archived active item resurrecting on an unrelated state edit.

Why a State lookup, not issue.state.group: assigning issue.state_id = … does not refresh the cached issue.state relation, so reading .state.group after the assignment can return the old group. A scalar values_list query on State is unambiguous and cheap.

Cascade & its asymmetry

Cancelling a parent archives the whole subtree; un-cancelling restores only the issue itself.

def _archive_subtree(root_id):
    """Archive `root_id` and every descendant (BFS down the parent tree)."""
    seen, frontier = set(), [root_id]
    while frontier:
        seen.update(frontier)
        frontier = [
            i for i in Issue.objects.filter(parent_id__in=frontier)
                                       .values_list("id", flat=True)
            if i not in seen          # guard a malformed parent cycle
        ]
    Issue.objects.filter(id__in=seen).update(is_archived=True)

One bulk UPDATE over the collected id set — no per-row save. BFS over parent_id__in walks epic→stories→sub-tasks; the seen set bounds it against a malformed cycle.

DOWN — on cancel

Whole subtree archived

An epic's stories and their sub-tasks all get is_archived=True in one statement, so no child is left orphaned in the backlog tree or story map.

UP — on un-cancel

Self only (intentional)

Restoring the parent does not auto-restore children — we can't know which were independently cancelled. Children are restored individually if ever needed. This is the documented asymmetry.

Bulk-update note: .update() bypasses Model.save(), so it won't bump updated_at for cascaded descendants. Acceptable — archive state, not edit recency, is what matters here. The root's own updated_at already moved on its issue.save().

// backlogStore.ts — applyServerItem (:685)
applyServerItem(item) {
  const items = get().items;
  if (item.is_archived) {                              // #633
    set({ items: items.filter((i) => i.id !== item.id) });
    return;
  }
  const exists = items.some((i) => i.id === item.id);
  set({ items: exists ? items.map((i) => (i.id === item.id ? item : i)) : [...items, item] });
}

Acceptance

  • Moving an issue to a cancelled-group state removes it from board, backlog, story map, and sprint rows; the open board updates without a manual reload.
  • Cancelling a parent archives its whole subtree — no orphaned children anywhere.
  • Moving an issue back to an active state restores it (self only) at its prior rank; the deep-linked drawer reloads the project so views repopulate.
  • The Cancelled column no longer renders on the board; Cancelled stays selectable in the detail picker.
  • An epic whose only remaining children are cancelled shows no expand arrow in the main app (sub_issues_count excludes archived).
  • No new model field and no migration — the rule keys on the state transition alone.
  • Backend + Studio suites green, with new tests covering each transition, the cascade, and the filtered child_count.
