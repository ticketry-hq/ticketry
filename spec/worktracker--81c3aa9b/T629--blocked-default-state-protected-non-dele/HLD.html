WorkTracker · worktracker-stack · Ticket #629 · HLD

Blocked Default State + Protected (non-deletable) States

Two small, paired changes to the seeded workflow: ship a sixth default state — Blocked — and make the three states the data model relies on (In Progress, Done, Blocked) impossible to delete. Protection is a per-row, server-owned, read-only flag; everything else about states (rename, recolor, reorder, group-move) stays exactly as it is.

What changes for a fresh project

Every new project seeds its workflow states from one frozen list. Today that's five, all freely deletable. After this change it's six, with three carrying a durable lock 🔒 that the DELETE route honors. The lock lives on the row, not the name — rename "Done" to "Shipped" and it stays protected.

Locked scope — three pillars

Click a pillar to expand what's in and what's explicitly out. The whole ticket is intentionally narrow: a seed addition, a flag, and one guard.
PILLAR 1 · SEED

Blocked is a seeded default

Added to DEFAULT_STATES after Todo, group unstarted. Seeded by all three writers: project-create, provision, and the backfill migration.

  • One source of truth: DEFAULT_STATES + a PROTECTED_STATE_KEYS set of (name, group)
  • Ordering via ensure_state_order so Blocked renumbers in right after Todo
  • Idempotent: get_or_create(name="Blocked", group="unstarted") stamps, never duplicates
  • Not configurable per-project at seed time — it's a default, like the other five
PILLAR 2 · FLAG

is_protected — read-only, server-owned

A new boolean column on State. Seeded true for the three critical (name, group) pairs. The flag, not the name, gates DELETE — durable through rename/recolor.

  • Surfaces in StateOut and the SDK State and the Studio State type
  • User-created states are always is_protected=False
  • Never in StateIn / StatePatch — clients can't set or clear it
  • No retro-stamp of a user-renamed Done/In Progress on existing projects (matches by seeded name within group)
PILLAR 3 · GUARD

DELETE-only protection

One new check at the top of delete_state: protected → 409, regardless of sibling count or usage. Every other state op is untouched.

  • DELETE on Done / In Progress / Blocked → 409 always
  • Studio hides/disables the ✕ on protected rows with a tooltip
  • Rename, recolor, reorder, and group-move stay allowed for protected states (open question closed)
  • No change to patch_state, create_state, reorder_states

Question board

Green = resolved in the 2026-06-21 refinement. Amber = an implementation-time caveat the LLD must carry, not a design hole.
RESOLVED · group-move

Can a protected state move between groups?

Yes — protection is DELETE-only. Rename, recolor, reorder, and group-move all stay allowed. Keeps scope tight and matches the ticket default.

D3 · D4
RESOLVED · identity

What makes a state protected — name or flag?

A durable per-row flag, seeded by matching (name, group) once. After that the flag — not the name — gates DELETE, so a renamed Done stays locked.

RESOLVED · existing projects

What about already-provisioned projects?

The migration backfills both: adds Blocked (get_or_create) and stamps is_protected on the seeded Done/In Progress/Blocked. A user-renamed Done is not retro-stamped — acceptable.

CAVEAT · stale SDK

Why might self-host tests still fail after this?

A stale pip-installed SDK can lag the in-repo SDK until reinstalled — a known pre-existing env caveat, not introduced here. Reinstall the SDK when validating.

CAVEAT · one source of truth

Where does create_project get the flag?

LLD picks one of two: (a) stamp is_protected inline in the bulk_create from PROTECTED_STATE_KEYS, or (b) a shared ensure_protected_states helper in seed.py called by all three writers. Either keeps the seed single-sourced.

Acceptance signal

The change is done when a fresh project seeds six states — Blocked sitting in unstarted right after Todo — with In Progress, Done, and Blocked carrying is_protected=true; a DELETE on any of the three returns 409 regardless of sibling count, while Backlog / Todo / Cancelled stay deletable once their group has a spare; StateOut, the SDK, and Studio all carry the read-only flag with no write path accepting it; Studio hides the delete control on protected rows; and the backfill migration adds Blocked and stamps the three flags on an existing five-state project, with a re-run a clean no-op.
