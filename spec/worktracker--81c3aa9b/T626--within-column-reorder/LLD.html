The rank model — one global key, sorted per column

There is a single rank per issue. Each column sorts only its own members by it, so two issues in different columns are never compared. Click a node to see why interleaved values are harmless. Worked numbers: column B = B1·100, B2·300; column A holds A1·200 — numerically between them, yet invisible in B.
Click a node.

How a new rank is computed — fractional indexing

On drop, the new rank is a key that sorts strictly between the moved card's two visible neighbors in the destination column. Only the moved row is written. Keys are sortable strings (LexoRank family); integers shown here for intuition.

Midpoint walk (column B: 100 … 300)

1drop between B1·100 and B2·300 → 200
2drop between 100 and 200 → 150
3between 100 and 150 → 125
4… 112 … 106 … each drop halves the gap
∞strings never structurally run out of midpoints; a rebalance re-spaces only when two adjacent keys leave no room

Why a sortable string, not a float

  • Top of column → key before the current first (neighbors = null, first).
  • Bottom → key after the current last (last, null).
  • Empty column → first key from null, null.
  • Dense insert → no key fits between two adjacent neighbors → server rebalances that sibling set (re-space evenly) in one transaction, then assigns.
  • Floats exhaust precision after ~50 stacked inserts at one spot; strings (base-62) push that far out and rebalance is rare and cheap.

API & schema contract

Rank algebra and rebalance live server-side — exactly like reorder_states / reorder_issue_types. The client sends intent (which neighbors), never a computed key.
NEW ENDPOINTPOST /api/work-items/{id}/reorder — body { before_id?: UUID, after_id?: UUID }. Server loads the two neighbors, computes key_between(before.rank, after.rank), writes it to the issue, returns the updated WorkItemOut. Either id may be null (top/bottom). 422 if before/after aren't adjacent siblings in the same column or belong to another project.
WorkItemOut (+1 field)rank: str added to the read shape so the client can sort and resolve neighbors. No other output field changes.
WorkItemPatchUnchanged — rank is not a free patch field. Reorder is the only write path, so neighbor-adjacency and rebalance can't be bypassed.
CROSS-COLUMN DROPTwo writes, client-sequenced: the existing patch (state_id for Kanban / sprint_id or epic for Story Map) then reorder with the destination neighbors — so the card lands where dropped, not at its stale rank.
LIST ORDERINGlist_work_items and list_module_work_items gain .order_by("rank", "sequence_id"). sequence_id is the stable tiebreak when two ranks ever collide across a group boundary.
MIGRATION 0006Add rank (indexed). Data migration backfills per project, per sibling group, in current visible order (sequence_id) with evenly spaced keys — nothing moves on first load.
