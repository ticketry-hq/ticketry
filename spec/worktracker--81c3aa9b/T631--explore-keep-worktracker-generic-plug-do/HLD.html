WorkTracker Studio · Ticket #631 · Exploration · HLD v1

Generic WorkTracker, Pluggable Domain Add-ons

Keep the work tracker domain-agnostic so it can run as-is for a non-coding project (meml), and let coding-specific features — the "needs you" agent badge today; launch-terminal, loops and a workflow builder next — plug in on top as a layer that core never imports. The boundary is drawn in the frontend first; the same split applies to the backend — a generic worktracker package the coding backend embeds (real FK to Issue, no cross-service UUID bridge), recorded here and carved into its own task later.

Three options, one chosen

The ticket framed coding as a permanent thin read-only seam. Exploration changed that premise: coding is an expanding domain layer (terminal launch, loops, workflow builder) that will want real estate inside Studio — which kills "status quo" and selects A.
C · STATUS QUO (today)
Sibling apps linked by issue UUID; the coding seam (badge, deep-link, poll) is imported directly by core files. Clean enough today, but every add-on re-wires by hand and core imports coding — the wrong direction.
⟶
B · BACKEND CUSTOM-FIELDS
JSON metadata / custom-field system on Issue so add-ons persist data in the tracker. Parked — coding stores its data in its own backend; nothing yet needs to write domain data into WorkTracker.
⟶
A · THIS DESIGN
Shared @worktracker/core + a slot registry. Core declares named extension points and renders whatever's registered; the coding layer registers into them and core never imports it. meml = core, nothing registered.

The boundary rule

One test decides which layer any current or future feature belongs to. It is provenance-based, not appearance-based.
THE TEST

A feature belongs to the coding layer if and only if it only exists because agents launch to do the work. Everything else belongs to core.

Worked example — the "needs you" badge looks like a generic status, but it only means anything because an agent is running and got stuck. Its provenance is agents → it is coding-layer, not core. (This is the user's own example, and it sets the precedent.)

What meml runs by itself, with nothing coding in sight.

Coding layer — registers on top

Loaded only by the coding app; absent from a meml build.
  • Agent lifecycle badge — "needs you" / "working" (today)
  • "Open in coding app" deep-link + the w shortcut (today)
  • Lifecycle polling service against the coding app's API (today)
  • Launch-a-terminal from an issue (next)
  • Loops dashboard, workflow builder (coming — whole pages)
  • All keyed by the shared Issue UUID; data lives in the coding backend

The plug surface — four slot kinds

Core's contract with an add-on is context in, UI out: core hands a spot a typed context (which issue, project, selection); the contribution brings its own data and renders. Four kinds, because "badge in a row" and "whole page" aren't the same thing. Click a card for the shape.
KIND 1 · REGIONS

Inject UI into a spot

An empty <Slot> core renders inline — backlog row, board card, drawer header, a stacked drawer panel. Nothing registered ⇒ renders nothing.

// core declares the spot — knows nothing of agents
<Slot id="issue-row.end" ctx={{ issue, projectId }} />

// coding fills it once, at startup
registerSlot("issue-row.end",
  (ctx) => <AgentStateBadge issueId={ctx.issue.id} />)
Today welded into BacklogList.tsx & IssueDrawerHost.tsx; becomes a registered region.
KIND 2 · ACTIONS

Commands, menus & keys

An entry that surfaces wherever commands do — context menu, ⌘K palette, keymap — filtered by when(ctx). One registration wires the menu item and the shortcut.

registerAction({
  id: "coding.launch-terminal",
  title: "Launch terminal here",
  when: (ctx) => !!ctx.issue,
  run:  (ctx) => codingApi.launch(ctx.issue.id),
  shortcut: "t",
})
Today's hardcoded useCodingAppShortcut.ts (w) collapses into one action.
KIND 3 · ROUTES + NAV

Whole pages

A route plus a nav entry. Core's router spreads in registered routes; the nav drawer lists registered items. meml has none ⇒ no link, no route exists.

registerRoute({
  path: "/workflows",
  element: <WorkflowBuilder />,
  nav: { label: "Workflows", section: "coding" },
})
This is what turns "decorate the tracker" into "host a whole section" — loops, workflow builder.
KIND 4 · SERVICES

Background work, no UI

A lifecycle hook core's shell drives on project change. The service polls its own backend and writes its own store — which a region slot reads. Core never touches agent data.

registerService({
  onProjectChange: (pid) => lifecycle.start(pid),
  dispose:          ()   => lifecycle.stop(),
})
Today's lifecycleStore.ts + StudioApp.tsx poll wiring becomes a registered service.

Why slots, not compound components

The conundrum: core must own the composition (so an upstream restyle of IssueDetail propagates everywhere — you never re-declare the arrangement), yet a consumer must extend parts without forking. This is a known React problem; the fit is slots / component-injection (MUI slots, Radix asChild), and the tempting alternatives are the wrong tool.
CHOSEN

Slots / component-injection

Core keeps the arrangement; the consumer swaps or fills named interior parts. Upstream restyle flows to both apps automatically; the consumer only touches the parts it registered. Exactly the requirement.

REJECTED

Compound components

<Issue><Issue.Header/>…</Issue> hands the arrangement to the consumer. Both apps would re-declare the composition, and an upstream layout change would not propagate. Loses the one thing we must keep.

REJECTED

Headless (logic-only)

TanStack-style: core ships behavior, each app writes its own markup. Maximal flexibility, but zero shared look — same propagation loss as compound, more work.

The one adaptation for a two-codebase split: MUI threads slots down as props, painful when a slot is buried deep in core. We back the same contract with a context-provided registry populated once at startup — so nothing is prop-threaded across the package boundary. Same pattern, cross-package form.

Build vs buy — the registry

The pattern splits into a low-level slot primitive and the cross-package registry. Verdict: depend on the primitive, hand-roll the small typed registry — the value is in our named slots and typed context, which no generic framework can supply.
OptionWhat it givesVerdict
@radix-ui/react-slotThe slot primitive — merge props onto a child, asChild. ~1KB, ubiquitous, likely already transitive.USE — for prop-merge / wrap-a-core-element cases. Not a registry on its own.
first-party registryMap<slotId, contribution[]> behind React context + register* + <Slot>. ~50–80 lines.BUILD — owns the typed context contract; the actual design work lives here.
react-pluggableA real plugin store: install features, render by name without imports.SKIP — heavier event-bus model, weaker typing of the context contract.
devnet-io/react-registryMinimal register/retrieve components by name.SKIP — right shape, small/unmaintained; not worth a dep over ~60 lines.
Module Federation + NxRuntime-loaded remote plugins, independent deploys.SKIP — for runtime remotes; we share a build-time npm package, not remotes.

Migration path

Incremental, so the tree never goes fully red and meml can come online before every coding feature is ported. This HLD scopes the direction; each step below becomes its own LLD + implementation ticket — no code in this phase.

Introduce the registry in core

Add <Slot> + register* + the typed context. No behavior change — nothing is registered yet, every slot renders null.

Move the existing seam onto slots

Re-home the badge, deep-link, w-key and lifecycle poll out of core call-sites into a coding integration that registers them. Core loses all coding imports; add the ESLint boundary rule (D8).

Split the codebase

Extract @worktracker/core as a package; today's studio/ becomes the coding app consuming core + the coding integration.

Stand up the meml app

A second consumer of core that registers nothing (or its own non-agent add-ons). This is the payoff — a clean tracker with no coding code present.

Grow the coding layer

Terminal launch, loops, workflow builder land as new register* calls — zero core edits. "Which layer?" becomes self-answering: core if it edits a core file, coding if it's just another registration.

Question board

Green = resolved in exploration. Red = genuinely open; none blocks adopting the direction — each is an LLD-time call.
RESOLVED · direction

A, B, or C?

A. Coding is a growing layer that renders inside Studio, so a slot registry is warranted; B (backend custom-fields) is parked; C (hand-wired siblings) doesn't scale.

RESOLVED · the line

Where does the boundary fall?

Agent-provenance test. Only-because-agents-launch ⇒ coding; everything else ⇒ core. Backend already sits on the right side.

OPEN · Q1

Is meml already a frontend?

Unknown — a started app vs a fresh consumer of core pointed at meml's backend changes the migration tail, not the boundary.

OPEN · Q2

Coding layer granularity?

One integrations/coding package, or independently toggleable features (tags / terminal / loops / workflows)? Lean: one package, internally modular.

RESOLVED → OWN TASK · Q3

Backend share form?

Same split as the frontend: share worktracker as a generic backend package the coding backend embeds. Agent rows then carry a real FK to Issue — no cross-service UUID bridge — and meml embeds the same package with nothing coding added. Implementation is its own follow-up task; this HLD only records the direction.

OPEN · Q4

Monorepo or published package?

Does @worktracker/core live in a monorepo (studio → packages/) or get published? Lean: monorepo workspace — both apps local for now.

Acceptance signal

The exploration is settled when this design is approved: the team agrees the line is the agent-provenance rule; that the whole tracker is shared as @worktracker/core with coding as a registered layer core never imports; that the surface is region / action / route / service slots driven by a first-party context-backed registry (+ Radix Slot), reached via the slots pattern, not compound components; that the backend stays generic (B parked); and that the migration runs in incremental steps ending with a meml app that renders the bare tracker with no coding code present. Implementing each step is follow-up ticket work — this phase ships the decision, not the refactor.
