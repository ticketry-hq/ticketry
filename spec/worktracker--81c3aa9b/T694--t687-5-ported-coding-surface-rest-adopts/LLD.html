SDK client wiring — the auth seam

Studio's studio/src/lib/api.ts builds its client from a static VITE_WT_API_KEY. The coding surface's key is per-profile and resolved asynchronously from configStore. So the coding surface gets its own client built on the same createWorkTrackerClient factory, with a custom fetch that injects the key per request.

The factory call

factorycreateWorkTrackerClient from @worktracker/typescript-sdk — the same export Studio uses.
baseUrl/api/work-tracker — the existing WORKTRACKER_BASE constant; the proxy already routes it.
apiKeyNot passed at construction — the key is dynamic. Left undefined so the SDK's built-in header injection is a no-op.
fetchA wrapper that, on every request, resolves the active profile's api_key and sets the x-api-key header before delegating to globalThis.fetch.
instanceA module-level singleton. The wrapper reads configStore at call time, so the singleton always tracks the current recentProfileIndex — no rebuild on profile switch.

Why a custom fetch, not apiKey

  • The key today comes from an async path — worktrackerHeaders() dynamically imports configStore and reads profiles[recentProfileIndex].api_key. createWorkTrackerClient's apiKey option is a sync string captured once.
  • The same auth logic moves verbatim into the fetch wrapper — no new behaviour, just relocated from worktrackerRequest.
  • The wrapper is exactly the SDK's documented extension point (options.fetch); the post/onError middleware that raises WorkTrackerApiError still runs.
  • No profile key → no header (same as today: worktrackerHeaders returns {}). The backend decides the 401/403; behaviour is identical.
Decision: the coding surface owns its client instance — it does not import Studio's module-level sdk() — because the two surfaces authenticate differently (env key vs. configStore profile). What is reused is the createWorkTrackerClient factory and the null-tightened type aliases from studio/src/lib/types.ts. This is the literal reading of the ticket's "reuse the createWorkTrackerClient wiring."

Boundary adapters — keep call sites frozen

The SDK returns the contract types (Project, WorkItem, Module, Sprint, State). The coding surface consumes its own narrower shapes (ProjectSummary, TaskSummary, …). The normalizers are the single translation layer; their inputs change to SDK types, their outputs stay identical, so tasksStore and every other consumer are untouched.

Adapters — what each one does

normalizeProjectInput type changes WorktrackerProject → Project. Body unchanged: {id, name, identifier: p.slug}. SDK Project has slug — confirmed.
normalizeModuleNew. Module → ModuleSummary: pick {id, name, project_id}. Replaces today's raw passthrough; SDK Module carries extra fields (key, sequence_id) the summary drops.
normalizeSprintNew. Sprint → SprintSummary: start_date/end_date/status are nullable/optional on the SDK type, coerced to "" defaults the coding UI expects.
normalizeTaskInput type changes WorktrackerTask → WorkItem. Body unchanged: spread + null-state fallback to the "No state" default. WorkItem's extra blocked_by_ids/blocks_ids are simply not surfaced.
directModuleTasksUnchanged: filters items where parent_id === moduleId, then normalizeTask. Operates on SDK WorkItem[] now.

Error mapping — preserve the throw contract

  • Today's request() throws the coding-local ApiError(status, message, body); call sites catch it and read .status / .body.
  • The SDK throws WorkTrackerApiError from its middleware. A thin call() wrapper (mirroring Studio's) catches it and re-throws the coding ApiError with the same fields.
  • The ApiError class stays exported from coding/lib/api.ts — it is part of the surface; only its producer changes.
  • AbortError passes through untouched (SDK onError re-throws it), so abortable call sites keep cancelling.
Type source: the migrated functions import the null-tightened aliases (Project, WorkItem, Module, Sprint, State, WorkItemPatch, WorkItemFilters, WorkItemDetail) from studio/src/lib/types.ts — the same aliases Studio's own api.ts uses — so the adapters get the exact shapes the normalizers expect. The coding types.ts output shapes are not edited.
