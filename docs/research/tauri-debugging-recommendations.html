Debugging Ticketry across the desktop stack

A source-backed review of open-source Tauri applications and the current Tauri 2 observability ecosystem. Research completed 1 September 2026.

Conclusion

Ticketry captures crashes and frontend console output reasonably well. Its main blind spot is the path between SQLite, GraphQL, Apollo's cache, and React rendering.

The launch configuration incident illustrates the gap. The row survived in SQLite, but the UI did not show it after restart. Existing logs could not tell us whether the read query omitted it, the GraphQL response contained it, Apollo normalized it incorrectly, or React filtered it.

The diagnostic path we want

  1. SQLite confirms the active profile and durable row identity.
  2. Rust tracing records the GraphQL operation and database transaction under one diagnostic_id.
  3. GraphQL tracing records resolver timing, selected fields, errors, and result count.
  4. WebView inspection confirms transport delivery and exposes browser exceptions.
  5. Apollo inspection shows watched-query variables, normalized identities, list membership, and eviction.
  6. React DevTools confirms whether the component received and rendered the record.

Every boundary should carry the same diagnostic ID. Log stable identifiers and metadata, not prompts, tokens, terminal output, authorization headers, or complete GraphQL payloads.

What other Tauri applications do

  • Spacedrive uses structured Rust tracing, module filters, and durable job IDs.
  • GitButler persists UI logs, uses a panic hook, provides opt-in debug and performance logs, opens Web Inspector in debug builds, and can archive logs.
  • Screenpipe documents persistent logs and concrete grep recipes. Its test guidance uses read-only SQLite checks.
  • Tolaria gates telemetry on user consent, disables default PII, and scrubs paths. Its React root reports caught and uncaught render failures.
  • Flow Desktop uses tracing and explicitly prohibits logging authentication, pairing, and encryption material.
  • Pake relies on Web Inspector during development, illustrating why DevTools are useful but insufficient for post-restart diagnosis.

Tools worth considering

  • tauri-plugin-log offers Rust and JavaScript logging, rotation, filtering, WebView forwarding, and custom formats. Ticketry should adopt it only if it can replace or feed the current sink cleanly.
  • React Developer Tools, including its standalone WebView mode, can prove whether component props and state received the record.
  • async-graphql OpenTelemetry and OpenTelemetry Rust are later options if local spans cannot explain cross-process behavior.
  • Sentry can collect panic and tracing information, but upload, privacy, and global-logger concerns make it a separate product decision.
