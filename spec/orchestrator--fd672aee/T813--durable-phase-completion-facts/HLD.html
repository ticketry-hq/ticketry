Durable Phase-Completion Facts — High-Level Design

Every phase finishes by reporting a durable act — never by a process exiting. Decompose gains an explicit completion tool, verify gains report_verdict, and both append facts to the same inbox the sidecar already feeds. Once completion is transport-independent, any phase can run attached (tmux, subscription-billed) or headless with identical semantics.

The agent ⇄ orchestrator completion interface

Three parts. The agent's obligation per phase is one tool call; the server's obligation is one durable append. Folding never happens in the tool handler — reconcile stays the only writer of run state (ADR-0003).
DATA · what crosses

A phase-completion fact

decompose_complete(run_id, node_id) and report_verdict(run_id, node_id, verdict, findings). The verdict payload is the same shape verdict.json carries today — the schema moves, not the contract. Implement keeps its existing act: the ticket-Done transition.

Tools append to the Fact inbox · nothing else
IDENTITY · who is calling

Injected, never inferred

The driver already threads AgentConfig into every launch; it gains run_id + node_id, surfaced to the agent in the rendered prompt. The tool handler validates the node is running in a non-terminal run and rejects everything else.

No "find my run" heuristics · explicit ids only
SAFETY · when the agent never calls

Exit is the backstop

Headless: sidecar completion file, as today. Attached: session hygiene notices a dead run-owned tmux session with no completion fact and appends a crashed node_exited. Either way the run cannot hang.

Completion is not exit — but exit still folds

The slice, in three pillars

PILLAR 1 · D1 / D2 · the heart of the slice

Orchestrator-owned MCP acts

A small orchestrator MCP surface in Muxed exposing the two completion tools, injected alongside the worktracker MCP into orchestrator-launched agents only.

  • FastMCP surface owned by apps/orchestrator — worktracker MCP stays generic (OWNERSHIP boundary intact)
  • decompose_complete: appends fact; the driver's existing structural gate still validates children on fold
  • report_verdict: appends fact carrying the verdict payload verbatim
  • Handler validates injected run_id/node_id against a running node; duplicate calls are idempotent no-ops
PILLAR 2 · D3 · one substrate, routed folds

Fact-kind router in reconcile

Reconcile's drain stops being node_exited-only: a kind router dispatches each pending fact to its fold. New kinds arrive without touching the drain loop again.

  • Kinds: node_exited (existing) · decompose_complete · verdict_reported
  • Reducer folds verdict/children from facts — the file-parse path in the driver collapses into one fold entry point
  • Unknown kinds stay pending, exactly as today
  • Seam for future acts (question answers #791, phase heartbeats) — kinds only, no code reserved
PILLAR 3 · D6 · the payoff

Launch policy unforced

The driver stops forcing non-implement phases headless; interactive+auto stops being rejected. Attached verify and decompose become launchable, gated or autonomous.

  • _default_launch: phase-based headless forcing deleted; launch_mode flows through for every phase
  • _verify_enabled: interactive check deleted — verify runs on either transport
  • start_run: interactive+auto accepted
  • Retry teardown: ManagedAgent terminates any existing attached session through the Session seam before respawn

Question board

Green = settled in this HLD (the dossier's eight open questions collapse into D1–D7). Red = genuinely open — neither gates the slice.
ANSWERED · decompose signal

Ticket transition, MCP tool, or both?

MCP tool only. A parent-ticket transition would overload user-facing state with protocol meaning; the structural children-gate still validates on fold, so a premature call fails loudly, not silently.

ANSWERED · run resolution

How does report_verdict find its run?

It doesn't — it's told. run_id/node_id are injected at launch and validated on call. Historical runs sharing a node can never be confused with the one non-terminal run the ids name.

ANSWERED · where tools live

Orchestrator tools in the worktracker MCP?

No. Verdict facts live in Muxed's orchestrator DB; worktracker MCP is generic and ported upstream. A separate orchestrator-owned surface keeps the OWNERSHIP boundary objective.

ANSWERED · retry teardown

Who tears down an attached session on retry?

ManagedAgent, through the Session seam it already launches with (T800) — terminate-before-respawn is part of start, not a driver concern.

STILL OPEN · default profile

Does orchestrate default to attached-auto?

Open, low-pressure: this slice makes interactive+auto legal; whether it becomes the default launch profile (subscription billing everywhere) is a product call after live E2E.

STILL OPEN · unify implement

Should implement also gain an explicit act?

Open by construction: ticket-Done keeps working. If the ticket gate ever feels overloaded, an implement_complete kind drops into the router without touching the drain. Post-v1.

Acceptance signal

The slice is done when a run launched fully attached (decompose, implement, verify all in tmux, autonomous) completes end-to-end: decompose finishes by calling decompose_complete and the fold admits the children through the existing structural gate; verify finishes by calling report_verdict and the run routes accept/reject off the fact; killing any attached session mid-phase leaves no hung run — hygiene's crash fact folds a failure on the next tick; the same strategy pack runs headless with zero prompt or fold changes; and a duplicate completion call is a no-op, proven by tests at the router, reducer, and tool-handler levels.
