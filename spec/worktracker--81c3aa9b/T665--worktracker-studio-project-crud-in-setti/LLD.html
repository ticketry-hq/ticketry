Backend & SDK contract

Three schema edits, one new route, and SDK parity. Described by obligation; field names are the contract, exact code is implementation detail.

Schema deltas — worktracker/schemas.py

ProjectOutAdd description: str (defaults to empty string for existing rows; the model field is blank=True). Required because the SDK OutputModel base is extra="forbid" — exposing the field on the API without adding it to the SDK model breaks deserialization.
ProjectIn (create)Add description: Optional[str] = None. Keep name, slug, workspace_slug as they are. A missing description persists as empty string.
ProjectPatch (edit)Add description: Optional[str] = None. Slug stays absent — key is immutable after creation. Patch remains partial: only provided fields are written.

Routes — worktracker/api.py

POST /projectsExtend create_project to read payload.description onto the new row. Preserve the existing duplicate-slug guard (explicit Project.objects.filter(workspace, slug).exists() → 409) and the IntegrityError fallback. Default-state seeding unchanged.
PATCH /projects/{id}Extend patch_project to apply description when present; add "description" to the update_fields list alongside name/updated_at. Slug is never read from the patch payload.
DELETE /projects/{id}New route. Permanent, no child-count guard (unlike module/work-item delete which 409 on children). Resolve the project (404 if missing) and call .delete() → 204. Cascade is automatic: State / IssueType / Label / Sprint / Issue / Attachment all declare on_delete=CASCADE on the project (or issue) FK.

SDK parity — worktracker-sdk/worktracker_sdk/

models.py · ProjectAdd description: str to the Project output model (mandatory — see ProjectOut note above).
models.py · inputsAdd input models ProjectCreate (name, slug, optional workspace_slug, optional description) and ProjectUpdate (optional name, optional description; no slug).
resources.py · ProjectsResourceAdd create, update, and delete methods mirroring the three routes, following the existing resource call pattern. Required for CRUD parity even though Studio talks to the ninja API directly and no current consumer uses SDK mutations.

Recent-project memory

A small persisted ordered list of project ids drives both startup selection and post-delete redirect, replacing today's projects[0] default.

Store: localStorage["studio.recentProjects"]

shapeJSON array of project-id strings, most-recently-used first. Mirrors the try/catch read-write pattern of uiStore (navCollapsed / groupByEpic).
moduleNew lib/recentProjects.ts exporting read, and a touch(id) that moves an id to the front, and a resolveStartProject(projects) helper. Keeps the persistence shape in one place.
"used" defUpdated on every project switch/selection — touch(id) is called from studioStore.selectProject when a project becomes selected.
hygieneReads filter to ids that still exist in the loaded projects; stale ids (deleted projects) are dropped on next write. No separate cleanup pass.

Consumers

  • Startup — RootRedirect opens the first surviving id from the MRU list; if none survive (e.g. fresh localStorage), falls back to projects[0]; if no projects exist at all, renders the create-project screen.
  • Project switch — selectProject(id) calls touch(id) so the order reflects real usage and survives reload.
  • Post-delete — after a successful delete of the selected project, redirect to the first surviving MRU id (excluding the deleted one); if none remain, the create-project screen.
  • Non-selected delete — deleting a project that is not currently open removes it from the list and stays on the current project; no redirect.

Settings layout — dedicated Projects sub-section

Settings gains an inner left nav. Projects is the first entry and the default sub-section — reachable with no project selected; the project-scoped sections sit beside it and keep their existing gate.
Click a nav entry or the panel.
SituationResolution
Projects sub-sectionThe first inner-nav entry and the default selection when Settings opens. The dedicated ProjectsView does not depend on selectedProjectId — it lists every project from studioStore.projects and offers create / edit / delete inline. Reachable even when no project is open.
Project-scoped sectionsIssueTypes / WorkflowStates are sibling nav entries that keep their existing "select a project" gate unchanged. Selecting one when no project is open shows the same gate prompt; only Projects renders unconditionally.
At least one project existsA project is always selected, so /settings renders and lands on the Projects sub-section by default. All three nav entries are usable.
Zero projects (fresh install or last one deleted)RootRedirect renders a create-project screen (replacing today's "No projects found" dead-end). Submitting it runs the same create path, then navigates into the new project. This is the create-from-empty entry point — no Settings route needed when there is nothing to select.
DecisionNo new global Settings route. Settings becomes a small inner left-nav layout with Projects as the default sub-section, IssueTypes / WorkflowStates as gated siblings, plus the RootRedirect create screen for bootstrap. The nav state is local view state — no router change. Smallest surface that gives Projects a dedicated home while staying reachable.

Acceptance

Every ticket criterion is mapped: a Projects section reachable with or without a selected project; create with markdown description and duplicate-key feedback; edit name + description with id/key/workspace/counters/timestamps read-only; a typed-key delete gate; permanent cascading delete verified by the backend test; post-delete redirect and startup both driven by persisted recent-project order; the empty state replaced by a create-project screen; and backend, SDK, types, stores, routing, and tests moved in lockstep — with no migration and no new dependency.
