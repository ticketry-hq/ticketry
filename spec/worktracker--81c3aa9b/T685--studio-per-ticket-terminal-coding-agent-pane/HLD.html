Coding · WorkTracker Studio · Ticket #685 · HLD

Per-ticket Terminal & Coding-Agent Pane — High-Level Design

An Agent tab inside Studio's issue drawer launches and attaches a coding agent (Claude / Codex / Gemini) against the open ticket, streaming a live terminal — without leaving Studio. It reuses Muxed's already-shipped terminal backend over the same single origin; no backend, no port, no new ingress.
Phase: HLD Zero backend change Single origin · no CORS Frontend-only · Studio Generic split retired — build wherever cleanest

Problem & solution

Studio is the planning surface; Muxed's desktop app is where agents actually run. Today those are two windows for one ticket.
PROBLEM · USER'S VIEW

I plan in Studio but run agents elsewhere

When I open a ticket in Studio I can read it, edit it, see the agent's lifecycle badge — but to actually launch or watch a coding agent against that ticket I have to switch to the Muxed desktop app.

That context switch breaks the loop: the ticket I'm reading and the terminal I'm driving live in different windows, even though they are the same work item.

SOLUTION · USER'S VIEW

Launch & watch the agent in the drawer

The issue drawer gains an Agent tab. I pick an agent, hit launch, and a live terminal opens — bound to this exact ticket. Existing sessions for the ticket are listed and I can re-attach to any of them.

Keystrokes, resize, and tmux scrollback all work; a drop reconnects transparently; I can terminate a run; and a toggle expands the drawer to near-full-screen when I want room.

REJECTED · port the backend
Re-implement the terminal/PTY/tmux/worktree engine inside Studio's stack. Huge surface, host-coupled, pointless duplication.
⟶
RECONSIDERED · cross-origin service
Talk to Muxed's backend on a separate origin. Works for WS but a cross-origin fetch needs CORS the backend doesn't send.
⟶
THIS DESIGN · same single origin
Muxed's Django server imports worktracker-stack and exposes both. Studio already consumes that one origin via its /api proxy. Terminal WS + REST ride it. No CORS, no backend change.

Spawn / attach flow

Click a step to reveal the exact wire frame. Note the mode field — the original ticket omitted it; the consumer dispatches on it.
STEP 1 · SPAWN

User picks an agent, hits launch

The pane opens a socket to ws(s)://<origin>/ws/terminal (origin derived from VITE_CODING_API_BASE) and sends the spawn init frame with the open ticket's IDs and the measured terminal geometry.

{ "type":"init", "mode":"spawn", "agent":"claude|codex|gemini", "project_id", "module_id", "task_id", "cols", "rows" }
STEP 2 · READY

Backend spawns in the worktree, replies ready

The engine resolves the ticket's top-level worktree (W2 wiring), starts the agent in a tmux session, and returns the run identity. The pane stores agent_run_id — the key the reconnect policy needs.

{ "type":"ready", "session_id", "agent_run_id" } → then binary PTY output frames
STEP 3 · LIVE I/O

Terminal streams; user types and resizes

xterm renders binary output; keystrokes go back as binary; the fit addon computes geometry. The expand toggle and window resize both recompute and send a resize frame; scrollback drives tmux copy-mode.

client → binary keystrokes client → { "type":"resize", "cols", "rows" } client → { "type":"scroll", "dir", "lines" }
STEP 4 · ATTACH

Re-open the ticket → list & attach

On mount the pane lists the ticket's sessions and attaches to a chosen run by id. The same path serves transparent reconnect after a drop.

GET /api/terminals?task_id=<id> → sessions[] ws init: { "type":"init", "mode":"attach", "agent_run_id", "cols", "rows" }
STEP 5 · RECONNECT

A drop heals itself

The ported policy retries only sockets that reached ready with an agent_run_id — rebuilding as an attach frame. ~8 attempts, 500ms→10s exponential backoff, ~25% jitter. Pre-ready failures are not retried.

reconnect → re-send mode:attach with stored agent_run_id
STEP 6 · TERMINATE

Stop a run

Terminate stops the tmux session and soft-deletes its row; the pane drops it from the list. The session also tears down naturally when the pane unmounts — but the backend run persists for re-attach.

DELETE /api/terminals/?agent_run_id=<id> → { "agent_run_id", "terminated": true }

User stories

The actor is a developer working a ticket in WorkTracker Studio, unless noted.
1DiscoverAs a developer, I want an Agent tab on a ticket's drawer, so that I can reach the agent surface from the same place I read and edit the ticket.
2SpawnAs a developer, I want to choose an agent (Claude, Codex, or Gemini), so that I can run the tool that fits the task.
3SpawnAs a developer, I want a launch to bind to this exact ticket (its project/module/task IDs), so that the agent works in the right context and worktree.
4SpawnAs a developer, I want the agent to start in the ticket's git worktree if one exists, so that its changes land on the right branch — without me managing worktrees here.
5WatchAs a developer, I want a live terminal rendering the agent's output, so that I can follow what it is doing in real time.
6DriveAs a developer, I want to type into the terminal, so that I can answer prompts and steer the agent.
7DriveAs a developer, I want the terminal to resize to its pane, so that output isn't clipped or wrapped wrong.
8DriveAs a developer, I want scrollback through tmux history, so that I can read output that scrolled off.
9AttachAs a developer, I want to see a list of existing sessions for the ticket, so that I can rejoin a run I started earlier.
10AttachAs a developer, I want to attach by run and immediately see live output, so that re-opening the ticket resumes where I left off.
11ResilienceAs a developer, I want the socket to reconnect automatically after a network blip, so that a transient drop doesn't lose my session.
12ResilienceAs a developer, I want a clear status (connecting / live / reconnecting / closed), so that I know whether what I see is current.
13ControlAs a developer, I want to terminate a session, so that I can stop an agent that's done or misbehaving.
14ControlAs a developer, I want a terminated session to leave the list, so that the list reflects what's actually running.
15LayoutAs a developer, I want to toggle the drawer to near-full-screen (~90%), so that I get room for a wide terminal; and back, so that I can see the rest of Studio.
16LayoutAs a developer, I want the terminal to re-fit on the expand toggle and on window resize, so that geometry stays correct as the pane changes size.
17LifecycleAs a developer, I want switching to the Details tab or closing the drawer to not kill the backend run, so that the agent keeps working while I look elsewhere.
18LifecycleAs a developer, I want re-opening the Agent tab to re-attach to the still-running session, so that navigating away is safe.
19ContinuityAs a developer, I want the existing lifecycle badge on the ticket to keep working unchanged, so that the at-a-glance state I already rely on is preserved.
20ConfigAs an operator, I want the terminal endpoints reached over the same origin Studio already uses, so that no CORS or extra backend config is required to ship this.

Testing decisions

Test external behavior — what the pane and the ws client do at their boundaries — not internals. Prior art: the existing lifecycleStore.test.ts / codingBridge.test.ts in Studio, and Muxed's ws.test.ts.
UNIT · terminalWs.ts

The reconnect policy

Mirror Muxed's ws.test.ts against a mock socket.

  • Builds correct spawn vs attach init frames (incl. mode)
  • Retries only after ready + agent_run_id
  • Backoff schedule + attempt cap; gives up cleanly
  • Does not retry pre-ready failures or clean (1000) closes
UNIT · terminalStore

Session state transitions

Drive the store via its actions; assert observable state.

  • Listing populates sessions for a task_id
  • Status moves connecting → live → reconnecting → closed
  • Terminate removes the session from the list
  • One active session at a time
COMPONENT · AgentTerminalPane

Pane behavior at its edges

Render with a faked store/ws; assert what the user sees and what frames go out.

  • Agent tab renders; picking + launching emits a spawn with the open ticket's IDs
  • Attach list renders and attaches by run
  • Expand toggle triggers a re-fit/resize frame
  • Unmount tears the socket down (run persists)

Scope boundary

v1 is the smallest end-to-end agent surface. Everything below is deliberately deferred.

Out of scope (v1)

  • Lifecycle poll → WS upgrade: keep the 5s /api/runs/lifecycle-states poll + badge as-is.
  • Worktree status surfacing / create-discard in the pane (/api/worktrees).
  • Doc-chat / planning / instant scratch terminal scopes.
  • Agent-run history / log archive beyond the live session.
  • Multiple simultaneous sockets per drawer.
  • Any backend change, including adding auth/CORS to the terminal endpoints.

Sequenced follow-ups (separate tickets)

  • Librarify the terminal transport into a shared package for Muxed's web frontend + Studio, with a single-source-of-truth wire-contract types module (the missing-mode drift is the case for it).
  • Retire the generic-split governance docs/skill (consequence of D9).
  • Possible epic: fold the worktracker backend into Muxed as a deployment composition + share Studio↔Muxed frontend code.

Acceptance signal

The feature is done when opening a ticket's drawer shows an Agent tab; selecting an agent and launching opens a live xterm session bound to that ticket (a correct mode:"spawn" frame carrying its project/module/task IDs); the ticket's existing sessions are listed and attachable by agent_run_id with output streaming and keystrokes, resize, and tmux scrollback all working; terminate stops a run and drops it from the list; a dropped socket reconnects transparently per the ported backoff; the expand toggle re-fits the terminal between normal and ~90% width; and the existing lifecycle poll and badge remain unchanged — with the transport-librarify and governance-cleanup work explicitly left to follow-up tickets.
