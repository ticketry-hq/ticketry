# T3 Code terminal architecture

Research snapshot: T3 Code commit [`038560e58036d51b2576b3c2cd9170a194cefe9e`](https://github.com/pingdotgg/t3code/tree/038560e58036d51b2576b3c2cd9170a194cefe9e), dated 2026-08-14. T3 Code changes quickly, so the pinned commit matters: this note describes that implementation, not older releases.

## Executive summary

T3 Code's current terminal is a client/server terminal, even in the Electron app. A T3 server owns ordinary OS PTYs; web, desktop, and mobile clients receive the PTY's raw output stream and send input and resize commands back over the same authenticated WebSocket RPC boundary used by the rest of the application. Renderer choice is deliberately client-local and never appears in the wire protocol. ([terminal renderer architecture](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/docs/architecture/terminal-renderers.md#L1-L27), [remote runtime boundary](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/docs/internals/remote.md#L10-L42))

The browser/Electron renderer is no longer xterm.js. It uses a pinned build of Ghostty's `libghostty-vt` C ABI compiled to WebAssembly for parsing and terminal state, then paints snapshots on a Canvas 2D surface. Browser-specific input, IME, selection, clipboard, sizing, links, and cursor behavior live in a thin TypeScript adapter; React does not participate in terminal frames. ([renderer architecture](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/docs/architecture/terminal-renderers.md#L7-L27), [web adapter README](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/web/src/terminal/ghostty/README.md#L1-L19))

T3 multiplexes many terminal sessions in its own server process, keyed by `(threadId, terminalId)`. It does **not** use tmux for durable process ownership. A client disconnect can reattach to a still-running server-owned PTY and get an initial snapshot plus ordered live events, but a T3 server restart kills its PTYs. Only a capped, sanitized text history is persisted and replayed; the shell/process itself is not resumed. ([session state and manager map](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/server/src/terminal/Manager.ts#L232-L291), [shutdown cleanup](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/server/src/terminal/Manager.ts#L2160-L2180), [history restore/open](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/server/src/terminal/Manager.ts#L2183-L2241))

## Architecture at a glance

```text
Keyboard / mouse / resize
        │
        ▼
Ghostty WASM + Canvas surface (web app, also loaded by Electron)
        │ terminal.write / terminal.resize JSON RPC
        ▼
Authenticated WebSocket RPC connection
        │
        ▼
T3 server TerminalManager
  map[(threadId, terminalId)] -> in-memory session + PTY handle
        │
        ▼
node-pty (Node runtime) or Bun's native PTY API (Bun runtime)
        │
        ▼
User shell and subprocess tree on the server host

PTY output travels upward as raw string chunks in `output` events.
Visible text history is separately capped and persisted for replay.
```

This is one runtime boundary rather than a desktop-only native terminal path: the client connects to one execution-environment server, and that server owns terminals, files, git, projects, and providers. A remote desktop, hosted browser, or phone therefore controls PTYs on the remote server host, not on the client device. ([remote model](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/docs/internals/remote.md#L10-L42), [SSH ownership](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/docs/user/remote-access.md#L125-L137))

## Frontend renderer and emulator

The web renderer loads one singleton Ghostty WASM runtime per browser tab. Each visible terminal owns its own Ghostty terminal, render state, iterators, key and mouse encoders, and input handles, while split terminals share the compiled module and its memory. ([renderer lifetime](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/docs/architecture/terminal-renderers.md#L24-L27), [runtime singleton](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/web/src/terminal/ghostty/runtime.ts#L213-L220))

`GhosttyTerminalCore` constructs the ABI objects, sets a maximum scrollback, feeds PTY bytes to `ghostty_terminal_vt_write`, and uses Ghostty for keyboard/mouse encoding and terminal state. `GhosttyTerminalSurface` creates an opaque Canvas 2D backing surface plus a hidden textarea for keyboard/IME input, observes its container for size changes, and schedules drawing outside React. ([core initialization and writes](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/web/src/terminal/ghostty/core.ts#L200-L301), [surface construction](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/web/src/terminal/ghostty/surface.ts#L540-L645), [render scheduling](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/web/src/terminal/ghostty/surface.ts#L1485-L1536))

Ghostty can generate PTY replies itself (for example, terminal device-query responses). T3 installs a tiny WASM callback trampoline that decodes those bytes and routes them back through the terminal's `onData` writer. When replaying saved history, T3 temporarily detaches this writer so historical device queries cannot be sent into the current live shell. ([callback trampoline](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/web/src/terminal/ghostty/runtime.ts#L184-L210), [safe history replay](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/web/src/terminal/ghostty/core.ts#L303-L323))

The Ghostty revision is pinned once at `native/libghostty-vt/VERSION`; generated web artifacts embed the revision and an ABI test checks that it matches the pin. That makes the emulator a vendored, reproducible native dependency rather than an ambient browser package. ([update and verification policy](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/docs/architecture/terminal-renderers.md#L29-L42), [pinned revision file](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/native/libghostty-vt/VERSION))

## Shell and PTY process spawning

The server defines a small `PtyAdapter` interface: spawn, PID, write, resize, kill, output subscription, and exit subscription. This isolates terminal orchestration from the runtime-specific PTY implementation; server startup selects Bun's adapter when running under Bun and node-pty otherwise. ([PTY adapter contract](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/server/src/terminal/PtyAdapter.ts#L32-L65), [runtime adapter selection](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/server/src/server.ts#L130-L140))

On Node, the adapter is `node-pty`: it spawns the chosen shell with the requested cwd, grid dimensions, environment, and `TERM=xterm-256color`; Windows uses node-pty's ConPTY path and receives an explicit `TERM` because node-pty does not set it there. ([node-pty adapter](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/server/src/terminal/NodePtyAdapter.ts#L70-L110), [spawn options](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/server/src/terminal/NodePtyAdapter.ts#L141-L168))

On Bun, the adapter uses `Bun.spawn(..., { terminal: ... })`, decodes streaming bytes with `TextDecoder`, and exposes the same interface. This path is explicitly unavailable on Windows, where T3 tells the user to run the Node build instead. ([Bun process wrapper](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/server/src/terminal/BunPtyAdapter.ts#L10-L118), [Bun spawn](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/server/src/terminal/BunPtyAdapter.ts#L120-L153))

The manager resolves a platform-specific list of shell candidates and retries only retryable spawn failures. On Unix it considers the configured shell, `/bin/zsh`, `/bin/bash`, `/bin/sh`, and PATH variants; zsh is started with `-o nopromptsp`. Windows falls back through PowerShell and `cmd.exe` candidates. ([shell candidate resolution](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/server/src/terminal/Manager.ts#L439-L562), [retry loop and spawn](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/server/src/terminal/Manager.ts#L1830-L1883))

The child inherits the server's full environment, with T3/Vite/app-runtime variables scrubbed and caller-supplied per-terminal variables overlaid. The cwd is only checked to exist and be a directory; it is not restricted to a project or worktree root. ([environment construction](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/server/src/terminal/Manager.ts#L1085-L1168), [cwd validation](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/server/src/terminal/Manager.ts#L1604-L1616))

## Transport and input/output protocol

Terminal operations are typed Effect RPC methods on a WebSocket: `terminal.open`, streaming `terminal.attach`, `terminal.write`, `terminal.resize`, `terminal.clear`, `terminal.restart`, and `terminal.close`. The client and server both use Effect's JSON RPC serialization over a WebSocket connection, and the HTTP server negotiates per-message DEFLATE when the client supports it. ([terminal RPC definitions](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/packages/contracts/src/rpc.ts#L748-L785), [client JSON/WebSocket protocol](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/packages/client-runtime/src/rpc/session.ts#L68-L116), [server JSON/WebSocket route](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/server/src/ws.ts#L2286-L2313), [WebSocket compression](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/server/src/server.ts#L180-L223))

The wire data is string-oriented. A write carries a non-empty string capped at 65,536 characters; resize is capped at 1,000 columns by 500 rows. An attach first yields a full snapshot containing history and status, then `output`, `exited`, `closed`, `error`, `cleared`, `restarted`, and activity events. Output events carry the original PTY string chunk, while monotonically increasing per-session sequence numbers prevent a raced initial snapshot from being replayed twice. ([contract limits and snapshot](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/packages/contracts/src/terminal.ts#L11-L110), [stream event shapes](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/packages/contracts/src/terminal.ts#L152-L233), [race-free attach](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/server/src/terminal/Manager.ts#L2389-L2432))

On the web client, stream events reduce into a bounded 512 KiB UTF-8 buffer. Resize commands use "latest wins" scheduling per terminal so stale `ResizeObserver` traffic does not pile up, while lifecycle operations are serialized per thread. ([client buffer reduction](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/packages/client-runtime/src/state/terminalSession.ts#L47-L173), [client terminal command scheduling](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/packages/client-runtime/src/state/terminal.ts#L19-L92))

## Persistence, reattachment, and multiplexing

Terminal IDs are chosen by the client (`term-N`) and are explicit in every request. The server keeps one in-memory `TerminalSessionState` per `(threadId, terminalId)`, allowing multiple terminals and split views without an external terminal multiplexer. ([client-assigned IDs](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/packages/contracts/src/terminal.ts#L4-L47), [server state map](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/server/src/terminal/Manager.ts#L232-L291))

While the server stays alive, an attach subscribes before taking its snapshot, buffers events that race the snapshot, drops events already represented by the snapshot sequence, and then switches to live delivery. Thus closing/reopening a browser pane or reconnecting a client does not restart a still-running PTY. ([attach algorithm](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/server/src/terminal/Manager.ts#L2309-L2357), [snapshot-to-live handoff](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/server/src/terminal/Manager.ts#L2389-L2432))

The durable piece is text history, not the PTY. T3 caps server history at 5,000 lines, strips control sequences unsuitable for history, coalesces file writes with a 40 ms debounce, writes one log per terminal, and reloads that log on the first open after manager/server startup. ([history constants](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/server/src/terminal/Manager.ts#L77-L85), [history persistence](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/server/src/terminal/Manager.ts#L1408-L1503), [output/history handling](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/server/src/terminal/Manager.ts#L1683-L1779))

When the manager scope closes, T3 removes all sessions and terminates each PTY with SIGTERM followed by SIGKILL after a grace period. Reopening later reads the saved log and starts a fresh shell; changing cwd/environment/worktree or reopening an exited session also clears the old history before spawning. This is replay-and-restart semantics, not process resume. ([kill escalation](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/server/src/terminal/Manager.ts#L1336-L1406), [manager finalization](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/server/src/terminal/Manager.ts#L2160-L2180), [open/restart rules](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/server/src/terminal/Manager.ts#L2244-L2303))

## Desktop versus browser

The Electron app does not bypass the server for terminals. It launches and supervises one or more T3 backend child processes, registers a custom `t3code://app/` protocol that targets the web renderer and backend origins, and loads that URL into a sandboxed BrowserWindow. The same web client then opens normal authenticated WebSocket connections, so its terminal surface and protocol match the browser version. ([desktop bootstrap](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/desktop/src/app/DesktopApp.ts#L142-L217), [custom protocol URL](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/desktop/src/electron/ElectronProtocol.ts#L11-L25), [sandboxed window](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/desktop/src/window/DesktopWindow.ts#L304-L355))

The meaningful desktop difference is process and connection management: Electron can supervise local/WSL backends and launch or reuse a remote server over SSH with a local port forward. Once connected, the renderer sees each as another execution environment and uses the same RPCs. ([backend pool design](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/desktop/src/backend/DesktopBackendPool.ts#L1-L80), [SSH architecture](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/docs/internals/remote.md#L158-L176))

The hosted web app is not a proxy: after pairing, the browser connects directly to the selected backend over HTTP(S)/WS(S). Consequently browser mixed-content rules apply, and plain LAN `ws://` endpoints cannot be reached from the hosted HTTPS app. ([hosted pairing constraints](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/docs/internals/remote.md#L104-L123), [direct WebSocket access](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/docs/internals/remote.md#L132-L150))

## Security and sandboxing

Remote WebSockets use a dedicated short-lived ticket. A client presents its long-lived bearer or DPoP credential to an authenticated HTTP endpoint, receives a WebSocket ticket, and places only that ticket on the `/ws` URL; the default ticket TTL is five minutes. The upgrade authenticates the ticket, and terminal RPCs additionally require the `terminal:operate` scope. ([remote ticket issuance](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/packages/client-runtime/src/authorization/remote.ts#L131-L213), [WebSocket upgrade authentication](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/server/src/ws.ts#L2286-L2313), [terminal RPC scope mapping](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/server/src/auth/RpcAuthorization.ts#L99-L109), [ticket TTL](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/server/src/auth/SessionStore.ts#L404-L421))

Electron's renderer is sandboxed with context isolation enabled and Node integration disabled. The terminal's WASM runs as a read-only renderer asset; it has no direct OS process access. All privileged terminal execution stays behind the authenticated server API. ([BrowserWindow preferences](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/desktop/src/window/DesktopWindow.ts#L336-L355), [WASM asset boundary](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/web/src/terminal/ghostty/README.md#L18-L19))

The shell itself is not sandboxed by T3's terminal manager. It runs as the server user, inherits nearly the full server environment, and may start in any existing directory supplied by a client with `terminal:operate`. Authentication and RPC authorization protect access to that capability, but there is no project-root jail, container, OS sandbox, or per-command policy in this terminal path. ([spawn environment](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/server/src/terminal/Manager.ts#L1120-L1168), [cwd check](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/server/src/terminal/Manager.ts#L1604-L1616), [PTY spawn](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/server/src/terminal/Manager.ts#L1859-L1867))

## Design tradeoffs and implications for Ticketry

### Pieces worth considering

- **A renderer-independent wire contract.** Keeping raw PTY output plus explicit input/resize/lifecycle messages makes web, Electron, mobile, SSH, WSL, and future renderers interchangeable without changing server process ownership. ([renderer/transport separation](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/docs/architecture/terminal-renderers.md#L1-L27))
- **Ghostty VT core with a thin platform renderer.** T3 gets Ghostty's parsing, grapheme, keyboard, mouse, selection, and hyperlink semantics while controlling its own Canvas/UI integration. The cost is owning a WASM/native build pipeline, ABI bindings, renderer, font measurement, IME, accessibility surface, and extensive conformance tests. ([web adapter responsibilities](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/web/src/terminal/ghostty/README.md#L1-L19), [platform split](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/docs/architecture/terminal-renderers.md#L17-L27))
- **Snapshot-before-live attach with sequence numbers.** This is a clean way to avoid output gaps and duplicates when a UI mounts or reconnects, regardless of renderer. ([sequence handling](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/server/src/terminal/Manager.ts#L392-L411), [attach handoff](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/server/src/terminal/Manager.ts#L2389-L2432))
- **Runtime-neutral PTY adapter.** The orchestration layer does not care whether Node's `node-pty`, Bun's PTY API, or another backend owns the OS primitive. ([adapter contract](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/server/src/terminal/PtyAdapter.ts#L37-L65))

### Pieces not to copy blindly

- **T3's persistence model is weaker than Ticketry's stated durable-session requirement.** T3 owns PTYs inside the backend process and persists only sanitized output logs. If the backend exits or updates, interactive programs and shell state are lost. Ticketry's tmux-backed durable-session boundary should remain unless product requirements deliberately accept restart-and-replay semantics. ([T3 finalization](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/server/src/terminal/Manager.ts#L2160-L2180), [T3 history restore](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/server/src/terminal/Manager.ts#L2183-L2241))
- **JSON strings are simple but not maximally efficient.** T3 sends terminal chunks as JSON strings and keeps independent server line and client byte caps. That is easy to inspect and shares the app RPC stack, but high-throughput terminal workloads pay UTF-8/JSON allocation and framing costs and need careful backpressure/buffer policy. ([JSON transport](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/packages/client-runtime/src/rpc/session.ts#L95-L116), [buffer limits](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/packages/client-runtime/src/state/terminalSession.ts#L65-L89))
- **Authorization is capability-level, not filesystem confinement.** `terminal:operate` is effectively remote shell access as the server user. If Ticketry exposes terminals beyond its trusted local desktop boundary, it should treat this scope as highly privileged and retain its own path/workspace controls where required. ([scope mapping](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/server/src/auth/RpcAuthorization.ts#L99-L109), [unrestricted cwd validation](https://github.com/pingdotgg/t3code/blob/038560e58036d51b2576b3c2cd9170a194cefe9e/apps/server/src/terminal/Manager.ts#L1604-L1616))

## Bottom line

The most transferable T3 idea is the separation of concerns: server-owned terminal sessions, a small typed raw-stream protocol, attach snapshots plus ordered events, and a platform-local renderer. T3's current Ghostty-WASM Canvas implementation is especially relevant if Ticketry wants one terminal semantics engine across native and web surfaces. The least transferable part is process durability: T3 deliberately multiplexes PTYs in memory and restores output, whereas Ticketry's architecture explicitly gives tmux responsibility for durable sessions.
