# Tauri 2 observability tool matrix

Date: 2026-09-01  
Scope: Tauri 2 desktop debugging and observability, using first-party project documentation, official API references, and upstream source repositories.

## Matrix

| Area | Tool or capability | Evidence | Tradeoffs and Ticketry fit |
| --- | --- | --- | --- |
| Tauri logs | `tauri-plugin-log` | Tauri's official plugin supports Rust and JavaScript logging, stdout, WebView console forwarding, application log directories or custom folders, size limits, rotation, levels, module filters, and custom formatting. [Tauri logging](https://v2.tauri.app/plugin/logging/) | Good baseline for persisted local diagnostics. It is `log`-based, not a tracing system, so it does not by itself carry span context. Ticketry already has a fixed file-log path and frontend console bridge; adopt only if it can replace or cleanly feed that sink. |
| Tauri dev inspection | Built-in WebView inspector and Rust debugger | Tauri documents WebView inspection through the platform inspector, programmatic `open_devtools`, and Rust-core debugging with GDB/LLDB or VS Code LLDB. Release inspection needs the `devtools` Cargo feature; macOS uses private APIs and Windows does not support the `Webview::close_devtools` method. [Tauri debug](https://v2.tauri.app/develop/debug/) [Tauri Webview API](https://docs.rs/tauri/latest/tauri/webview/struct.Webview.html) | Highest-value interactive tool for a missing-UI record. Keep it debug-only or behind an explicit diagnostic build because production enablement has platform and security costs. |
| Tauri-specific live view | CrabNebula DevTools | Tauri's official guide describes the public-preview tool as capturing assets, configuration, logs, spans, Tauri commands, events, payloads, responses, and execution timing. Its upstream README warns that it conflicts with another process-wide logger unless the loggers are deliberately composed. [Tauri guide](https://v2.tauri.app/develop/debug/crabnebula-devtools/) [upstream source](https://github.com/crabnebula-dev/devtools) | Useful for development command/event timing and payloads. Public-preview status, external UI, and logger-global conflicts make it a secondary dev-only choice, not Ticketry's production diagnostic contract. |
| Rust structured diagnostics | `tracing` + `tracing-subscriber` | `tracing` provides spans, events, typed fields, causality, and async-friendly context. `tracing-subscriber` composes layers and supports runtime filtering such as `RUST_LOG`. [tracing](https://docs.rs/tracing/latest/tracing/) [subscriber fmt/filtering](https://docs.rs/tracing-subscriber/latest/tracing_subscriber/fmt/) [subscriber layers](https://docs.rs/tracing-subscriber/latest/tracing_subscriber/layer/) | Best foundation for one correlation ID across command, GraphQL, transaction, subscription, and UI-log boundaries. It requires deliberate field naming and context propagation; it should become the internal source of structured records, with the existing file logger as one output. |
| Distributed telemetry | OpenTelemetry Rust + OTLP | OpenTelemetry Rust currently documents traces, metrics, and logs as Beta. The Rust docs recommend bridging existing logging through `tracing`; `opentelemetry-otlp` exports all three signals to compatible collectors/backends. OTLP is stable for traces, metrics, and logs and supports gRPC or HTTP. [OpenTelemetry Rust](https://opentelemetry.io/docs/languages/rust/) [Rust getting started](https://opentelemetry.io/docs/languages/rust/getting-started/) [OTLP Rust exporter](https://docs.rs/opentelemetry-otlp/latest/opentelemetry_otlp/) [OTLP spec](https://opentelemetry.io/docs/specs/otlp/) | Strong for cross-process or future service boundaries, but adds SDK/exporter/collector lifecycle, sampling, privacy, and offline-delivery work. | GraphQL server tracing | async-graphql `Tracing` extension | The current async-graphql API exposes a tracing extension and configurable scalar tracing. The schema builder accepts extensions. [Tracing extension](https://docs.rs/async-graphql/latest/async_graphql/extensions/struct.Tracing.html) [schema extensions](https://docs.rs/async-graphql/latest/async_graphql/struct.SchemaBuilder.html) | Low-friction resolver timing and event visibility for Ticketry's Rust GraphQL. Scalar tracing should stay off normally to avoid span explosion; enable it briefly when field-level diagnosis requires it. |
| GraphQL server telemetry | async-graphql `OpenTelemetry` extension | async-graphql exposes an OpenTelemetry extension that creates resolver spans from a supplied tracer; scalar/enum tracing is opt-in to limit volume. [OpenTelemetry extension](https://docs.rs/async-graphql/latest/async_graphql/extensions/struct.OpenTelemetry.html) | A good later layer over the same `tracing`/OTel pipeline. | GraphQL client/cache | Apollo Client DevTools | Apollo's official DevTools provide GraphiQL, watched-query inspection, mutation inspection, and normalized-cache search. [Apollo DevTools](https://www.apollographql.com/docs/react/development-testing/developer-tooling) [Apollo cache](https://www.apollographql.com/docs/react/caching/overview/) [Apollo Client API](https://www.apollographql.com/docs/react/api/core/ApolloClient) | Directly diagnoses “database row exists but query/cache/UI does not”: compare the response, cache entity identity, watched query variables, and list field. The Chrome/Firefox extension is awkward inside a native Tauri WebView; the same checks can be exposed through a debug-only in-app cache inspector or the experimental VS Code remote path. |
| React rendering | React Developer Tools | React's official docs say the Components and Profiler panels inspect components, props, state, and performance. The official standalone package supports embedded WebViews through a localhost connection. [React DevTools](https://react.dev/learn/react-developer-tools) [standalone source](https://github.com/facebook/react/tree/main/packages/react-devtools) | Best for proving the record reached the component but was filtered, keyed incorrectly, or not rerendered. Standalone mode adds a development client and local socket; never ship it in production. |
| Panic collection | Rust panic hook; Sentry Rust integration | Rust's global panic hook runs before abort or unwind and receives payload and source location. Sentry's Rust SDK adds backtraces, panic capture, optional tracing/log integrations, and flushing via a guard. [Rust `set_hook`](https://doc.rust-lang.org/std/panic/fn.set_hook.html) [Sentry Rust](https://docs.rs/sentry/latest/sentry/) [Sentry panic](https://docs.rs/sentry-panic/latest/sentry_panic/) [Sentry tracing](https://docs.rs/sentry-tracing/latest/sentry_tracing/) | A panic hook covers Rust panics, not every native crash. Sentry adds network/DSN/privacy/vendor cost and can conflict with another global logger. Ticketry's current decision favors local OS-native reports and local export, so use the hook to annotate the existing report path before considering upload. |
| Native crash dumps | Crashpad or Breakpad | Crashpad uses a separate handler process to snapshot state, store dumps, and optionally upload them. Breakpad documents compact minidumps, symbol files, and `minidump_stackwalk`. [Crashpad design](https://chromium.googlesource.com/crashpad/crashpad/+/main/doc/overview_design.md) [Crashpad status](https://chromium.googlesource.com/crashpad/crashpad/+/main/doc/status.md) [Breakpad getting started](https://github.com/google/breakpad/blob/main/docs/getting_started_with_breakpad.md) | Broad native coverage, but heavy integration and sensitive process-memory contents. Ticketry's existing ADR rejects a general embedded handler in favor of OS-native reports; retain that choice unless native crash evidence remains inadequate. |
| SQLite inspection | SQLite CLI, integrity checks, query-plan inspection | The SQLite project owns the CLI, `PRAGMA integrity_check`, and `EXPLAIN QUERY PLAN` documentation. [CLI](https://sqlite.org/cli.html) [integrity check](https://sqlite.org/pragma.html#pragma_integrity_check) [query plans](https://sqlite.org/eqp.html) | Lowest-risk, read-only investigation tool. Run against a copied or read-only database and record the exact database path, schema, row identity, lifecycle/state fields, and query result. A GUI is easier for ad hoc browsing but adds an install and can accidentally write. |

## Diagnosis path for “persisted record, missing UI”

Use one stable `diagnostic_id` and record it at each boundary:

1. SQLite read confirms the row, its identity, project/parent/state fields, and database file.
2. Rust `tracing` span confirms the mutation or read transaction committed and records the GraphQL operation name.
3. async-graphql tracing confirms resolver entry, selected fields, and response/error timing.
4. Tauri/WebView inspector confirms the response reached the WebView and shows console, exceptions, and network/transport failures.
5. Apollo DevTools or a debug cache view confirms normalized identity, list membership, variables, and cache eviction/write behavior.
6. React DevTools confirms the component received the item and whether its props/state changed or a filter/key prevented rendering.

## Prioritized shortlist for Ticketry

1. **P0: `tracing` + `tracing-subscriber`, feeding the existing local file log.** Add boundary fields rather than a second state store: `diagnostic_id`, `work_item_id`, `operation_name`, database/profile identifier, cache policy, result count, and error code. Keep payloads redacted.
2. **P0: built-in Tauri WebView inspector plus a debug-only Apollo cache/query view.** This is the fastest way to separate transport failure, stale Apollo state, and React rendering failure.
3. **P1: async-graphql `Tracing`, then its OpenTelemetry extension when resolver evidence is needed.** Start with request/resolver spans and scalar tracing off.
4. **P1: SQLite CLI read-only playbook.** Include database-path verification, row lookup by stable ID, schema/version checks, `PRAGMA integrity_check`, and query-plan inspection for the exact list query.
5. **P1: panic-hook annotations into Ticketry's existing local crash-report collection.** Do not add a general Crashpad handler or remote Sentry upload without a new privacy and operations decision.
6. **P2: CrabNebula DevTools for developer builds only.** Trial it only after resolving the single-global-logger constraint with the chosen `tracing`/file-log setup.
7. **P2: full OpenTelemetry OTLP export.** Revisit if Ticketry gains multiple independently deployed processes or local logs no longer explain cross-boundary timing.

## Repository-specific note

Ticketry already has a persisted desktop log, frontend console forwarding, crash-report collection, Apollo as the frontend record owner, Rust GraphQL, SQLite-backed persistence, and a decision against a general embedded minidump handler. The shortlist therefore favors wiring and correlation over adding another agent, logger, cache, or crash database.
