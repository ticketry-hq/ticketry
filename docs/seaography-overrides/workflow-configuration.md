## Revisioned workflow configuration

- Generated capability attempted: Seaography create-one, create-batch, update, and delete for `IssueTypeTransition` and `LaunchBinding`.
- Exact missing behavior: every row write must compare and advance its owning Issue Type's workflow revision. Transition deletion and workflow-state removal also prune unreachable transitions and bindings. Launch Binding upsert validates the complete launch policy before either row or revision commits.
- Why `.graphql` selection/alias/adapter is insufficient: a caller document cannot claim an Issue Type revision or combine row persistence, reachability repair, and policy validation in one database transaction.
- Why `ColumnOptions`, skips, guards, or `entity_filter` are insufficient: generated writes operate on one model. They cannot compare a revision stored on Issue Type while atomically writing or deleting a Transition or Launch Binding.
- Why a database constraint/default and SeaORM lifecycle hooks are insufficient: constraints enforce row uniqueness and references, but they cannot report a typed stale revision, compute graph reachability, or validate provider, model, reasoning, and automation policy as one candidate.
- Create-one safety: generated create stays private. `create_issue_type_transition` binds the natural transition key and required workflow revision. Launch Binding creation occurs only through its restricted upsert.
- Create-batch safety: private. Ticketry has no batch workflow edit contract, and one revision cannot safely authorize an unrestricted batch.
- Update safety: generated updates stay private because their optional filters can affect several rows and cannot claim the owning workflow revision. `update_issue_type_transition` and `upsert_issue_type_launch_binding` bind concrete identities.
- Delete safety: generated deletes stay private. `delete_issue_type_transition` must prune unreachable policy in the same transaction. Launch Binding has no public delete mutation.
- Smallest custom seam: transition create, update, and delete use `(issue_type_id, from_state_id, to_state_id, workflow_revision)`. Launch Binding upsert uses `(issue_type_id, state_id, workflow_revision)` and an allowlisted patch. `remove_state_from_issue_type_workflow` is the one named graph-membership operation.
- SeaORM transaction/domain module used: `commands::workflow::transition_rows`, `commands::workflow::membership`, and `commands::workflow::launch_policy` own revision claims, row writes, reachability repair, policy validation, commit, and rollback.
- Protected fields excluded: callers cannot submit row IDs, timestamps, Issue Type revisions, or Launch Binding ownership. Transition callers may set only `agent_allowed` and `handoff`; binding callers may patch prompt, required skills, model, reasoning, auto-start, and subtree-run policy.
- Identity/scope binding: every view requires one Issue Type identity and its current revision. Transition endpoints require both state identities. Membership and binding endpoints require one state identity. Domain commands verify all states belong to the Issue Type's project.
- Drift/regression test: `work_management_commands::graphql_exposes_only_authored_mutations_and_structured_errors` pins the public fields, arguments, typed stale errors, and authoritative results. Workflow command tests cover concurrent revision claims, rollback, reachability pruning, omitted binding fields, and launch-policy validation. `graphql:drift` validates the unchanged client operations and aliases.
- Registry entry, if this is genuinely non-CRUD: `remove_state_from_issue_type_workflow` remains in the operation registry because workflow membership is graph reachability, not row CRUD. Transition and Launch Binding fields remain model-shaped CRUD overrides.
