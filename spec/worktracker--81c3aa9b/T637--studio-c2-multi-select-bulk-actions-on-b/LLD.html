Four decisions, all client-side

C2 adds no backend and no new fetch. The selection is a small piece of pure client state; each bulk action is a parallel fan-out over the seam each single-item action already uses. These four choices were confirmed with the user during refinement.

1 · Where does selection live?

One store shared by both surfaces, or per-view?
A new selectionStore holds { surface, ids, anchorId }. Selection is per-surface — switching Backlog↔Board, changing project, or unmounting clears it. The store is layout-agnostic: the view passes the surface's ordered-id list into range() at click time, so the store never knows about trees, columns, or collapse state.

2 · What does a plain click do?

Select the row (Jira) or open the drawer (today)?
Unchanged: plain click opens the drawer (/issues/KEY-N) and clears any selection. Selection only begins with a modifier — ⌘/Ctrl toggles, Shift ranges. This preserves the current one-click-to-open muscle memory and avoids a checkbox column.

3 · How does Shift-click range work on the Board?

Within one column, or across columns?
Across columns, in visual reading order — columns left-to-right, each top-to-bottom (rank order), flattened to one list; the range spans column boundaries. On the Backlog the ordered list is the visible (non-collapsed) row order, top-to-bottom across epic groups.

4 · What happens to undeletable items in a bulk delete?

Block the whole op, or delete what you can?
Confirm → fan-out → report. A confirm dialog shows the count; deletes fan out; items with sub-tasks 409 individually; successes are removed and a summary reports "N deleted · M skipped (have sub-tasks)". Each delete rolls back independently.

The selection model

A small Zustand store and three click intents. The store is the single source of truth for "what is selected"; the views translate raw clicks into intents and supply the ordered list a range needs.

Store: selectionStore

surface"backlog" | "board" | null — which view owns the current selection. A click on a different surface resets first. Drives whether the bar renders in a given view.
idsSet<string> of selected work-item UUIDs (stories & sub-tasks only).
anchorIdThe last ⌘/plain-selected id — the fixed end of a Shift range. null until the first modifier click.
toggle(surface, id) — ⌘/Ctrl: add/remove id; set anchorId = id; reset if surface changed.
range(surface, id, orderedIds) — Shift: select the inclusive slice of orderedIds between anchorId and id; anchorId unchanged. No anchor → behaves like toggle.
clearEmpty the set, drop the anchor and surface.
isSelected(id) => boolean — read by each row/card for its highlight.

Click intents & lifecycle

  • Plain click → clear() then open the drawer. Drawer behavior is exactly today's.
  • ⌘/Ctrl-click → toggle(). First one starts a selection of size 1; the bar appears.
  • Shift-click → range() over the surface's ordered-id list. Contiguous, inclusive, anchor-pinned.
  • Epic headers / module rows are never selectable — only work-item rows wire the intents.
  • Cleared by Escape (while a selection exists), a click on empty surface background, a project change, and surface unmount.
  • Drag is unaffected — a modifier click never starts a drag; the post-drag draggedRef click-suppression already in the row/card stands.
  • After a bulk op the selection is trimmed to survivors (delete) or kept (state/sprint/priority) — see the fan-out section.

The two ordered-id lists

A Shift range is only as good as the order it ranges over. Each surface computes its own flat list in the exact order the user sees, and passes it to range(). Decision 3, made concrete.
SurfaceOrdered list (passed to range())Source
backlog The visible row order: walk groupBacklog()'s groups top-to-bottom; within each, pre-order DFS over TreeNodes, skipping the children of collapsed rows and of collapsed epics so the list matches exactly what is on screen. Derived in BacklogList from the same groups + collapsed/collapsedRows sets it already renders.
board Columns concatenated left-to-right in display order; within each column, items in rank order (the same compareRank sort the column renders). A flat reading-order list spanning column boundaries. Derived in BoardView from boardColumns(...) — the array it already maps over.
Why pass the list in rather than store it → the order changes with collapse toggles, filters, and optimistic rank moves. Recomputing it at click time keeps the store free of layout state and guarantees the range matches the pixels under the cursor.

Store delta & the fan-out

Four new methods on backlogStore, each a parallel fan-out of an action that already exists for one item. Snapshot once, apply optimistically to all, fire in parallel with Promise.allSettled, reconcile per-item: fulfilled → applyServerItem, rejected → roll that one row back.
// backlogStore.ts — new bulk methods (shapes; field-by-field is impl detail)
async bulkSetState(ids, stateId) {
  const snapshot = get().items;
  const target = get().states.find(s => s.id === stateId) ?? null;
  const todo = ids.filter(id => itemOf(id)?.state?.id !== stateId);  // skip no-ops
  set({ items: optimisticApply(snapshot, todo, i => ({ ...i, state: target })) });
  const results = await Promise.allSettled(
    todo.map(id => api.patchWorkItem(id, { state_id: stateId }))
  );
  reconcile(results, todo, snapshot);   // fulfilled→applyServerItem, rejected→rollback id
}
// bulkSetSprint(ids, sprintId|null) and bulkSetPriority(ids, priority) are identical
// in shape — only the patch key and the optimistic field differ.

async bulkDelete(ids) {
  const snapshot = get().items;
  set({ items: snapshot.filter(i => !ids.has(i.id)) });           // optimistic remove-all
  const results = await Promise.allSettled(ids.map(api.deleteWorkItem));
  const skipped = [];                                            // 409 = has sub-tasks
  results.forEach((r, k) => { if (r.status === "rejected") restore(ids[k], snapshot), skipped.push(ids[k]); });
  return { deleted: ids.length - skipped.length, skipped };       // → summary in the bar
}

Scope & boundaries

A tight presentational + client-state slice. What it deliberately leaves alone keeps it zero-risk to the backend and the other concurrent C-series tickets.

This slice does

  • ⌘/Ctrl-click toggle + Shift-click range on Backlog rows and Board cards
  • A floating bulk-action bar at ≥1 selected: State · Sprint · Priority · Delete · clear
  • Fan-out bulk set of state / sprint / priority (optimistic, per-item rollback)
  • Confirm-gated bulk delete with skip-children-and-report
  • Selected-row highlight; Escape / empty-click / nav clears
  • 3 new Vitest suites; tsc + build green

This slice does not

  • Touch the backend, SDK, migrations, or API client (reuses patchWorkItem / deleteWorkItem)
  • Add a right-click context menu (deferred follow-up)
  • Bulk reparent, bulk assignee (cut), or bulk label edits
  • Select-all / ⌘-A, or cross-surface persistent selection
  • Multi-select on the Story Map
  • Re-rank cards within a destination column on bulk state change
