Cancelled = Archived — drop cancelled issues out of every active view

Moving an issue into a Cancelled-group state auto-archives it. It then vanishes from board, backlog, story map, sprints and every other list consumer — because those routes already exclude archived rows. One coupling point; almost everything else is free.

The problem

Cancelled is a terminal, dead state — but it still consumes screen real estate everywhere active work lives.

The decision

Couple the existing Cancelled state group to the existing is_archived archive mechanism — instead of building a new "show cancelled" toggle.

CHOSEN — transition-based

Cancel → archive (auto)

patch_work_item reads the issue's old state group before applying the patch and compares it to the new target group. active → cancelled sets is_archived=True (and cascades down the subtree); cancelled → active sets is_archived=False (self only). Active→active and cancelled→cancelled leave the flag alone. Keying on the transition means no new field and no migration — and it naturally won't resurrect a manually-archived active item when its state is edited.

REJECTED

A per-view "show cancelled" toggle

Would mean threading a flag through board / backlog / story-map / sprint selectors and a UI control on each. More surface, more state, and the requester explicitly does not want a place to look at cancelled items. Archive coupling does it once, server-side.

No new archive/cancelled browsing view is built. Recovery is by deep-link only (see Transition flow, step 5). The manual archive/unarchive routes are untouched.

  1. Pick the Cancelled state in the issue-detail StatePicker (the state stays selectable — only its board column is hidden).
  2. patch_work_item receives state_id. This is the only path that mutates state, so the coupling lives in exactly one place.
  3. Couple to archive: compare old group (read pre-patch) to new group. Only the active → cancelled and cancelled → active transitions flip is_archived; same-group edits don't touch it.
  4. Cascade: active → cancelled archives the issue and its task descendants (BFS down the parent tree) so the tree never shows orphaned children. cancelled → active restores only the issue itself (intentional asymmetry).
  5. Recovery: the single-issue GET / /issues/<KEY-N> deep-link does NOT filter archived, so a cancelled issue is still openable; flipping its state back un-archives it, and the Studio drawer reloads the project so it repopulates the views. No browse view needed.

What actually changes

The whole feature is one new rule. Most of what makes it work is already built — click any row to see what it means.

THE ONE RULECancelling an issue now also archives it› This is the entire backend of the feature. The moment someone moves an issue into a Cancelled state, the system quietly marks it archived too — and archives everything nested under it, so a cancelled epic takes its stories and sub-tasks with it. Move the issue back to any active state and it un-archives just as quietly. It costs nothing extra to use; it happens on the same action people already take. Lives in the single state-change handler — patch_work_item, the only path that changes an issue's state.
ALREADY WORKSEvery active view stops showing cancelled items — for free› Board, backlog, story map and sprints all read the same filtered lists, and those lists already drop archived rows. So we don't touch any of them: once a cancelled issue is archived, it simply stops arriving on screen. This is why the feature is small — the hiding behaviour is inherited, not rebuilt for each view. No code changes here — the existing list endpoints already exclude archived rows.
ALREADY WORKSA cancelled issue is still recoverable — no special screen needed› Opening an issue by its direct link never filters by archived, so a cancelled issue stays reachable even though it's hidden from the lists. Flip its state back to active and it returns to its views at its old position. That's the entire recovery story — there's deliberately no "browse cancelled" screen to build. No code changes — the single-issue lookup already ignores the archived filter.
SMALL CLEANUPTidy the board column, the progress counts, and the open board› A handful of small touch-ups so nothing looks half-done: (1) the board stops drawing the now-permanently-empty Cancelled column; (2) sprint progress drops its redundant || cancelled clause (cancelled rows no longer load, so they can't pad totals); (3) the moment a cancel patch comes back archived, applyServerItem drops that one item from the store so the open board updates without a reload; and (4) the FE WorkItem type gains is_archived so the store can recognise it. Cascade-archived descendants simply don't reappear on the next project load — no front-end descendant walk. A few edits in the Studio store (boardColumns, sprintProgress, applyServerItem) and the shared WorkItem type.
BACKEND ROLLUPAn epic with only cancelled children loses its expand arrow› The child-count the backend reports (sub_issues_count) drives the expand arrow in the main Muxed app's task tree. Today it counts every child, so an epic whose only surviving children are cancelled would still show an arrow over an empty subtree. The fix is one annotation change: count only non-archived children. Studio doesn't use this field, but the main app does — so it's a real, shared backend correction. A single annotation in the work-item queryset — child_count filters out archived children.
SAFETY NETTests that pin each rule in place› New tests prove the behaviour and stop it regressing: cancel hides it, restore brings it back at the right spot, cancelling a parent takes its children along, the direct link still opens a cancelled issue, the board drops the Cancelled column, and progress counts ignore cancelled work. Added to the backend suite and the Studio test suite.

Edge cases & calls to make

PARENT WITH CHILDREN

Cascade on cancel

Cancelling an epic/story archives its whole subtree so no child floats orphaned in the backlog tree or story map. Verify both renderers.

ASYMMETRY

Un-cancel restores issue only

Restoring a parent does not auto-restore children (we can't know which were independently cancelled). Document this; children are restored individually if ever needed.

DECIDED — accepted residual

Manual-archive → cancel → un-cancel

Because the rule keys on the active↔cancelled transition (not a stored "why archived" flag), the round-trip manually-archive an active item, cancel it, then un-cancel it ends up visible. Rare, and not worth a tracking field — accepted and documented rather than designed around.

RANK

Restore lands correctly

rank is never touched by the transition, so an un-cancelled issue returns to its prior position in the active column/row.

Out of scope: a dedicated archive/cancelled browsing view · a generic "show archived/cancelled" toggle · changes to the manual archive/unarchive routes.

Acceptance signal

  • Moving an issue to a cancelled-group state removes it from board, backlog, story map, and sprint rows.
  • Moving it back to an active state restores it to the matching view at its prior rank.
  • The Cancelled column no longer renders on the board; the Cancelled state stays selectable in the detail picker.
  • Sprint progress and epic/story rollups exclude cancelled issues entirely.
  • Cancelling a parent cascades archive to descendants — no orphaned children anywhere.
  • A cancelled issue is still openable by /issues/<KEY-N>; changing its state un-archives it and the drawer reloads the project.
  • An epic whose only remaining children are cancelled shows no expand arrow in the main app (sub_issues_count excludes archived).
  • No new model field and no migration — the rule keys on the state transition alone.
  • Backend + Studio suites green, with new tests covering each transition, the cascade, and the filtered child_count.
