# Source-control pull-request DRF override record

## Commit, push, and open a GitHub pull request for a task worktree

- DRF-native capability attempted: a serializer-backed create action on `WorktreePullRequestViewSet`.
- Exact missing behavior: the request drives a git working tree and the user's `gh` CLI rather than creating an ORM row, so there is no model, queryset, or instance for `CreateModelMixin` to build. The response is an ordered list of five typed step outcomes, and both a rejected push and a refused pull request are explicit `failed` steps on `200` rather than errors — a commit that already landed and a branch that was already published are the only record the caller has of them, and an error envelope would carry neither.
- Why a frontend adapter over the generated SDK is insufficient: only the sidecar can stage a working tree, run `git commit` with the repository's hooks, push an explicit refspec, spawn a headless generator CLI, and invoke `gh pr create` in that checkout. A client sequencing three calls could also commit and then fail to push, or push a commit the user never confirmed.
- Why a serializer field / `validate` / `read_only_fields` is insufficient: the request serializer does validate the whole input — three context identifiers and nothing else — but resolving the base branch, checking the login, generating the title and body, and running the three steps in order is application behavior with no serializer expression.
- Why `permission_classes` and `get_queryset` scoping are insufficient: default API-key authentication applies, and the scope that matters is not a queryset but the recorded worktree path for the task; `apps.source_control.checkout` resolves it and refuses anything that is no longer a git checkout. The GitHub scope is the user's own `gh` login, which this app never reads.
- Why a database constraint/default is insufficient: what may be committed, whether the remote would accept the push, which branch is the repository's default, and whether a pull request already exists are all current git and GitHub facts held outside the database.
- Why an existing service function is insufficient: the application operations `apps.source_control.pull_request_action.commit_push_and_open_pull_request_for_task` and `open_pull_request_for_task` own all of the behavior; the custom seam only invokes and serializes them.
- Smallest custom seam: `WorktreePullRequestViewSet.commit_push_pr` and `WorktreePullRequestViewSet.pull_request`.
- Service module / `transaction.atomic` used: `apps.source_control.pull_request_action` coordinates the stack, and `apps.source_control.pull_request` owns the provider boundary. `apps.source_control.ship_records` opens one short transaction after the action settles. It never holds a transaction across Git hooks or GitHub calls.
- Protected fields excluded from the request schema: no action identifier, record owner, title, body, base branch, reviewer, remote, force option, hook bypass, token, or filesystem path is accepted. The server resolves all of them or keeps them outside Ticketry. The ship record is a read-only nested response.
- Identity/scope binding (URL kwarg + queryset filter): the ship writer verifies the requested task, resolved worktree anchor, worktree index, and module relationship against server rows before it creates the record.
- Contract-drift and regression test: `apps/source_control/tests/test_pull_request_api.py`, `test_pull_request_message.py`, and `test_ship_record_actions.py` cover ordered results, partial failures, provider isolation, and durable receipts against real repositories and a local bare remote. `npm run contract:check` seals the schema.
- Registry entry, if this is genuinely non-CRUD: `POST /api/worktrees/changes/commit-push-pr` and `POST /api/worktrees/changes/pull-request` in `worktracker.registry.HOST_ROUTES`.
