S1 — Durable Single-Task Planning Run-State

Low-level design spec for persisting the execution engine's single-task planning run-state to Django DB, ensuring the duplicate-launch guard survives server restarts.

Scope

CODIN-776 (S1) targets the single-task execution flow. Process-local cache registries are bypassed for correctness reads to guarantee ASGI restart safety.

In Scope

  • Create the EngineRun Django model in apps.execution.
  • One row per task: task_id is the primary key (OneToOneField to Issue).
  • Cascade deletes: deleting an Issue automatically cascades to its EngineRun.
  • Retarget driver.get_state() and driver._store() to query/update the DB directly.
  • Retarget the 409 guard check in planning API to query the durable row.
  • Retarget manual release (DELETE /planning-run) to delete the durable row entirely.
  • Maintain zero liveness inference: no timeouts or boot sweeps.

Out Of Scope (S2 / Future Slices)

  • Graph-level persistence (GraphRun model) — deferred to slice S2.
  • Passive run-death detection, timeouts, or AgentRun-status syncs.
  • Any process-level tmux/terminal termination logic.
  • Validation of board progress from engine states (kept separate).

Design Justifications

  • OneToOne Relation: Enforces the "one-run-per-task" guard strictly at the database integrity level.
  • Cascade on Task/Project Delete: Ensures orphans are never left behind if tasks or projects are deleted by users.
  • Module Nullability: Root task issues that do not sit inside any parent module will have module_id as null.
  • Process-Memory Bypass: All single-task status writes and preflight 409 guard reads hit this row directly, eliminating ASGI process divergence risks.

Test Plan

DB transactional rollbacks ensure clean states. Restarts are simulated by clearing in-memory caches and re-fetching from DB.

Restart 409 Test

Seed a running EngineRun row in DB, clear in-memory registries, POST planning-run. Assert 409 occurs with no spawn call executed.

Fresh Launch Test

Start with no row. POST planning-run. Assert 201 created, and an EngineRun row is saved in the DB with status="running" and a valid agent_run_id.

Launch Failure Test

Configure spawn mock to fail. POST planning-run. Assert 422/error returned and EngineRun row persists status="failed" with the traceback/exception string.

Completion Test

Trigger issue_state_changed signal for task transitioning backlog -> todo. Assert that the matching EngineRun row updates its status to "done".

Manual Release Test

Delete planning-run. Assert EngineRun row is deleted from the DB. Assert a subsequent POST planning-run launches successfully.

Negative Test

Ensure no background task or timer or restart sweeps attempt to automatically mark "running" rows as "failed". Status transitions stay manual-only.

Risk Controls

Controls targeting key concurrency and edge-case risks.
RiskControl
Race conditions on simultaneous launchesDatabase OneToOne primary key constraint on `task_id` ensures only one row can insert. The second concurrent launch attempt will violate integrity and fail database write, returning a clean 409/422.
Orphaned run recordsCascade deletes ensure that if a task or project is deleted, the execution metadata row goes away automatically.
Lifecycle mismatchKeep EngineRun phase/status completely private to the execution context. Do not link board status logic to EngineRun fields.

Acceptance Signal

Green Signal: Simulated server restarts (cache clears) do not forget running tmux states, ensuring subsequent launches for running tasks reject with 409. Completion observer and manual release correctly sync states on DB rows. No timeout or automatic death-inference pathways are introduced.
