# One query entry per work item, filled by a batched read

Studio holds each work item in its own React Query entry keyed by its id, and nowhere else. The module read returns membership as ids only — root ids, a parent-to-children map, and order — so no read carries records inside a collection. Two hundred rows mount two hundred queries; their `queryFn` calls collect in a ten-millisecond window and leave as one HTTP request against `GET /work-items?ids=…`, chunked at one hundred ids for URL length. Each entry is then filled by its own query resolving, so no code writes into a cache key it does not own. Client state stays in the four existing zustand stores — `uiStore`, `selectionStore`, `dialogStore`, `toastStore` — which already hold ids and view state only; `tasksStore`, `taskTreeCache`, `issueStore`, `backlogStore` and `TaskSummary` are deleted outright.

This reverses ADR-0009, which chose one Redux store as the single source of truth and forbade the request layer from holding records. The reason for the reversal is structural, not a line count: a **work-item change frame** carries identity and revision only, so a request-keyed cache must know every entry holding that item. That objection is fatal to a cache keyed by request shape, and it disappears entirely when the key *is* the item's id — a frame becomes `invalidateQueries(['workItem', id])`, one entry, one row repainted. ADR-0009's own machinery existed to route around a cache it had forbidden to hold data: a read seam, a write seam, and an enforcement test whose only job was to prove the cache was empty. All three are gone. Optimistic writes are `useMutation`'s `onMutate`/`onError` context, as the library supplies them, rather than a hand-rolled write seam. A reorder writes `{before_id, after_id}` — the endpoint is already id-shaped.

Freshness is push, not polling. `staleTime` is an ordinary five minutes rather than `Infinity`, which was only ever needed to prevent a two-hundred-query stampede that batching removes. The status feed's cursor replay (`apps/runs/consumers.py`) closes gaps on reconnect. **This rests on one backend change**: the work-item change revision must advance for every published change, as `backend/worktracker/CONTEXT.md` already defines it and as `issue.py` does not yet do — today it advances only on a state move, so a rename publishes no frame and a client never learns. CODING-145 blocks on CODING-144 for it, and a backend test must fail when a published field changes without the counter advancing, because with push-only freshness a missed bump never heals.

Enforcement, which ADR-0009 correctly identified as the decision that actually matters, survives with the same intent and a smaller surface: a DOM-level rename regression test that references no store or cache; a test that no work-item id appears in two query entries; a walk of every registered client store after a rename asserting the name appears nowhere; and lint rules barring record types from client store files and barring `create` from zustand outside the `createClientStore` factory, so no store escapes the walk. Prose invariants have been false twice here. Rejected along the way: seeding entries with `setQueryData` from one batch response, which is the same one-response-many-keys fan-out shape as the defect being removed and would need a standing exception to the invariant; `@normy/react-query`, which syncs copies rather than removing them; and a nested-tree serializer, which bundles an entity with a collection against CODING-144's read contract and makes every optimistic move rebuild an ancestor path. Measured blast radius: 48 of 208 non-test modules and 45 of 114 test files, not the 200-plus modules and 80-of-89 files the superseded plan assumed. Full reasoning, the paths walked and left, and the rejected alternatives: [`docs/decisions/2026-08-06-one-holding-per-thing.md`](../../../docs/decisions/2026-08-06-one-holding-per-thing.md).
