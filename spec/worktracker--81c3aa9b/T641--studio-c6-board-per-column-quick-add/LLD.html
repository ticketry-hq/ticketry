Modal contract — the one new prop

CreateIssue already takes defaultParentId and passes a body through createIssue. The whole change is a sibling defaultStateId prop that seeds a state field and rides along in the create body.

New prop: defaultStateId?: string | null

sourceThe clicked column's state.id, threaded by BoardView. Backlog's "New issue" / "+ add under" callers omit it → undefined → behaves exactly as today.
seedsModal-local stateId state, reset on each open alongside the existing name/parentId/priority reset effect.
UIA <StatePicker> row in the modal, defaulting to the seeded state; user may re-pick before submit. StatePicker reused as-is — already returns a stateId on change.
on submitBody gains state_id: stateId ?? undefined. Absent → backend falls back to _default_state_id (unchanged behavior for backlog callers).
backendNo change — WorkItemIn.state_id already accepted & persisted (api.py:460); new issue _append_ranks to the column bottom.

Why the store is untouched

  • Pass-through already. createIssue(projectId, body) calls api.createWorkItem(projectId, body) with the whole body and appends the result. WorkItemCreate already declares state_id?.
  • Today's gap is the caller. CreateIssue builds { name, parent_id, priority } and simply omits state_id. Adding it to that object literal is the entire store-side change — i.e. none in the store.
  • Re-bucketing is free. The appended item flows through boardColumns(), which buckets by state.id — so the new card appears in the right column with no board-specific wiring.
  • No optimistic dance. createIssue awaits the server item before inserting (it carries the real nested state), so no rollback path is needed.

The submit body, before → after

// CreateIssue.tsx — submit()
const created = await createIssue(projectId, {

  parent_id: parentId,
  priority,

Filter seed-resolution

A plain top-level new card can be hidden by an active board filter. BoardView resolves a seed parent from the live epic filter so the card stays visible in the view that created it. Pure function of filters.epicIds — no store change.
Active board filterSeeded defaultParentIdWhy
Exactly one real epic (epicIds = [epicId])epicId → card becomes a story under that epicCard passes passesEpic and shows in the filtered board immediately.
No-Epic sentinel (epicIds = ["none"])null → plain top-levelNO_EPIC = "none" is not a real module id; a top-level card matches the No-Epic member.
No epic filter (epicIds = [])null → plain top-levelUnfiltered board shows everything; nothing to seed.
Sprint filter (filters.sprintId)not seededThe board's BoardFilterBar exposes no sprint control, and create has no sprint_id field (PATCH-only). A stale cross-view sprintId is ignored for seeding — out of this thin FE scope.
The board's BoardFilterBar is single-select (epicIds[0]), so "exactly one epic" is the only multi-member case reachable from the board today; the resolver still guards length === 1 defensively for any future multi-select.
// BoardView.tsx — derived once, passed to CreateIssue as defaultParentId
const seedParentId =
  filters.epicIds.length === 1 && filters.epicIds[0] !== NO_EPIC
    ? filters.epicIds[0]
    : null;
