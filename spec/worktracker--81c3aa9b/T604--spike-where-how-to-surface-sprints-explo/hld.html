Sprints as “Now / Later” — Lifecycle & Surface

Modules say what a task is; sprints say when. The product need: cleanly separate what I’m working on now from what I’m putting off — without faking it with a throwaway module. This HLD specifies the Now / Later / History model, a start / close sprint lifecycle where closing rolls unfinished work into the next sprint, and the UI lens that makes it visible.

The problem this solves

A real workflow observation, not a feature wish.
Today, to separate “work on now” from “later”, a throwaway module gets created — which corrupts the module axis.
THE BUG IN THE WORKFLOW

Modules used as a time bucket

A “stuff for now” module is invented to hold today’s work. But modules are the what (Auth, API, Billing) — overloading them with when pollutes the backbone and the task no longer lives under its real feature.

THE FIX

Two orthogonal axes

A task keeps its real module (what) and separately carries a sprint (when). “Now vs later” rides the sprint axis — the module axis stays clean. The data model for this already exists (#602): Issue.sprint is a nullable FK, orthogonal to parent.

THE BONUS

History falls out for free

Because a sprint is a time-box, finishing one leaves a frozen record of what got done in that stretch — no extra bookkeeping. Closing a sprint is archiving it.

The model — reuse #602, add only “which one is active”

No new table, no new fields. The existing Sprint.status enum (planned / active / completed) already carries everything: “Now” is simply the one sprint with status = active. The only additions are behavioral: exactly one active per project, and the active sprint may only move forward.
NOW

The active sprint

The one sprint with status = active. Its member tasks are “what I’m working on now”, shown across all modules at once.

sprint.status == "active" (exactly one)
LATER

The backlog

Tasks with no sprint — “yet to tackle”. You pull from here into Now, or push from Now back to here.

issue.sprint_id IS NULL
HISTORY

Closed sprints

Frozen cohorts. Each completed sprint is a record of what shipped in that window. Read-mostly.

sprint.status == "completed"
Forward-only. Sprints carry an order from existing fields (start_date / created_at — no new “increment” column needed). Setting “active” may only target a sprint ordered after the current one — you can never reactivate a completed or earlier sprint. Now marches monotonically forward.

Lifecycle — start, and close-as-advance

Two user actions. Start bootstraps the first Now. Close is the workhorse: it’s an atomic “advance the iteration” — freeze what’s done, roll what isn’t into the next Now. Close always advances to a later sprint, never back. Click a step for its mechanics and edge cases.

Backend delta vs #602

#602 shipped the storage and CRUD. This feature adds zero new model fields: one real operation (close), two behavioral rules, and it surfaces one existing field on reads. Everything else is reuse.
ChangeWhatDetail
REUSESprint model + status enumNo new table, no new fields. “Active = Now” reuses the existing status='active'; the order (“increment”) comes from the existing start_date/created_at.

Question board

Green = decided in this conversation. Amber = genuine forks to settle in the LLD — none block the model.
DECIDED · reuse model

New model, or fit the existing one?

Reuse #602 as-is — zero new fields. “Active = Now” is just status='active'; order comes from existing start_date/created_at. The only new state is which sprint is active, and the enum already expresses it.

DECIDED · forward-only

Can the active sprint move backward?

No. Active advances monotonically — only to a sprint ordered after the current one. Reactivating a completed or earlier sprint is rejected.

DECIDED · close behavior

Where does unfinished work go on close?

Rolls forward into the next sprint (not back to backlog). Done work freezes as history. The point of “close as advance”.

DECIDED · surface

Where do sprints live in the UI?

A Now/Later/History lens in the Modules pane that filters the Tasks pane across modules — plus a DetailsTab Now↔Later toggle. Not a separate screen.

FORK · active marker

How is “the active one” recorded?

Lean: reuse status='active' + the single-active rule (zero new fields). Alternative if you want it explicit: a single Project.active_sprint pointer — still “one small thing”, but a new column. LLD to pick.

FORK · next-sprint identity

Does close advance to an existing sprint, or create one?

Lean: advance to the next existing planned sprint if one exists (you pre-create the pipeline); else auto-create the next one. Either way it must be ordered after the current (forward-only).

FORK · naming & dates on create

If close creates the next sprint, how is it named/dated?

Lean: prompt in the close dialog, pre-filled (start = today, end = +2 weeks). Sprints require name + start/end dates, so a created next-sprint must supply them. N/A when advancing to a pre-made planned sprint.

Relationship to #602 and #603

This feature sits between the two — it consumes #602 and reframes #603.
#602 · CONSUMED

Sprint storage & CRUD

Model, status enum, FK, 5 routes, progress, sprint_id patch — all reused as-is. This feature adds the lifecycle on top.

#604 · THIS

Now/Later lifecycle + lens

The missing verbs (start, close-as-advance, roll-forward) and the first view (the lens). This is the simplest surface that delivers the actual workflow.

#603 · DEFERRED

Planning map (modules × sprints)

The richer 2-axis story map with drag-to-plan becomes a later view, once you outgrow Now/Later. It depends on the same sprint_id-on-read change. Not first.

Acceptance signal

The design is settled when: a task carries its real module and, orthogonally, sits in Now (the one active sprint), Later (backlog), or History (a closed sprint); the developer sees Now across all modules from a lens in the Modules pane and flips a task Now↔Later from DetailsTab; pressing Close sprint performs one atomic step — the done work freezes as a history cohort and the unfinished work rolls into the next (later) Now, never backward; the design adds no new model fields — only the close operation, the single-active + forward-only rules, and surfacing the existing sprint_id on the work-item read, with everything else reused from #602 — and the three LLD forks (active marker, next-sprint identity, naming/dates) are answerable without disturbing this model.
