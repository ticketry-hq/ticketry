Tabbed Ticket Drawer

Requirements for making the WorkTracker issue drawer the primary per-ticket workspace for Details, design docs, and live agent terminals.

State: Backlog Requirements only Input: ticket id only HLD next
Problem Goal Contract Boundary Requirements Trace Split Scope Acceptance

Problem

The user has to leave the ticket drawer to read design docs or work with the ticket's live agent terminals.

Disconnected

Details live in Studio

The current drawer renders the ticket's existing `IssueDetail`, but no docs or terminal workspace.

Separate

Docs and terminals live in `/coding`

The user must switch routes and re-find the same ticket to continue the work.

Risk

Selection models disagree

Studio drawer selection and coding workspace selection are separate state machines today.

Goal

A ticket drawer should become a lightweight issue workspace without becoming another full coding app.

For the user

Open a ticket, stay in context, read its docs, attach to live terminals, and start issue-scoped agent work from the drawer.

For the product

Preserve `/coding` while making the drawer the primary per-ticket surface. The transition should not duplicate terminals or repoint hidden app state visibly.

Input Contract

The drawer presentation receives one thing: the ticket id. Everything else is resolved behind the issue workspace boundary.

Receives issueId / ticket id.
Resolves Details, docs, terminal sessions, dormant doc chips, terminal history chips, and doc-chat overlay state.
Does not receive Project id, module id, worktree path, profile key, or coding selected-task state as drawer props.
Does not do The drawer presentation does not manually assemble run launch scope and does not visibly repoint `/coding` selection.

Requirements

These are user-visible requirements. HLD can decide the implementation shape later.

Details

Pinned core tab

Render the existing Studio `IssueDetail` unchanged as the non-closable Details tab.

Docs

Issue docs in drawer

Discover docs from the ticket id, open them as closable tabs, and keep closed docs as reopen chips.

Terminals

Live sessions in context

Discover, restore, display, and launch issue-scoped terminal runs from the drawer.

Ownership

One terminal DOM owner

The same xterm session must not render in the drawer and `/coding` simultaneously.

First use

No `/coding` prerequisite

Docs and terminal sessions load even if the user has not visited `/coding` in this app session.

Resize

Panel-style drawer width

Use coding-panel-style drag resize and persisted ratio behavior where practical.

Approved Split

Implementation should proceed through these vertical slices, updating the existing CODIN-708 through CODIN-713 children rather than creating duplicate work.

1. Issue drawer tab shell with pinned Details Blocked by: None. Covers stories 1, 2, 3, 14, 15. Adds the drawer tab strip, pinned Details tab using existing IssueDetail, and panel-style resize behavior.
2. Issue workspace orchestration seam Blocked by: slice 1. Covers stories 13, 18, 19. Given only issueId, resolves docs, sessions, profile/API readiness, and issue-scoped launch context without visibly repointing /coding.
3. Single-owner terminal foreground registry Blocked by: slice 2. Covers stories 9, 10, 17. Ensures a live terminal session renders in exactly one xterm DOM owner, with drawer priority while foregrounded and /coding still functional.
4. Drawer Doc tabs and dormant doc chips Blocked by: slice 2. Covers stories 4, 5, 16, 18. Discovers ticket docs by issueId, opens them as closable iframe tabs, and exposes closed docs as reopen chips.
5. Drawer Terminal tabs and run history chips Blocked by: slices 2 and 3. Covers stories 6, 7, 8, 9, 10, 11, 16, 18, 19. Shows live/restorable terminal sessions, lifecycle badges, terminated-run history chips, and starts new issue-scoped runs through the orchestration seam.
6. Doc edit-with-agent overlay in drawer Blocked by: slices 4 and 5. Covers stories 12, 19. Reuses per-doc doc-chat overlay semantics and launches doc-chat through the same issue-scoped boundary.

Scope Boundaries

These constraints keep the PRD from turning into implementation design.

In scope

  • Ticket-id-only drawer input.
  • Details, docs, terminal tabs, chips, and doc-chat overlay.
  • Issue-scoped tab discovery and terminal launch boundary.
  • Single terminal foreground owner across drawer and `/coding`.
  • HLD and revised split children after PRD approval.

Out of scope

  • Retiring `/coding`.
  • Building a second full coding app inside the drawer.
  • Passing project/module/worktree scope into the drawer.
  • Replacing Studio `IssueDetail` with coding `DetailsTab`.
  • Starting implementation from CODIN-703 while it is Backlog.
