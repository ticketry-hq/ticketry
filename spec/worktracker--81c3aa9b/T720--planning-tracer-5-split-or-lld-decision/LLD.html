Planning Tracer 5 — Split Proposal Phase

Low-level plan to add a third phase to the #716/#719 tracer: launch one HLD/splitter run for a Todo task that consumes the locked PRD and writes a code-context-aware HLD with a proposed split tree, then mark the local split state done only when the same task is observed moving into the LLD state. The engine never creates leaf tasks, wires edges, or generates leaf LLDs.

Scope lock

This slice proves the planning split-proposal phase only. The engine launches the HLD/splitter agent and observes the approval transition into LLD; it does not register the proposed split, generate leaf LLDs, or start the next phase.

Build

  • Add split as a third phase beside implement and refine in the existing phase vocabulary.
  • Add a split entry to the per-phase contract: launch recipe plus completion gate.
  • Launch the split recipe only for a task currently in the unstarted group (Todo).
  • Build the HLD/splitter launch prompt from the locked PRD task context, instructing to-issues-style tracer-bullet reasoning and a proposed split tree in the HLD.
  • Carry the destination to_state name through the seam so the gate can match a move into the named LLD state.
  • Complete split only when the active task is observed moving into the state named LLD.

Do not build

  • No split registration: no leaf task creation, no blocked_by edge wiring — deferred to #745.
  • No leaf-level LLD generation — deferred to #743.
  • No hidden/internal lifecycle-state model — deferred to #744; reuse the existing LLD state as the interim approval signal.
  • No engine mutation of Issue.state; the agent or a human moves Todo to LLD.
  • No HLD-artifact existence or content validation before completion counts.
  • No new public HTTP route, MCP tool, Studio action, CLI, UI surface, trigger pipeline (#721), or agent default policy.

Execution loop

One pass, six steps. Trigger (1): an internal caller invokes execute(task_id, agent, phase=split) for a task in the unstarted (Todo) group. Endpoint (6): the phase is marked done when that same task is observed moving into the LLD state, after which the engine stops — it does not chain to #745/#743/#721. Click a node for responsibilities; dashed boxes/edges are seams, the human-paced agent, or deferred phases this slice observes but does not own.

Execution driver

selected
  • Accepts explicit task id, agent, and phase.
  • Validates split starts only from a Todo (unstarted) task.
  • Resolves the destination state name and threads it into the seam event.
  • Does not register the split, generate leaf LLDs, or expose a user trigger.

Completion gate — why state name, not group

The #719 refine gate matched a group change (Backlog to Todo). The split gate cannot, because a move into LLD may not change the group.

The seam fires on state identity

  • The #704 seam detects a transition on state_id identity, not group, so a move between two states in the same group still emits an event.
  • If a project models LLD in the unstarted group, a Todo to LLD move emits an event with from_group equal to to_group equal to unstarted.
  • A group-only gate would either miss that move or fire on unrelated unstarted moves, so the split gate must read the destination state name.
  • The seam payload already carries to_state_id; the driver resolves it to the destination state name before building the reducer event.

The split gate

  • Complete split when the active task is running and the resolved destination state name equals LLD.
  • The source state is unconstrained: any observed move into LLD for the active task is the approval signal.
  • The literal target name LLD is the interim convention recorded in the refinement notes, to be replaced by #744's hidden-state model later.
  • Reaching LLD does not trigger split registration here; it only marks the local split phase done.

Visibility contract

This slice adds no new UI, but the operator should still know where the HLD/splitter run appears and where the proposal is reviewed.

Where the proposal appears

  • The HLD/splitter run uses the existing per-task agent launch flow: the same operator path as starting an agent run from a task.
  • The agent writes the visual HLD with the proposed split tree into the task spec directory and presents it for review in the existing agent terminal/tmux session.
  • The run stays visible through the current Coding app run and terminal surfaces that already attach to launched task runs.
  • The task board shows the user-visible approval signal when the task moves into the LLD state.

What this slice does not add

  • No new Todo button, command palette action, or dedicated planning panel.
  • No engine-specific progress dashboard beyond the existing run record and terminal attach flow.
  • No UI affordance for split registration, recursion, or leaf LLD review; those belong to #745, #743, and #721.
  • No special waiting state in the UI; an HLD/splitter run awaiting human review is still a running agent run.

Implementation harness

The reducer remains the main test seam. Driver and receiver tests only prove boundary adaptation. No code blocks; tests assert the behaviors below.

Reducer tests

  • Execute split from idle produces exactly one launch action with recipe split.
  • Run started records the agent run id and marks status running.
  • Run failed records error text and marks status failed.
  • An issue_state_changed event with to_state=LLD for the active running task marks split done.
  • Completion after done leaves the state unchanged.

Negative tests

  • Unrelated task id is ignored.
  • Destination state name other than LLD is ignored, even within the same group.
  • A to_state=LLD event while status is not running is ignored.
  • Non-Todo split launch raises and does not call spawn_run.
  • Receiver does not mutate WorkTracker state or launch any follow-up phase, registration, or leaf LLD.
