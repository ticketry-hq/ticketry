Rich Description Editing — High-Level Design

Closes gap G05. Today the issue drawer's DescriptionEditor is a raw-HTML textarea: you literally type and read HTML, and the stored markup is rendered straight into the page via an unsanitized dangerouslySetInnerHTML. This slice swaps it for a markdown editor — a markdown source textarea with a small formatting toolbar and an Edit ⇄ Preview toggle — and sanitizes every render. The persisted field never changes: it is still description_html, produced by converting markdown on save. Pure frontend, zero backend, no schema change.

TODAY'S DRAWER
DescriptionEditor (IssueDetail.tsx:71–137) is a plain <textarea> over the raw description_html string — you edit HTML by hand. Read mode dumps that string into the page with dangerouslySetInnerHTML and no sanitization, so a stored <script> would execute. There is no formatting affordance and no preview.
⟶
THIS DESIGN
A markdown editor. The textarea holds markdown, with a toolbar (Bold · Italic · Heading · List · Link · Code) and an Edit ⇄ Preview tab. Save converts markdown → HTML (marked) and patches description_html exactly as today. Re-opening seeds the textarea by converting the stored HTML back to markdown (turndown). Every render — read and preview — is sanitized through isomorphic-dompurify.

The pure-FE round-trip

One persisted field — description_html — unchanged. Markdown is purely a client-side edit convenience: it never reaches the backend, and description / description_stripped are not written. The patch route (api.py · patch_work_item) is untouched.

Save / Preview — markdown → stored HTML

textarea md→ marked→ dompurify→ description_html
Save runs md → HTML and patches { description_html } on the same optimistic patchField path used today. Preview runs the identical md → HTML → sanitize pipeline, so what you preview is exactly what gets saved and later rendered.

Read / Re-edit — stored HTML ⇄ markdown

description_html→ dompurify→ render
description_html→ turndown→ textarea md
Read sanitizes the stored HTML before dangerouslySetInnerHTML. Open editor converts stored HTML back to markdown to seed the textarea — best-effort and lossy by design; legacy hand-HTML or plain text converts on first edit. Empty → the existing "Add a description…" placeholder stays.

The slice, in three pillars

Click a pillar to expand its boundary. The whole change is one component rewrite plus a tiny markdown helper — no store, route, or backend touch.
PILLAR 1 · the round-trip

marked · turndown · dompurify

A small markdown helper module wraps the three libraries; description_html stays the only persisted field.

  • marked (basic config): textarea markdown → HTML string on Save and Preview
  • turndown: stored HTML → markdown to seed the textarea on edit (lossy, accepted)
  • isomorphic-dompurify: sanitize HTML before every render — fixes today's unsanitized injection
  • Save still calls patchField({ description_html }) — the same optimistic path
  • description / description_stripped not written; patch route unchanged
PILLAR 2 · the surface

Toolbar + Edit/Preview

DescriptionEditor grows a button toolbar and an Edit ⇄ Preview tab over the markdown textarea.

  • Toolbar: Bold · Italic · Heading · bullet list · link · inline code — insert/wrap at selection
  • Edit ⇄ Preview tabs (not a live split); Preview = the md→HTML→sanitize pipeline
  • Keyboard: ⌘/Ctrl+B / ⌘/Ctrl+I; ⌘/Ctrl+Enter Save, Esc Cancel
  • Keeps the Save / Cancel buttons and the "Add a description…" empty placeholder
  • Honours the dark Studio theme + existing field tokens
PILLAR 3 · the blast radius

Drawer-only, FE-only

One component in the issue-detail drawer. No backend, no schema/migration, no other description surface.

  • Touches only DescriptionEditor in IssueDetail.tsx + a new md helper
  • No backend, no schema, no migration, no SDK change
  • Story-map / board / backlog description surfaces unchanged
  • No comments/activity (G08), no attachment rendering (C4 #639), no labels (G06)

RESOLVED · edit model

Markdown source or WYSIWYG?

Markdown source. The textarea holds markdown with a toolbar + Edit/Preview tabs — not a contentEditable WYSIWYG. Simplest, deterministic, and keeps the textarea + Save/Cancel shape.

RESOLVED · libraries

Which libraries?

marked + turndown + isomorphic-dompurify — 3 new Studio deps. dompurify matches the web-frontend stack already in the repo.

RESOLVED · persisted field

Does the stored shape change?

No. description_html stays the only persisted field; markdown is client-side only. The patch route and SDK are untouched — zero backend.

RESOLVED · round-trip loss

What about lossy HTML→md re-edit?

Accepted, best-effort. turndown seeds the textarea from stored HTML; legacy hand-HTML / plain text converts approximately on first edit. Not a correctness gate.

OPEN · LLD Q1

marked config + dompurify allow-list

Exact basic-CommonMark options (GFM off, breaks?) and the sanitizer tag/attribute allow-list (what survives, are links forced to safe schemes / rel=noopener?). LLD detail.

OPEN · LLD Q2

Toolbar insertion mechanics

Wrap-vs-insert when the selection is empty, cursor placement after insert, link-URL prompt vs inline placeholder. LLD detail.

OPEN · LLD Q3

Bundle size of 3 deps

marked + turndown + dompurify add weight; confirm acceptable (or lazy-load the editor chunk). Tests extend IssueDetail.test.tsx. LLD detail.
